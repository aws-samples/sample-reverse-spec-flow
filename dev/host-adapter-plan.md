## 1. 目的

`init.sh` が生成する作業リポジトリを、**Claude Code 以外のコーディングエージェントでも同じ手順で回せるようにする**。
対象は Kiro IDE を第一候補とし、Codex CLI・Cursor へ展開可能な構造にする。

**フレームワークの核心価値（依存ゼロ・ツール非依存）を崩さないことが制約。** ホスト固有の結合を 1 つの層に閉じ込め、
本体（規約・手順書・ゲート）はホストを知らない状態を保つ。

## 2. 方針: harness 層（`GP-105` の Playbook 層と同型）

`init.sh` に `--host <surface>` を追加し、ホスト固有の配置・語彙・任意のフックを `hosts/<surface>/` に閉じる。

```
hosts/
├── README.md              # 対応表（SUPPORT_LEVEL 欄を必須）
├── _template/
│   ├── profile.env        # 能力宣言（読み手は init.sh と手順書だけ）
│   ├── entry.md           # 規範の読ませ方 ＋ ツール名対応表
│   ├── placement.sh       # 配置処理（ホストを知る唯一のコード）
│   ├── skills/            # サーフェス native 形式（SKILL.md / .mdc / rules）
│   ├── hooks/             # 任意。縮退経路の明記が必須
│   └── MEASURED.md        # 実測記録（版・日付・3 回再現）＝SUPPORT_LEVEL の根拠
├── claude-code/           # 現状の挙動を移設（root-CLAUDE.md.template もここへ）
│   ├── agents/spec-verifier.md    # 検証官の定義（共同開発者が core 直下から移設）
│   └── hooks/verifier-guard.sh    # 読み取りを SOURCE_PATH 配下に制限（fail-closed）
├── kiro-ide/              # ← 私
└── kiro-cli/              # ← 共同開発者（kiro-verify.sh で別セッション起動）
```

### 2.0 `entry.md` は生成先へ `HOST.md` として写す（2026-10-22 に追加）

**`entry.md` をフレームワーク側に置くだけでは、実行時（生成先で作業しているセッション）から読めない。**
`placement.sh` が生成先のルートへ **`HOST.md`** として写し、手順書と skill は
「`HOST.md` に従う」と**役割で書く**（ツール名・パスを書かない）。

**これは当初の設計の穴で、共同開発者が埋めた。** 「手順書に反映されていない運用ルールは実行時には存在しないのと同じ」
（`pipeline.md` 追記ルール6）と同型の抜けだった——配布されない文書に規律を書いても実行時には無い。

### 2.1 `gates.sh` は `profile.env` を読まない

`profile.env` を見るのは **`init.sh`（配置）** と **work-plan の並列プロファイルを書く人/AI** だけ。
ゲートは work-plan の**記載内容**だけを見る（既存の `G-PARALLEL` と同じ作り）。

**理由**: ゲートがホスト設定を読むと、同じ成果物の合否がホストで変わり、完走試験 R1〜R4 と R5 を比較できなくなる。

### 2.2 2 層の直交性

| 層 | 軸 | 正本 | 知ってはいけないこと |
|---|---|---|---|
`playbooks/<domain>/` | スタック（`GP-105`） | `enumeration.md`（分母の定義） | ホスト |
`hosts/<surface>/` | ホスト × 機構世代 | `profile.env`（能力宣言） | スタック |

## 3. 参照した先行事例（AI-DLC）

`awslabs/aidlc-workflows` が同じ軸を採っている（`core/` ＋ `harness/<host>/`、7 サーフェス）。
**層の切り方は借りるが、実装技術は借りない**（約 1,900 ファイル・TypeScript/bun・独自インストーラ・プラグイン機構。依存ゼロと衝突する）。

借用した補正は 5 点。

1. **軸は「ベンダ」ではなく「ホスト × 機構世代」。** AI-DLC は `kiro-ide`（Kiro IDE 1.x ＋ Kiro CLI v3）と `kiro`（CLI v2）を別 harness として持つ。agents 形式が `.md` と `.json` で違う。
2. **ツール名の対応表は一級の成果物。** Kiro IDE のサブエージェント起動は **`invoke_sub_agent`**（Phase A で実測）。フックのツール名は世代で 3 系統揺れ（`shell`/`execute_bash`、`write`/`fs_write`/`str_replace`/`fs_append`、`subagent`/`invoke_sub_agent`/`subagent_<agent>`）、ファイルパスも 4 通りの形で届く。
   - ⚠ **未解決の食い違い**: AI-DLC の `harness/kiro-ide/manifest.ts` は「Kiro CLI は `orchestrate_subagent`」と書くが、**Kiro 公式ドキュメントはどのページでも `invoke_sub_agent` とし、`orchestrate_subagent` は記載が無い**。一次情報が 2 つあって矛盾している。**確定するまで対応表に書かない。**
   - ⚠ **CLI は別製品である**（Phase A の実測）。手元の `kiro-cli` は **2.33.0** で IDE の **1.4.5** とは別の版系列。`/usr/local/bin/kiro` は IDE のランチャ（VS Code の `bin/code` へのシンボリックリンク）で CLI ではない。**IDE の実測結果を CLI に適用してはいけない**——少なくとも並列上限の定数は CLI バイナリに存在しない。
3. **能力は内側から検出できない。宣言（ピン止め）が唯一の守り。** Kiro CLI の既定 v2 エンジンは `.kiro/hooks/*.json` を登録しないが、フックの内側からそれを検出できない。
4. **版で挙動が変わる前提でフィクスチャを置く。** ただし**この実践の根拠は AI-DLC ではなく自前の実測**（Claude Code 2.1.265 と 2.1.267 で `AGENTS.md` の読み込み挙動が違う。教訓 38）。AI-DLC の版ピン止めは自身の版で、ホスト版を名前に持つのは 1 件だけだった。
5. **アダプタは「フックを必須経路にしたコスト」。** 7 harness のうち claude だけアダプタを持たない。フック処理に正規化が要らないため。**ゆえにフックを必須にしない判断が裏側から支持される。**

**真似しない点**: AI-DLC の reviewer scope 強制（`PreToolUse` フック）は **fail-open** を明言している（dispatch 記録が無い・古い・不正な場合は通す＋環境変数で無効化可）。本フレームワークは fail-open を最大の危険と位置づけるので採らない。

#### 既存ゲートが最も危険な経路を既に塞いでいる（本体の変更が不要な理由）

`grep_search` の 0 件が最も危険なのは Phase 1 の列挙だが、`enumeration.md` は
**全走査コマンドを文字列として記録すること**を要求し、`G-ENUM-SOURCE` が記入を、
`G-SCANCMD` がコマンドの再現性を検査する。**`grep_search` はコマンド文字列として残せない**ので、
それで数えた分母は欄を埋められず `G-ENUM-SOURCE` が FAIL する。

→ **本体を変えずに守られている。** 残る穴は **Phase 2/3 の個別調査で 0 件を「無い」と読む経路**で、
ここはゲートに掛からない（規律で守る範囲として明記する）。

#### harness 層に書く規約（Phase B で実装する）

**`profile.env`**:

```
SOURCE_IN_WORKSPACE=no            # 解析対象はワークスペースに入れない（SB-5 を配置で担保）
HOST_SEARCH_SCOPE=workspace-only  # grep_search / file_search はワークスペース内のみ
SOURCE_SCAN=shell                 # 解析対象の走査はシェル経由に限る
SOURCE_READ=approval-required     # 解析対象の読み取りは承認が必要
UNATTENDED=conditional            # 無人実行は承認のセットアップ次第
```

**`entry.md`** に 3 件:

1. **`grep_search` / `file_search` を解析対象に使わない。** 走査範囲外では**エラーでなく 0 件**が返るため、
   「無い」と読むと分母が静かに空になる（`GP-2` ルール5 の全走査要求に違反する）。
2. **解析対象の走査はシェル（`grep -r` / `find`）で行い、コマンドを成果物に残す**
   （既存の `enumeration.md` / `G-SCANCMD` の作法がそのまま効く）。
3. **0 件は `unknown` として扱う。** `GP-4` ルール8 の原則
   （Playbook の `gate-snippets.sh` が `NR ? NR : "unknown"` を返すのと同じ理由）のホスト版。

**`setup.md`**（新規。セッションを開く**前**に済ませる手順）:

- `.kiro/skills/` へ skill を配置する（**提示一覧はセッション開始時のスナップショット**なので事前必須）
- 解析対象への `fs_read` allow と走査用の `shell` allow を承認しておく
- **承認はリポジトリ外に残るので `gates.sh` から検査できない**（「気づかない」のではなく「無人実行が止まる」が症状）

**機械で守っていない範囲**: Phase 2/3 で `grep_search` の 0 件を「無い」と読む経路。
`entry.md` の規律と `UNKNOWN[partial]`（確認した範囲を書く）に頼る。

**残すもの**: フレームワーク自身の `CLAUDE.md` への言及（`pipeline.md:1700, 2474` / `gates.sh:717`）はホストと無関係。
条件付き案内（「Claude Code では `/density-verify` を使う」）は中立な文書にあっても正しい書き方なので残す。

したがって `selftest.sh` に足す検査は**ベンダ名を禁じるのではなく「機能上の結合」を禁じる**形にする

         effect: allow

## 7. 検討の経緯（却下した案と、訂正した誤り）

### 7.1 取り下げた案: 独立 Verify の受領証化（W1）

Kiro で `GP-22` の隔離が成立しない場合に備え、独立性の根拠を「ホスト機構」から「受領証」へ移す改修を検討したが、
独立検証で**論証 4 件が崩れた**ため取り下げた。

| 崩れた論証 | 理由 |
|---|---|
受領証でチャネルの崩壊を検出できる | **受領証を書くのが生成者自身**（`skills/density-verify/SKILL.md` §3 で生出力の保存もメインエージェントが行う）。隔離が壊れても同じ形式の JSON を書き続けられる |
引用バイトの再抽出で原典参照を強制できる | `SOURCE_PATH` に触れられる者なら誰でも埋められる。かつ **R4 で実際に起きた誤り 11 件はすべて `verified` ブロック内で、引用した行はどれも実在した**（型は閉じた列挙の漏れ・条件の欠落・引用範囲の外の根拠） |
作業空間の物理分離はホスト非依存 | Kiro は steering と入れ子 `AGENTS.md` を自動で読むので、作業ディレクトリに生成物が無いだけでは別経路を止められない |
R4 ログへの遡及適用が改訂の根拠になる | 合格した主張には引用の記録が無く、測れるのは検証官の引用の正確さだけ。独立性があったかは測れない |

**根本原因は既に起票済みだった**: `dev/developing-the-framework.md`「未着手: 密度 Verify の検証官が誤りに気づいても不合格にしない」。
実際の失敗は「引用が実在しない」ではなく「**反例に気づいた 4 件が `missing` 欄に書かれて不合格にならなかった**」。
対処の方向性（`missing` に「影響する主張」欄を持たせて機械的に不合格と数える）も記載済みで、v2.0.0 は残存誤り率を開示して出しているため意図的に保留されている。
