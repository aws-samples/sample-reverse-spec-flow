# 完走試験（`R1`）の凍結記録 — 安定版リリースの前提

この文書は **試験を走らせる前に、「完走」の定義・測定器・実行条件・記録する量を固定するため**のものである。
走り始めてから定義を変えた結果は使えない（[[SB-101]]）。
**以下を変更したら、その時点で走っている／走り終えた試験は無効になり、やり直しになる。**

**この文書は、試験を開始した後は追記専用。** 未実施（`freeze-state: pending`）のあいだは
**再凍結による §2 の更新を許し**、そのつど「再凍結の履歴」に追記する（**履歴は追記専用**）。
実行中に定義を変えたくなった場合、変更せずに
末尾の「実行中に起きた定義への疑義」に記録し、**その回は無効として再実行する**。

<!-- freeze-state: done -->

**`freeze-state` の取りうる値は `pending`（未実施）と `done`（実施済み）の 2 つだけ**である。
**その回を無効と判定したとき**（§0c・§7。ゲートを直したので測定器が変わった等）は
**`pending` に戻し、§2 を再凍結して「再凍結の履歴」に無効の理由を書く**
——`invalidated` のような第三の値を作らない（検査は第三の値を赤にするので、増やすなら実装と対で直す）。
`done` にするときは §結果 に**実行日と `gates.sh phase4` の出力**を書く
（`selftest.sh` の `T-FREEZE` が「`done` なのに中身が無い」を赤にする。
**`done` と書けばハッシュ突合が飛ぶので、裏付けの無い `done` は検査を丸ごと無効化する**）。

## 0. この試験が何であって何でないか

> **問い: 現在の版は、1 つの解析対象を最後まで仕様化し、完了ゲートを exit 0 で通せるか。**

### 0a. なぜこの試験が要るのか

**どの版も `gates.sh phase4` を exit 0 で通したことがない。**

- 完走した「参照成果物」とされる成果物は **v1.15 系**で生成され、現在のゲートを当てると
  **`FAIL 2 / INCOMPLETE 5 / WARN 1`** である（密度台帳の全 verified・`fabricated_open` 0 は達成している）。
- **v1.17〜v1.22 は「本質層を先に書く」順序**で、効果測定 2 回でその順序が否定された（`FB-16`）。
- **順序をボトムアップに戻した変更は未リリース**である（最後のタグは `v1.22.0`／2026-09-11）。

⇒ **「安定版」と名乗れる根拠が 1 つも無い。** 本試験はその根拠を作るためのものである。

### 0b. この試験は「方式の比較」ではない

E1・E2 は差分設計で 2 回とも判定不能に終わり、E3 は差分設計をやめて絶対水準の実測にした。
**本試験はさらに別で、「合否を持つ 1 本の到達試験」である**——比較相手は無い。
**逐次実行との比較もしない**（§3 のとおり並列を実行条件にするため、比較の条件が揃わない）。

### 0c. 1 回目は「ゲートの調整ラウンド」と読む

**今回強化したゲートは一度も完走試験を通っていない**（2026-09-24〜25 に
`G-SYMMETRY` の空カテゴリ検出・`G-POPULATION` の列挙元と `verified` 側検査・`G-LINK` の範囲拡大・
`gate-config` のキー削除で `rc=2` を追加した）。

⇒ **1 回目に出る未達は「仕様の欠陥」ではなく「ゲートの設計ミス」である可能性が高い。**
**「完走できなかった＝方式が悪い」と読まないこと。** ゲートを直したら測定器が変わるので
**その回は無効**とし、直した版で再度凍結して走らせる（§7）。

## 1. 「完走」の定義（**合否線。事後変更禁止**）

| | 線 | 判定 |
|---|---|---|
| **一次（合否）** | **`bash 03-audit/gates.sh phase4` が exit 0**（`FAIL` 0 かつ `INCOMPLETE` 0） | 到達＝完走 |

**この 1 本だけを合否にする。** 理由:

- 「安定版」の意味は「**利用者が同じ手順で exit 0 に到達できる**」以外に定義できない。
- 中間の線（全カテゴリ非空・`fabricated_open=0`・`verified` 100% 等）は**どこまで許すかの交渉**になり、
  E1・E2 が判定不能に終わった型（線の設計の失敗）を繰り返す。

**`WARN` は合否に影響しない**（終了コードに影響しない設計）。
**`SKIP` は合否に影響しない**が、§5 で件数と理由を記録する（`SKIP` が多いなら「通った」の意味が薄い）。

> **⚠️ 合否線を実施者に渡さない。** 渡すと「exit 0 になる形」を目標に書いてしまう（teaching to the test）。
> 実施者への指示は別文書（`docs/completion-run-instructions.md`）に切り出す。

**E1・E2・E3 と同じ 8 ファイルを固定する**（記録どうしを突き合わせられるようにするため）。
`selftest.sh` の `T-FREEZE` が検査するのは次の 7 つである。

| | 検査 | いつ走るか |
|---|---|---|
| (a) | 主表の行数が期待リテラルの件数（8）と一致 | 常に |
| (b) | 主表のパス集合が期待どおり（**行のすり替えを防ぐ**） | 常に |
| (c) | ハッシュが書かれていない行が 0 行（**突合の免除を認めない**） | 常に |
| (d) | 2 つの表のマーカーが begin/end 各 1 個（走査範囲が一意） | 常に |
| (e) | 各行のハッシュが実ファイルと一致 | **`pending` のみ** |
| (f) | `shasum` / `sha256sum` がある（無い場合は**失効と別の語で報告**） | **`pending` のみ** |
| (g) | Playbook 表が §3 で宣言した Playbook の全ファイルを列挙 | **`pending` のみ** |

**「常に」の列があるのは意図的である。** 当初は `done` に倒すと 13 項目のうち 11 項目
（注入検査を含む）が止まり、**検査が空回りしていないことの証明が恒久的に消えていた**
——教訓 60 の「記録を退避したら検査も消えた」を**時間で再発**させる形だった。
**現物と突き合わせる検査だけを `pending` に限る。**

> **`selftest.sh` 自身も突合の対象にする。** 「自分のハッシュは自分の中に書けないから不動点が無い」は
> **本件には当てはまらない**——ハッシュは `selftest.sh` ではなく**この記録の中**に書くので、
> 「`selftest.sh` を直す → この表を更新する」で**1 手で収束する**。
> **`selftest.sh` を触ると selftest が赤くなるのは仕様である**（教訓 50）。
> 赤を消したくなったら「測定を先にやる」か「再凍結して測り直す」かを決める。
> **検査を緩めて赤を消してはいけない**——8 ファイルのうち最も測定器そのものである 1 本が網から外れる。

### 4a. Windows で実施する場合（2026-09-25 に実測。追記）

**WSL を使う。git bash は使わない。**

実測（ある Windows 機・同一リポジトリ・同一ファイルで 3 回ずつ。仕様書 107 件・密度台帳 181 行の成果物）:

| 操作 | git bash | WSL | 倍率 |
|---|---|---|---|
| `gates.sh phase4` | **26.2 分**（1,534〜1,598 秒） | **3.4 分**（199〜217 秒） | **7.6 倍** |
| `gates.sh session` | 6.6 秒 | 0.8 秒 | 8.0 倍 |

**本試験では `gates.sh` を何十回も走らせる**（各 Phase 境界・各検証ラウンド・各セッション終了時）ので、
**git bash を選ぶと点検だけで数十時間になる**。`phase4` の消費時間はシステム時間が
**git bash で 73%・WSL で 63%** を占め、**プロセス起動が主成分**であることと整合する。

- **実行環境は §4 の表に加えて記録する**（ディストリ・`bash` / `grep` / `awk` の版・`locale` の `LANG`）。
- **WSL の既定ロケールは `C.UTF-8` になりがち**で、それ自体が固有の壊れ方を生む
  （ブラケット式の非 ASCII 範囲で `grep` が異常終了する。本体側で対策済み・機械検査あり）。
  **`LANG` を記録する**——後から「どのロケールで測った値か」を言えるようにするため。
- **`/mnt/*` に置いたままでよい**（WSL1 は NTFS を直接叩く）。WSL 側へコピーした場合はそう明記する。

> **⚠️ 上の絶対値は本試験の成果物とは規模が違う**（測定に使ったのは別ブランチの成果物で、
> `gates.sh` も本記録が凍結した版とは別物である）。**移植できるのは倍率だけ**である。

**load は開始のゲートにしない**（制御できない）。**開始時・各 Phase 終了時に `uptime` の 3 値を記録する。**
**実時間は load とセットでなければ意味を持たない**（同一の selftest が load 13 で 9 分／load 21 で 41 分）。

## 6. `GP-15`（並列）の見直しの判断材料

**本試験では `GP-15` を変更しない**（オプションのまま）。
判断は**実測の後に置く**——変更するかは §5 の #4（実時間の短縮幅）と #5（並列由来の事故件数）で決める。

| 観測 | 示唆 |
|---|---|
| 実時間が大幅に縮み、事故 0 件 | 必須化の根拠になる。ただし**ツール非依存の核心と衝突する**ので、必須化ではなく「支えるホストでは強く推奨」等の中間形を検討する |
| 実時間は縮むが事故が出た | **事故の型を手順に反映するのが先**。必須化は保留 |
| 実時間が縮まない | 必須化しない。並列は「支えるなら使う効率化」のまま |

> **⚠️ `CLAUDE.md` は「ツール非依存・依存ゼロ」を核心価値として明示し、
> この境界を変える提案が来たら必ず確認せよと定めている。**
> **並列を規約として必須化すると、並列を支えないホストで手順が成立しなくなる**——
> これは核心価値と正面から衝突する。**実測は必須化の十分条件ではない。**

## 7. 除外基準

| 除外するもの | 扱い |
|---|---|
| 環境固有の失敗（メモリ・ディスク不足による打ち切り） | **打ち切りは「合否不明」**——再実行する |
| **負荷による実時間の伸び** | 実時間のみ除外。品質側の量は有効（load を記録してあれば判断できる） |
| **ゲート自身の設計ミスに起因する未達** | **記録し、直して再凍結・再実行する**（§0c。直すと測定器が変わるのでその回は無効） |
| 母集団の外のファイルに起因する未達 | 母集団の外 |
| `WARN` のみのゲート | 終了コードに影響しない設計 |

**除外しないもの**: 分母の定義が終盤で覆った巻き戻し／全称主張の検証で差し戻ったラウンド／
是正が新しい誤りを作った分／**隔離 Verify の運用上の失敗**（エージェントが落ちた等。**方式のコストとして数える**）／
**並列由来の事故**（競合・ID 衝突・取りこぼし。**並列を実行条件にしたのだからコストとして数える**）。
