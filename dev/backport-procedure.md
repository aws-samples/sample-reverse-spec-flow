# 知見の還元手順（プロジェクト → フレームワーク）

生成された `<source>-spec/` リポジトリで得た汎用知見を、フレームワーク本体（`reverse-spec-flow`）の
`pipeline.md`（GP-N）/ `playbook.md`（SB-N）へ戻す手順。

## なぜ手順が必要か（この文書が生まれた経緯）

`init.sh` は `pipeline.md` / `playbook.md` を生成先へ**コピー**する。コピー先は別リポジトリの
切り離されたスナップショットであり、そこに追記された知見は放っておくとフレームワークに戻らない。

**実際に起きたこと（2026-08-10 実測）**:

**対策（2 段構え）**:
1. **採番の名前空間分離**: プロジェクト側は `GP-<spec-name>-N` / `SB-<spec-name>-N` を使う
   （`init.sh` がコピーの冒頭に宣言を注入し、`AGENTS.md` にも明記する）。
   これで「プロジェクトで汎用知見を書く」行為を禁止せずに ID の一意性を保てる。
2. **本手順書**: 還元を明示的な工程にする。

## 手順

### 0. 採番の起点を実測で確認する（新 GP/SB を作る前に必ず）

**記憶や「前回空けた番号」で判断してはいけない。** プロジェクト側は作業継続中に採番を進めるため、
数日前の調査結果はすでに古い。実際に Phase G で「Phase F で 23 番が空いた」と記憶で判断し、
既に使用済みの GP-23 と衝突させた（自分が作った衝突対策を自分で破った）。

```bash
# フレームワーク本体
grep -oE '^## GP-[0-9]+' pipeline.md | grep -oE '[0-9]+' | sort -n | tail -1
grep -oE '^## SB-[0-9]+' playbook.md | grep -oE '[0-9]+' | sort -n | tail -1
# 全 spec リポジトリ（占有済み番号）
for r in <workspace>/*-spec; do
  p="$r/spec-extraction/docs/knowledge"
  [ -f "$p/pipeline.md" ] || continue
  printf '%-28s GP=%s SB=%s\n' "$(basename "$r")" \
    "$(grep -oE '^## GP-[0-9]+' "$p/pipeline.md" | grep -oE '[0-9]+' | sort -n | tail -1)" \
    "$(grep -oE '^## SB-[0-9]+' "$p/playbook.md" | grep -oE '[0-9]+' | sort -n | tail -1)"
done
```

**新番号は「全リポジトリの最大値 + 1」以降を採る。** 途中の番号は欠番として保持する。

### 1. 還元候補を一覧する

プロジェクトリポジトリで:

```bash
grep -nE '^## (GP|SB)-[a-z0-9-]+-[0-9]+' spec-extraction/docs/knowledge/{pipeline,playbook}.md
cat spec-extraction/docs/knowledge/FRAMEWORK-VERSION   # 生成時のフレームワーク版
```

`FRAMEWORK-VERSION` の `framework_commit` は「どの版を基準に得た知見か」を示す。
その版以降にフレームワーク側で同じ問題が既に解決されている場合があるので、必ず先に確認する。

### 2. 1 件ずつ再利用範囲を判定する

<!-- source-column: 0 -->  出所欄なし

| 判定 | 意味 | 行き先 |
|-----|------|-------|
| **汎用** | 言語・スタックを問わず、他のリバースエンジニアリング案件でも成立する | フレームワークの `pipeline.md` / `playbook.md` に**新番号で**追記 |
| **ドメイン** | 特定の技術スタックでのみ意味を持つ（JVM アノテーション・ORM 方式など） | 該当 Playbook の `practices.md`（`DP-<domain>-N`） |
| **プロジェクト固有** | その対象システムだけの癖 | 還元しない（当該リポジトリに残す） |

**判定は厳しめに行う**: 「汎用的な原則を述べているが、例がすべて特定スタック依存」の場合は、
**原則が抽象化に耐えるかを確認し、耐えるなら例を差し替えてから汎用として入れる**。
耐えないならドメイン行き。

### 2b. 出所の秘匿性を判定する（**還元の前に必ず。飛ばせない工程**）

> **還元はプロジェクトの情報がフレームワークへ流れ込む唯一の経路であり、
> フレームワークは配布物である。** つまりこの工程は、そのまま「配布物に何を載せるか」の判定である。

判定は 2 段。**知見の内容**と**出所の名前**を別々に見る。

<!-- source-column: 0 -->  出所欄なし（ラベルの書式例のみ）

| 見るもの | 判定 | 扱い |
|---------|------|------|
| **出所の名前** | 公開 OSS など、名前を出して差し支えない | 実名を書く |
| | それ以外 | **匿名ラベル**（`プロジェクト A` の形式）を使う |
| **知見の内容** | 抽象化すれば汎用の原則になる | **原則と数値だけ**を書く |
| | 業務ドメインの語・画面名・固有の識別子が必要 | **抽象化してから**入れる。抽象化できないなら還元しない |

やること:

1. **匿名ラベルを使う出所は、詳細な実測データをリポジトリに置かない。**
   手元の退避ファイルに残し、判定時にそこを読む。リポジトリへ入れるのは
   **抽象化した原則と、出所が分からない形の数値**だけにする。
2. **匿名ラベルに出所の性質を書かない。** 所属・業種・規模・社外かどうか・機械生成かどうかを
   書き添えると、ラベルだけでは絞れなかった母集団が絞られる。**ラベルを伏せても性質が残れば同じ**
   ——「機械生成したプロジェクトは 29 件中 28 件」のように**性質を数値の修飾語として書くと、
   別の箇所にある「そのラベルは機械生成」という記述と結合して一意に対応する**（実際にこの形で書きかけた）。
3. **例を差し替えるときは「実名を消す」のでは足りない。** 業務ドメインの語（扱う対象・
   帳票名・状態名）が残ると出所は容易に推定される。**原則が成立する最小の語彙まで落とす。**
4. **実測値は「プロジェクト別の内訳」と「絶対数」を書かない。** 公開 OSS を実名で数件挙げ、
   その横に匿名ラベルを 1 つ置くと**消去法で正体が絞られる**。
   規模（モジュール数・件数の分母）は**それ自体が顧客システムの情報**である。
   **「N プロジェクトのうち M 件でこうだった」までに落とす**——原則を導くのに内訳は要らない。
5. **配布物の範囲を取り違えない。** `init.sh` は `pipeline.md` / `playbook.md` / `templates/` /
   `playbooks/` を**生成先リポジトリへコピーする**。つまり**別の案件のリポジトリに
   ある案件の記述が入る**。「配布物 = `init.sh` と `templates/` だけ」ではない
   ——**リポジトリ全体が配布物**として扱う。
6. **判定の結果を `dev/backport-sources.allow` に 1 行足す。**
   この 1 行が「判定した」記録である。`selftest.sh` T6 がリストに無い識別子を FAIL にするので、
   **この工程を飛ばすと検査で止まる**。

> **文言の注意（2026-09-12 実測）**: 本文書で「`<トークン> 由来`」と書くと、
> T6 層 1 の「ラテン文字トークン ＋ `由来`」パターンに一致して**未許可の出所名として FAIL する**
> （実測: フレームワークの概念名にこの連結を使ったところ、その語が出所名として検出された。
> **偽陽性だが検査は設計どおり動いている**。この注記自身も literal を書くと引っかかるので書いていない）。
> **許可リストに足して黙らせないこと**——`tier` は出所ではない。**「〜起因」等に言い換える。**

**この検査が守らない範囲を理解しておく。** T6 が突合するのは**識別子の形をしたもの**
（`*-spec` 形・`プロジェクト <大文字>`・ラテン文字トークン ＋ `由来`）だけである。守らないもの:

- **業務ドメインの語**（扱う対象・帳票名・状態名・画面名）——機械では判別できない
- **ラテン文字でない新規の固有名**（日本語の会社名・製品名）
- **実測値の並べ方による特定**（上記 2・4 の形）

**「機械検査があるから安全」と読まないこと**——上記 2・3・4 は人が読む工程である。
また `backport-sources.allow` は**顧客名を 1 行足せば緑になる**ファイルでもある
（機械には「載っている名前が非機密か」を判定できない）。
**このファイルの変更は反証レビューの対象にする**（完了条件 4）。

### 3. 既存エントリとの関係を決める（重複を作らない）

新エントリとして足す前に、既存 GP/SB との関係を判定する:

- **重複** → 還元しない（既存エントリを参照するに留める）
- **既存の拡張・限定条件の追加** → **既存エントリを改訂する**（新番号を起こさない）。
  例: 「独立検証は実施の有無でなく検証した割合で報告する」は SB-12 の欠けていた量化なので、
  22 番目の兄弟を作るのではなく SB-12 のチェック方法を改訂する。
- **独立した新しい不変条件** → 新番号で追記する

**同一テーマの GP/SB が対を成す場合、手順・ゲート実装の詳細は GP が正本**で、
SB は「不変条件の宣言＋失敗サマリ＋正本 GP への参照」に圧縮する（CLAUDE.md の構造を崩さない）。

### 4. フレームワーク側で採番して追記する

- 番号は**既存最大 + 1**（`pipeline.md` / `playbook.md` の `<!-- ENTRIES END -->` マーカーの直前に挿入）
- サマリ表に行を追加する
- 失敗に基づくものなら、失敗そのものを `playbook.md` の**実運用フィードバック（FB-N）表**にも追記し、
  新エントリから `FB-N` で参照する

### 5. 手順書への反映を対で決める（最重要）

> **手順書に反映されていない運用ルールは、実行時には存在しないのと同じ。**

新 GP/SB が実行時の作業手順・完了条件を変えるなら、**同じコミットで**
`templates/pipeline-procedure.md.template` の該当 Step に反映する。
どの Step に反映したかをコミットメッセージに書く。

反映先が無い（＝実行時の振る舞いを変えない）と判断した場合も、**その判断を明示する**
（「参照文書のみ。手順書への反映なし。理由: ...」）。暗黙にスキップしない。

ゲート化できる内容なら `templates/gates.sh` にゲートを追加する。
**「機械化できない」を「検査しない」にしない**——機械化不能なら「記録欄が埋まっているか」の存在検査に落とす。

### 6. 検証する

```bash
./selftest.sh    # GP/SB/FB のリンク閉包・サマリ表整合・ゲートの偽陰性/偽陽性を検査
```

### 7. 還元元に痕跡を残す

プロジェクト側の元エントリに 1 行追記する:

```markdown
> → フレームワークの GP-N として還元（framework commit: <sha>, YYYY-MM-DD）
```

これで同じ知見が二度還元されるのを防ぐ。

> **計測の手順（これだけは環境非依存で有用）**: 区間タイマーは `$EPOCHREALTIME`（bash 5+）を使う
> ——`date` を呼ぶとプロセスが増えて計測が対象を歪める。**計測ログは `$WORK` の外に置く**
> ——`$WORK` は終了時の trap で消えるため、`$WORK/timing.tsv` に書くと**完走した実行の値が残らない**
> （実測でこれを踏み、T5/T6 の内訳を 1 度失った）。ただし**リポジトリ内にも置かない**
> ——T6 は `find "$SCRIPT_DIR" ... -name '*.tsv'` で出所ラベルを走査するので混入しうる
> （`.gitignore` は `find -name` に効かない）。`$TMPDIR` に置く。
> なお `EPOCHREALTIME` は**ロケールの小数点**を使うので、`LC_ALL=de_DE.UTF-8` では
> `1789209514,223671` になり差分計算が壊れる（実測）。カンマを点へ正規化する。

##### 最適化を実装する場合に必ず踏む罠（mac で採用を検討するなら先に読む）

**「同一フィクスチャで旧実装と A/B が一致した」は「判定を変えていない」ではない。**
畳み込みは*その入力で通った経路*しか等価性を示さない。実際、全 29 ゲートの出力を `cmp` で
一致させた後に、**未発火の経路で判定が変わる欠陥が 5 件残っていた**（反証レビューが検出）。
危険な型は 5 つ:

1. **集約は退化の仕方が変わる（最も危険）。** awk は**開けないファイルで fatal 終了し、
   それまでに読んだレコードも出さない**（`emit()` が次の `FNR==1` か `END` でしか走らないため）。
   `2>/dev/null || true` で rc を捨てると集約結果が空になり、**全判定が空のまま `report PASS`**
   になる（＝fail-open）。ファイル単位のループは 1 件を飛ばすだけで済んでいた。
   → **集約に畳むときは rc を見て fail-closed にする。**
2. **awk のルール順に依存する挙動。** 旧 `awk -v h="## $sec" '$0==h{f=1;next} f&&/^## /{exit} f'` は、
   **2 回目の `## <節名>` が `$0==h` に先に当たって `next` されるため終端にならない**。
   素朴に `^## ` で break すると、見出しが重複する仕様で**旧 PASS / 新 FAIL に反転**する。
3. **BRE↔ERE の非互換は `+ ? ( ) { } |` だけではない。** **`^` は BRE では RE 先頭のみ特殊**
   （パターン中間に置かれる節名では literal）、**`$` は RE 末尾のみアンカー**。
   grep(BRE) の式を awk(ERE) に移すとき、この 2 文字を漏らすと `a$b` / `a^b` / `$a` / `^a` を
   含む節名で判定が変わる（**節名末尾の `$` は両者ともアンカーなのでエスケープしてはいけない**）。
4. **`awk -v x="$v"` は値のバックスラッシュ escape を解釈する**（`a\tb` → タブ）。
   シェルの `for` で回していた旧実装は解釈しない。→ **`ENVIRON[]` 経由で渡す。**
5. **`match()` / `head -1` の「最初の 1 件だけ」。** `grep -rl "artifact-key: ${key}"` は
   行のどこにあっても一致するが、`match()` は行内の最初の 1 件しか返さない。
   1 行に 2 値ある成果物で取り落とす。→ **残りに対して `match` を回し続ける。**

加えて **`IFS=$'\t' read` は空フィールドを保持しない**（タブは IFS の「空白類」文字なので、
`IFS` をタブだけにしても**連続タブを 1 個に畳む**。bash 3.2 と 5 で同じ仕様）。
集約結果を TSV で渡すなら**空になりうる値は最終列に置き、他の列は必ず 0/1 にする**。
番兵文字（`-` 等）は使えない——実データが同じ値を持ちうる。
また `declare -A` は **bash 4+** で mac の既定 bash 3.2 には無い（現行の `gates.sh` /
`selftest.sh` / `init.sh` は bash 4+ 機能を 1 つも使っていない。この前提を壊さない）。

##### 手順上の失敗（環境非依存。次に必ず避ける）

1. **実行中の `selftest.sh` を編集した。** bash は逐次読み込みするので、前方に行を挿入すると
   バイト位置がずれて途中で壊れる（実測: 3490 行付近に 5 行足したら
   `line 4164: syntax error near unexpected token '('` で中断）。25 分の実行が無駄になった。
   **selftest 自身は「最後まで到達しなかった（rc=2）」と正しく検出した**——最終サマリの無い
   出力を合否に使わない設計が効いた。**実行中はリポジトリ内のどのファイルも編集しない**
   （T5/T6 は docs も読み、T1〜T4 は `templates/` をフィクスチャへコピーする）。
2. **反証レビューを確認実行と直列にした。** レビュー（26 分）と selftest（36 分）は
   どちらも手を塞がないので**並行して走らせられた**。直列にしたため実行が 1 回増えた。
   → **レビューは確認実行と同時に起動する。**
3. **エスケープの検証をインラインのヒアドキュメントで行った。** このホストの Bash ツール層が
   バックスラッシュを 1 段畳むため、**全ケースが偽の DIFF になった**（`\\\\&` が `\\&` になる）。
   → **実ファイルから該当行を抽出して組み立てる**（既知の罠を自分で踏んだ）。

##### 下限（実装しても越えられない）

**プロセス起動のコスト × 検査件数**が床になる。この機では検査 750 件 × 最低 1 プロセス ≒ 150 秒。
それ以上の短縮は WSL2 か EDR の除外設定が必要で、**フレームワーク側では動かせない**。
