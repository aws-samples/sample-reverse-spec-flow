# 完走試験（`R5`）の実施指示書（**実施セッションに渡すのはこの文書だけ**）

この文書は凍結記録（設計側が保持）の**実施者に渡してよい部分だけ**を自己完結した形で切り出したものである。
**凍結記録本体は渡さない**（合否線と判定規則を含むため。その所在は §6 の参照禁止表にある）。

> **なぜ分けるか**: 合否線を知ると「その線に届く形」を目標に書いてしまう（teaching to the test）。
> **あなたは「通す」ことを目標にせず、手順どおりに最後まで作り切ることを目標にする。**
> ゲートの未達が出たら**直す**が、**ゲートを緩める・迂回する・目視で代替することは禁止**である。

---

## 1. やること

**解析対象を 1 つ、最後まで仕様化する。** 手順書（生成先の `spec-extraction/pipeline-procedure.md`）に
**全面的に従う**。この文書は手順書を置き換えない——**実行時に従う唯一の文書は手順書**である。
**このホスト（Kiro IDE）での読ませ方・ツール名・禁止事項・検証官の隔離は、生成先のルートの `HOST.md` に従う。**

| 項目 | 値 |
|---|---|
| 解析対象 | `jpetstore`（`/Users/<user>/workspaces/_measure/r5-run/jpetstore`） |
| 断面 | `c9a37f22e0afa06c11dfad26b1a8bf0e1a111d3e` |
| 範囲 | **全能力**（能力の切り方と数は**あなたが Phase 1 で決める**） |
| `purpose` | `rebuild` |
| Playbook | **なし**（この解析対象に合う Playbook が無い。手順書の Playbook なしの経路で進める） |

**成果物の規模の目安は与えない。** 与えると規模を合わせて書いてしまう。

**作業ディレクトリは `_measure/r5-run/`**（解析対象の複製は `r5-run/jpetstore`、生成先は `r5-run/jpetstore-spec`）。
**同じ解析対象を過去の測定で扱った置き場所（`_measure/pa-run/`・`_measure/pb-run/`・`_measure/v-run/`）は参照禁止である**（§6）。

## 1a. 始め方

- **生成先は試験前の準備で作られている**（`init.sh <解析対象> jpetstore rebuild --host=kiro-ide`。準備は設計側の手順で、この指示書の範囲外）。
  **この指示書の写しは生成先の `spec-extraction/worklog/R5-instructions.md` に置いてある。読むのはそちらである**（フレームワーク側の原本は §6 の参照禁止の範囲にある）。
- **ワークスペースは生成先のリポジトリ（`r5-run/jpetstore-spec`）。** フレームワークのディレクトリや、過去の作業ディレクトリでは始めない。
- **最初に `HOST.md` と `HOST-SETUP.md` を読む。** 解析対象はワークスペースの外にあるので、**走査はシェルで行い**（`grep_search` / `file_search` は外に対して 0 件を返す）、
  原典の読み取りには承認のダイアログが出る（人が承認する。止まったら待つ）。
- **生成先の git の履歴を潰さない**（squash・rebase・履歴の書き換えをしない）。引き渡しは**履歴ごと**行う。
- **Kiro の自動メモリに jpetstore についての記憶が提示されたら、使わずに `R5-run-log.md` に記録する**（過去の測定の記憶である可能性がある）。

## 1b. セッションの記録（Kiro IDE）

**セッションを始めるたび・再開するたびに**、シェルで `echo "$KIRO_SESSION_ID"; date '+%Y-%m-%d %H:%M'` を実行し、結果を `R5-run-log.md` の「セッション」表に 1 行足す。
コンテキストが尽きて新しいセッションに移るのは構わない（引き継ぎは手順書の `worklog/session-context.md` で行う）。

**検証官の隔離の確かめ**（`HOST.md` §5）の出力は、走らせるたびに
`spec-extraction/03-audit/verify-log/isolation-check-<YYYYMMDD-HHMM>.txt` に**そのまま**保存する（加工しない。PASS 以外の行も残す）。

**環境を記録する**: macOS の版・`bash --version` / `grep --version` / `awk --version` の 1 行目・`locale` の `LANG`・Kiro IDE の版（ユーザーに聞く）・使っているモデル。

## 2. 並列実行は手順書に従う

**手順書の「並列化の指針」（`GP-15`）に従う。** ホストが並列サブエージェントを持つ（`HOST.md`。同時に動くのは 5 体まで）ので、**安全区間（ノード列挙・分析・執筆・密度 Verify・監査）は並列が既定**である。
逐次にした区間があれば、理由を `01-code-graph/work-plan.md` (D) の並列プロファイルに語彙で書く（手順書が定めている）。

- **事故対策は手順書の「並列化の指針」の 7 項目**。**担当への指示に必ず書く。**
- **直列を保つ箇所**（フェーズ順序・ユーザー確認ゲート・統合の段）は手順書のとおり。**ノードレジストリはエッジ発見の前に凍結し、凍結後に並列でノードを足さない**（手順書 Step 1-3）。

## 3. 記録すること（**走らせた後で聞かれても答えられないので、その場で記録する**）

`spec-extraction/worklog/` に `R5-run-log.md` を作り、次を記録する。

> **`03-audit/` には置かない。** `03-audit/*.md` は `G-TEMPLATE` の走査範囲で、実行記録は
> ゲート出力や雛形の形をした文字列（`<…>` や `[ ]`）を**説明のために引用する**ので、
> **記録を書くほど未達が増える**。`worklog/` は作業中の文書の置き場で、`G-TEMPLATE` の走査範囲に入らない。
> **ただし `G-PROVISIONAL` は `worklog/` も走査する**——暫定記述マーカーの記法そのもの
> （`<!--` と `PROVISIONAL` を含む HTML コメント）を説明のために書くときはバッククォートで囲む。

| # | 記録する量 | 数え方 |
|---|---|---|
| 1 | **実時間**（全体・Phase 別） | 各 Phase の開始・終了時刻 ＋ `uptime` の 3 値 ＋ 同時に走らせたエージェント数 |
| 2 | **並列の実績** | 同時に走らせたエージェント数（段ごと）・並列にした単位・上限（5 体）で待たされた区間 |
| 3 | **並列由来の事故** | 共有ファイルの競合 ／ ID 衝突 ／ 統合バリアの取りこぼし ／ サブエージェントが落ちた回数 ／ 並列中のコミット ／ 検証官の隔離違反 ／ ラウンド名の上書き ／ 同時実行数の上限での起動拒否 ／ 担当の規則逸脱。**0 なら 0 と書く** |
| 4 | **密度 Verify のラウンド数** | 能力別・ブロック別の `fabricated_found` 推移 |
| 5 | **ブロック分割** | 上限超過で割った回数と、割った後のラウンド数 |
| 6 | **能力数と分母** | Phase 1 で決めた能力数・ノード数・分母の割当 |
| 7 | **密度ブロックから外した主張（分母の理由）** | 分母が原典から再現できないために外した件数と理由（HOLD-9 で外したものは #13） |
| 8 | **ゲートの未達** | `gate-verdicts.tsv` の FAIL / INCOMPLETE / SKIP をゲート別に。**SKIP も理由つきで** |
| 9 | **Verify の 2 種類の内訳** | ラウンドごとに (a) 引用の裏取りと (b) 件数宣言の再現それぞれの `fabricated` 件数と、(b) で見つかった型 |
| 10 | **修復が新しい誤りを作った件数** | ラウンドごとに「修復した行に残った誤り」と「前の巡が見落とした誤り」を分けて数える |
| 11 | **報告と記録の突合で拾った件数** | 担当の報告を記録と突き合わせたとき、**突合で初めて記録に加えた項目**の数。**0 なら 0 と書く** |
| 12 | **並列プロファイル** | work-plan (D) に書いた区間ごとの方式・同時数・逐次の理由（実績） |
| 13 | **HOLD-9 の回数と選んだ選択肢** | ブロックごとに。**自動で選んだもの（初回の切り出し）と人に諮ったものを分ける** |
| 14 | **UNKNOWN の内訳** | 完了時の `gates.sh metrics` の `unknown_*` の値をそのまま写す |
| 15 | **修復が作った誤り** | 台帳 notes の `repair-induced: N` の合計と、それを書いたブロックの数 |
| 16 | **ブロックの大きさ** | 完了時のブロック数・1 ブロックあたりの主張行の平均・主張 3 行以下のブロックの数 |
| 17 | **セッション** | §1b の表（`KIRO_SESSION_ID` と開始時刻）。セッションの切り替えで失われた作業があれば書く |
| 18 | **検証官の隔離の確かめ** | `HOST.md` §5 の確かめを走らせた回数、行の PASS / FAIL / SKIP の数、FAIL の理由（C1〜C5）。FAIL の結果をどう扱ったか（検証し直した等） |
| 19 | **台帳の `verifier` の内訳** | 完了時の `subagent-isolated` / `prompt-isolated` / `fresh-context` / `human` の件数。`subagent-isolated` 以外があれば理由 |
| 20 | **承認で止まった回数** | 承認のダイアログで人を待った回数と、その時の操作（原典の読み取り・サブエージェントの起動・シェル） |

> **担当（サブエージェント）の報告は、記録に写すときに全項目を突き合わせる。**
> 担当の報告を受け取るたびに、**報告の各項目が記録のどこにあるか**を確かめ、無ければその場で記録に加える。

## 4. 詰まったときの扱い

### 4a. ゲートが未達になったら

**直す。** ただし次は禁止である:

- ゲートの定義を変える／閾値を緩める／対象から外す
- 目視で代替する・自己申告で通す（「実質問題ないので進みます」は**設計上の禁止事項**）
- 検査対象のファイルを壊して 0 件にする

**直し方が分からない未達は、直さずに記録して報告する**（`R5-run-log.md` に「未達の内容・試した対処・
なぜ直せないか」を書く）。**フレームワーク自身の欠陥である可能性がある**——それは有効な結果である。

### 4b. 手順書・`HOST.md`・ゲートが矛盾したら

**変更せず記録して報告する。** どれかが誤っているので、その場で判断せず止める。
**このホストで手順書どおりにできないこと**（ツールが無い・承認で進めない等）も同じく記録して報告する。

### 4c. 密度 Verify が収束しないとき

**手順書 Step 3-1d の `HOLD-9` に従う**（上限は緩めない）。初回は手順書のとおり自動で進み、人に諮るのは手順書が定める場合だけである。選んだ選択肢と回数を記録する（#13）。

### 4d. 判断が要る場面（停止して人に諮る）

手順書の `HOLD` トリガーに従う。とくに**分母を縮める判断**・**Phase 境界**・
**高影響な宣言（レディ・監査完了）**は必ず止める。

## 5. 完了の扱い

**`bash 03-audit/gates.sh phase4` を走らせ、出力をそのまま `R5-run-log.md` に貼る。**
**終了コードも書く。** 到達したかどうかの判定は**設計側が行う**ので、
**あなたは「通った」「完走した」と書かない**——**実測値と終了コードだけを書く。**

## 7. 報告の形

終了時（または中断時）に次を報告する:

1. **`gates.sh phase4` の出力と終了コード**（加工しない）
2. **`R5-run-log.md`**（§3 の 20 項目。**0 なら 0 と書く**）
3. **直せなかった未達**（§4a）と、**手順書・`HOST.md`・ゲートの矛盾**（§4b）
4. **手順書のどこで迷ったか**——書かれていなくて自分で決めた判断を列挙する
   （これは手順書の欠陥の一次情報である。「特になし」で済ませない）。**このホストに固有の迷い**（`HOST.md` に無かったこと）は分けて書く

**「完走した」「品質は十分」などの評価は書かない。** 実測値と、迷った箇所だけを書く。
