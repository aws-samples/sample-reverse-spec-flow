# 完走試験（`R2`）の実施指示書（**実施セッションに渡すのはこの文書だけ**）

この文書は凍結記録（設計側が保持）の**実施者に渡してよい部分だけ**を自己完結した形で切り出したものである。
**凍結記録本体は渡さない**（合否線と判定規則を含むため。その所在は §6 の参照禁止表にある）。

> **なぜ分けるか**: 合否線を知ると「その線に届く形」を目標に書いてしまう（teaching to the test）。
> **あなたは「通す」ことを目標にせず、手順どおりに最後まで作り切ることを目標にする。**
> ゲートの未達が出たら**直す**が、**ゲートを緩める・迂回する・目視で代替することは禁止**である。

## 1b. Windows で実施する場合は WSL を使う

**git bash（MSYS2）は使わないこと。** 判定結果は同じだが、**点検の実時間が 7.6 倍**になる（実測）。
本試験は `gates.sh` を**各 Phase 境界・各検証ラウンド・各セッション終了時**に走らせるので、
**点検だけで数十時間の差**になる。

- **記録すること**: ディストリ・`bash --version` / `grep --version` / `awk --version` の 1 行目・
  `locale` の `LANG`（WSL の既定は `C.UTF-8` になりがちで、ロケール固有の壊れ方があるため後から
  「どのロケールで走らせたか」を言えるようにする）。
- `/mnt/*` に置いたままでよい。**WSL 側へコピーした場合はそう明記する。**

## 2. 並列実行は必須である（この試験の条件）

**逐次で回さないこと。** 実時間を縮めるのが本試験の目的の一部である。

### 2a. 並列にする単位（**既存の分離軸にのみ写像する。新しい分割を発明しない**）

| 段 | 並列の単位 |
|---|---|
| Phase 1 ノード列挙 | ノード種別・ディレクトリ別 |
| Phase 2 分析 | **縦串（能力）単位**、縦串内はカテゴリ観点単位 |
| Phase 3 密度 Verify | **密度ブロック単位**（隔離サブエージェント） |
| Phase 4 監査 | finding・引用単位 |

### 2b. 直列を維持する（**ここを並列化してはいけない**）

1. **フェーズ順序 0→1→2→3→4。** フェーズをまたいだ並列はしない。
2. **ユーザー確認ゲート**（Phase 0 の参考情報ゲート・各 Phase 境界 = `HOLD-8`）。
3. **統合・整合の段**: コードグラフのマージ ／ `overview` の確定 ／ スライス横断の整合レビュー ／
   共有能力・横断関心事の de-dup。
4. **ノードレジストリの凍結**——エッジ発見の前に閉じる。**凍結後に並列でノードを足さない。**

### 2c. 共有ファイルへ同時に書かない

`01-code-graph/code-graph.md` ／ `specs/cross-cutting.md` ／ `specs/overview.md` ／
`03-audit/traceability.md` ／ `03-audit/density-ledger.tsv` は**単一の書き手がバリアでマージする**。
並列エージェントは各自 `02-analysis/<slice>.md` 等に書く。

### 2d. 先に決めておくこと（**後から直せない**）

**ID の接頭辞と宣言形式を Phase 1 の work-plan で全能力分まとめて割り当てる。**
並列だと後から気づいても直せない——**是正の一括置換が別能力の主張を書き換える**。

- **接頭辞**: 能力ごとに分ける（分けないと 2 本目で `REQ-01` が衝突する）。
- **宣言形式**: **1 つに固定**し、`work-plan.md` の「ID 名前空間」欄に**形式も**書く。
  形式が揃っていないと機械走査が**黙って 0 件を返す**（実測で、別形式の 155 件を 1 件も拾えなかった）。

## 3. 記録すること（**走らせた後で聞かれても答えられないので、その場で記録する**）

`spec-extraction/worklog/` に `R2-run-log.md` を作り、次を記録する。

> **`03-audit/` には置かない。** `03-audit/*.md` は `G-TEMPLATE` の走査範囲で、実行記録は
> ゲート出力や雛形の形をした文字列（`<…>` や `[ ]`）を**説明のために引用する**ので、
> **記録を書くほど未達が増える**（前回の試験で実測）。`worklog/` は作業中の文書の置き場で、
> `G-TEMPLATE` の走査範囲に入らない。**ただし `G-PROVISIONAL` は `worklog/` も走査する**——
> 貼り付けたゲート出力（`<パス>.md:<行>:…` の形）は数えない設計だが、**暫定記述マーカーの記法そのもの**
> （`<!--` と `PROVISIONAL` を含む HTML コメント）を説明のために書くときはバッククォートで囲む。

| # | 記録する量 | 数え方 |
|---|---|---|
| 1 | **実時間**（全体・Phase 別） | 各 Phase の開始・終了時刻 ＋ **`uptime` の 3 値を併記**（load が無いと実時間は比較に使えない）。**WSL1 では `uptime` / `/proc/loadavg` が固定値を返す**ので、その場合は固定値であることを書き、**壁時計時刻と同時に走らせたエージェント数**を代わりに記録する |
| 2 | **並列の実績** | 同時に走らせたエージェント数（段ごと）・並列にした単位 |
| 3 | **並列由来の事故** | 共有ファイルの競合 ／ ID 衝突 ／ 統合バリアの取りこぼし ／ サブエージェントが落ちた回数。**0 なら 0 と書く** |
| 4 | **密度 Verify のラウンド数** | 能力別・ブロック別の `fabricated_found` 推移 |
| 5 | **ブロック分割** | 上限超過で割った回数と、割った後のラウンド数 |
| 6 | **能力数と分母** | Phase 1 で決めた能力数・ノード数・分母の割当 |
| 7 | **密度ブロックから外した主張** | 分母が原典から再現できないために外した件数と理由 |
| 8 | **ゲートの未達** | `gate-verdicts.tsv` の FAIL / INCOMPLETE / SKIP をゲート別に。**SKIP も理由つきで** |
| 9 | **Verify の 2 種類の内訳** | 手順書は Verify を **(a) 引用の裏取り** と **(b) 件数宣言の再現** に分けている。ラウンドごとに (a) と (b) それぞれの `fabricated` 件数を書く。**(b) で見つかった型**（数が違う・コマンドが実行できない・裏付けが無い）も書く |
| 10 | **修復が新しい誤りを作った件数** | ラウンドごとに「修復した行に残った誤り」と「前の巡が見落とした誤り」を分けて数える。**修復の波及がブロックの外に出た件数**も書く |
| 11 | **報告と記録の突合で拾った件数** | 担当の報告を記録と突き合わせたとき、**突合で初めて記録に加えた項目**の数（下の注記）。**0 なら 0 と書く** |

> **担当（サブエージェント）の報告は、記録に写すときに全項目を突き合わせる。**
> 前回の試験では、担当が報告した発見の一部が**報告の中だけに残り、記録に入っていなかった**
> （引き渡しの後、設計側の確認質問を受けて初めて見つかった）。担当の報告を受け取るたびに、
> **報告の各項目が記録のどこにあるか**を確かめ、無ければその場で記録に加える。

## 4. 詰まったときの扱い

### 4a. ゲートが未達になったら

**直す。** ただし次は禁止である:

- ゲートの定義を変える／閾値を緩める／対象から外す
- 目視で代替する・自己申告で通す（「実質問題ないので進みます」は**設計上の禁止事項**）
- 検査対象のファイルを壊して 0 件にする

**直し方が分からない未達は、直さずに記録して報告する**（`R2-run-log.md` に「未達の内容・試した対処・
なぜ直せないか」を書く）。**フレームワーク自身の欠陥である可能性がある**——それは有効な結果である。

### 4b. 手順書とゲートが矛盾したら

**変更せず記録して報告する。** どちらかが誤っているので、その場で判断せず止める。

### 4c. 密度 Verify が収束しないとき

**3 ラウンドで `fabricated_found` が 0 にならない、または増えたら停止する**（増加時は 3 を待たない）。
対処は**ラウンドを足すことではなく、ブロックを割ること**である（上限は緩めない）。
割ったら**割った回数と、割った後のラウンド数**を記録する（#5）。

### 4d. 判断が要る場面（停止して人に諮る）

手順書の `HOLD` トリガーに従う。とくに**分母を縮める判断**・**Phase 境界**・
**高影響な宣言（レディ・監査完了）**は必ず止める。

**あなたは「通った」「完走した」と書かない**——**実測値と終了コードだけを書く。**

## 7. 報告の形

終了時（または中断時）に次を報告する:

1. **`gates.sh phase4` の出力と終了コード**（加工しない）
2. **`R2-run-log.md`**（§3 の 11 項目。**0 なら 0 と書く**）
3. **直せなかった未達**（§4a）と、**手順書とゲートの矛盾**（§4b）
4. **手順書のどこで迷ったか**——書かれていなくて自分で決めた判断を列挙する
   （これは手順書の欠陥の一次情報である。「特になし」で済ませない）

**「完走した」「品質は十分」などの評価は書かない。** 実測値と、迷った箇所だけを書く。
