## 1. 何が足りないか

`purpose=rebuild` の完了条件 `fabricated_open=0` は、検証官が生成者の視野を持たないことを前提にしている（GP-16 ルール2・SB-12）。
Kiro IDE ではいま、それを機械で確かめる手段が無く、台帳の `verifier` を `prompt-isolated` に格下げしている。

Phase B で、IDE のカスタムエージェント（`tools: ["read"]` ＋ `permissions` の deny）について次が分かった。

| | 実測 | 隔離への効き方 |
|---|---|---|
| 1 | `specs/` ・ `spec-extraction/` への読み取りは deny で止まる。リンクの別名でも抜けられない。外への deny も効く | **経路 3（自分で読みに行く）は塞げる** |
| 2 | **拒否された読み取りでも、そのフォルダの入れ子 `AGENTS.md` が検証官に注入される** | **経路 2 が残る**（`spec-extraction/AGENTS.md` には解析対象パス・purpose・スコープがある） |
| 3 | 外への allow（エージェントの `permissions`）は効かず、原典を読むたびに承認ダイアログ | 無人では回らない |
| 4 | カスタムエージェントは呼ぶたびに「Sub-agent: <名前>」の承認が要る | 無人では回らない |
| 5 | セッション記録 `sub-executions/<id>.jsonl` に、検証官に注入された文書（`steering_inclusion`）とツール呼び出しの結果が残る | **事後に機械で確かめられる** |
| 6 | workspace の hook はサブエージェントの中でも動く。ただし**渡る情報に呼び出し元のエージェントの区別が無い**（親のセッション ID がそのまま入る） | hook で「検証官だけ」を止めるのは難しい |

## 2. 方針

**「防ぐ」より「確かめて、だめなら採用しない」に寄せる。**

- **防ぐ**: カスタムエージェント `spec-verifier`（`tools: ["read"]`、仕様リポジトリへの deny）で経路 3 を塞ぐ。
  経路 2（拒否されても注入）は防げないので、**検証官への指示で仕様リポジトリを読みに行かせない**（指示は必要だが十分ではない）。
- **確かめる**: 検証官が終わったら、**セッション記録を機械で読み**、次をすべて満たした結果だけを採用する。
  満たさない・判定できないときは**採用しない**（fail-closed）。

| # | 確かめること | 記録のどこを見るか |
|---|---|---|
| C1 | 検証官が **`spec-verifier` として**起動した | メインの `sub_agent_start` の `subAgentName` |
| C2 | 検証官に、**ルート以外の仕様リポジトリの `AGENTS.md` が注入されていない** | 検証官の `sub-executions/<id>.jsonl` の `steering_inclusion` |
| C3 | 検証官が**仕様リポジトリの中のファイルを読めていない**（読み取りは解析対象の配下だけが成功している） | 同 `tool_call` の `status` と引数のパス |
| C4 | **権限が実際に働いていた**（カナリア: 検証官が最初に仕様リポジトリのルート `AGENTS.md` を読もうとし、**deny で拒否された**記録がある） | 同 `tool_result` の拒否文（`Source: subagent-profile`） |
| C5 | 記録が読める形である（`steering_inclusion` が 1 件以上ある。無ければ形式が変わった疑い） | 同 |

C4 はカナリアである。`docs/designs/verifier-isolation.md` の Claude Code 版と同じく、**自己申告ではなく機械の記録**で、
権限が効いていたことを確かめる（`permissions` が読み込まれていない・別の定義で起動した、を検出する）。
ルート `AGENTS.md` は起動時に既に注入されているので、読み取りを試みても新たな昇格は起きない（Phase B の R2 で確認済み）。

### hook で止める案（§11 の候補 A）を採らない理由

hook はサブエージェントの中でも動くが、**どのエージェントの呼び出しかが分からない**（実測。§1 の 6）。
「検証官を起動してから戻るまでの間だけ止める」窓を作る方法はある（hook 自身が `invoke_sub_agent(spec-verifier)` で開き、
`subagent_response` で閉じる）が、**並列で起動したとき・記録が欠けたときに窓の開閉がずれる**。ずれると
メインのエージェントの必要な読み取りまで止めるか、止めるべき読み取りを通すかのどちらかになる。
また hook で止めても**昇格が防げるかは未測定**である。
→ **採らない。** 事後の確かめ（C2）が昇格を直接見るので、hook が無くても判定できる。
**hook は「検証官のツール呼び出しの記録」として補助に使える**（`GP-107` ルール7 の例外）が、必須にしない。

## 3. 部品

```
hosts/kiro-ide/
├── agents/spec-verifier.md          検証官の定義（tools: read、仕様リポジトリへの deny、本文はカナリアの手順だけ）
├── kiro-ide-verify-check.sh         C1〜C5 をセッション記録で確かめる（bash と coreutils だけ）
├── entry.md §5                      起動方法・確かめ方・縮退（生成先では HOST.md）
├── setup.md                         事前の承認（下記）を足す
└── placement.sh                     上の 2 つを .kiro/agents/ と 03-audit/ へ置く
```

### `spec-verifier.md`（案）

```yaml
---
name: spec-verifier
description: 仕様ブロックの敵対的検証官（density-verify の原典突合専用）。生成ブロック本文と原典パスだけを受け取り、解析対象ソースだけを読んで反証する。
tools: ["read"]
permissions:
  rules:
    - capability: fs_read
      effect: deny
      match: ["<仕様リポジトリの絶対パス>/**"]     # placement.sh が生成時に埋める
---
## 隔離の自己確認（最初に必ず行う）
作業ディレクトリ直下の AGENTS.md を read_file で読もうとせよ。これは拒否されるのが正常である。
## 読んでよいもの
指示文で渡された【原典パス】の配下だけ。それ以外のパスを読もうとしない（読もうとするだけで規範が注入される）。
```

- **`hooks` を front-matter に書かない**（IDE は丸ごと無視する）。
- deny は**仕様リポジトリ全体**にし、**ワークスペース基点の相対パスだけ**で書く
  （直下の項目ごとに `<名前>` と `<名前>/**`、加えて `**/AGENTS.md`）。記録上の `resource` も `specs/overview.md` のような相対である。
  **絶対パスを書かない（2026-10-22 ユーザー判断）**: 仕様リポジトリは完成後にコピーして持ち運ぶ前提なので、
  定義にマシンのパスを焼き込まない（焼き込むと、移した先で deny が外れて置き直しが要る）。
  相対の規則が当たるかは V-4 で測る。**当たらなくても漏れはしない**: 読めた・注入された記録が残り、確かめが FAIL にする。
- Phase B で効いた `**/specs/**` 形は使わない。**解析対象ソースの中の `specs/` まで拒否して、検証できなくする**。
- ブロックが引く `path:line` は解析対象ソースの基点からの相対パスである。**相対のまま開くと仕様リポジトリを指す**ので、
  定義の本文で「基点を前に付けて絶対パスに直してから開く」と指示する（直さずに開けば C3 で FAIL になる）。
  **仕様書の引用は相対パスのまま**である（絶対パスが現れるのは検証官への指示文と、検証官が開く操作だけ）。
- ルート `AGENTS.md` は起動時に注入される（deny で止まらない）。**ルートに対象固有の値を書かない規律**（`entry.md` 禁止事項 4）が前提である。

### `kiro-ide-verify-check.sh`（案）

```
使い方: bash spec-extraction/03-audit/kiro-ide-verify-check.sh [--since <UTC時刻>]
  KIRO_SESSION_ID（IDE のシェルに出ている）からセッション記録を探し、
  --since 以降に起動した spec-verifier のすべてについて C1〜C5 を確かめる。
出力: 検証官ごとに 1 行（subSessionId / 判定 / 理由）。
終了コード: 0 = すべて合格 / 3 = 1 体でも不合格・判定不能 / 2 = 前提を満たさない（記録が見つからない等）
```

- **JSON を完全には解釈しない**（依存を増やさない）。1 行 1 イベントの記録から、`"type":"steering_inclusion"` の行の
  `file://<仕様リポジトリ>/…/AGENTS.md` を拾う、など**形が決まった部分だけ**を見る。
  **想定した形が 1 つも見つからなければ不合格にする**（形式が変わったのに黙って合格にしない。C5）。
- 起動時の注入は文字列、昇格した文書は `{"id":…}` の形で記録される（実測）。両方の形を拾う。
  昇格した文書は中身（`"content":"…"`）も記録されるので、**中身の中の `file://` を拾わないよう先に中身を消す**。
- **C3 は厳しめにした**: 拒否されていない呼び出しは `read_file` / `read_code` / `list_directory` で、パスの実体（リンクを辿る）が
  解析対象ソースの配下のものだけを認める。`grep_search` / `file_search` は**使っただけで FAIL**
  （ワークスペース＝仕様リポジトリしか探さない。拒否されたとき結果が絞られるかは未測定）。それ以外のツールも FAIL。
- **C4 は「最初のファイル操作」**で見る。カナリアより前に何かを読めていたら、権限が働いていた保証にならない。
- 実データでの確かめ: Phase B の S3 再測定の記録（`kp-verifier` を `spec-verifier` と読み替えた写し）に掛けると、
  3 体とも **C2: `.kiro/steering/kp-steer-always.md` が注入された**で FAIL になった（測定用に置いた `always` の steering。正しい判定）。
- 記録はリポジトリの外（`~/.kiro/sessions/`）にある。**`gates.sh` はこれを読まない**（`GP-107` ルール4）。
  合否は台帳の `verifier` 欄に写る（下記）。

### 台帳への写し方

| 確かめの結果 | `verifier` 欄 |
|---|---|
| check が rc=0 | `subagent-isolated`（機械で確かめた） |
| check が rc≠0 | **その結果を採用しない**（集計にも台帳にも入れない）。検証し直す |
| check を使えない（記録の形が変わった等が続く） | `prompt-isolated`（明示格下げ）。縮退の扱いは §5 |

## 4. 事前の承認（無人で回すため）

§1 の 3・4 は、**エージェントの `permissions` では解けない**。ワークスペースの承認（`Always allow` → `This workspace`）で
解けるかは**未測定**である（Phase A でも「承認の粒度とキャッシュ」は測っていない）。`setup.md` に足す候補:

| 承認 | 保存先 |
|---|---|
| 解析対象の配下の `fs_read` | `~/.kiro/workspace-roots/<hash>/permissions.yaml` |
| サブエージェント `spec-verifier` の起動 | 同（`capability: subagent` になる見込み。未確認） |

**エージェントの deny はワークスペースの allow より強い**（deny が勝つ。Kiro の評価規則）ので、
ワークスペースに解析対象の allow を足しても、検証官の仕様リポジトリへの deny は崩れない。

## 5. うまくいかなかったときの扱い（**測る前に決める**）

結果を見てから基準を作らない（GP-21 と同じ理由）。本書の案が測定で成り立たなかった場合（C1〜C5 のどれかが記録から判定できない、
または事前の承認で無人実行が成り立たない）、Kiro IDE の検証官は `prompt-isolated` のままになる。その扱いを次から選ぶ。

| 案 | 内容 | 帰結 |
|---|---|---|
| **α** | `prompt-isolated` の結果だけで完了したら、レディ判定を **provisional-ready** にする | SB-12 の文言どおり。**Kiro IDE では `rebuild` を名乗れない**（判定は出せるが「未検証レディ」） |
| **β** | `prompt-isolated` でも完了を認めるが、**完了宣言に件数を書き写す**（`prompt-isolated` のブロック数）。利用者が判断する | `partial` の扱い（GP-5 ルール10）と同型。保証が Claude Code より弱いことは隠さない |
| **γ** | `prompt-isolated` のブロックだけ、GP-16 ルール8 (3) の**人間サインオフ**を併用する | 規模が大きいと現実的でない（R4 の規模で検証結果は約 3,700 件） |

**β に決定**（2026-10-22、ユーザー判断。測定の前に固定）。理由: α は「rebuild が Claude Code だけになる」状態に戻る。γ は規模で破綻する。
β は弱い保証を件数で開示するので、SB-12 の「未検証を隠して名乗らない」に反しない。
β の実装（完了宣言に `prompt-isolated` のブロック数を書き写す）は、本書の案が測定で成り立たなかったときにだけ行う。

## 6. 測定（Phase B と同じ環境 `_measure/pb-run/` を使う）

| # | 測ること | 合格の基準（測る前に固定） |
|---|---|---|
| V-1 | ワークスペースの承認（`Always allow` → `This workspace`）で、検証官が原典を**ダイアログなしで**読めるか | 2 回目以降の読み取りでダイアログが出ない |
| V-2 | 同じく、`spec-verifier` の起動が**ダイアログなしで**できるか | 2 回目以降の起動でダイアログが出ない |
| V-3 | **陰性対照**: 指示どおり原典だけを読む検証官 → check が rc=0 | 3/3 で rc=0 |
| V-4 | **陽性対照**: 仕様リポジトリのファイルを読もうとする検証官（昇格が起きる）→ check が rc=3 | 3/3 で rc=3、理由が C2 |
| V-5 | **陽性対照**: 定義に deny が無いエージェント（`kp-plain` 相当）で起動 → check が rc=3 | rc=3、理由が C1 または C4 |
| V-6 | 記録の形を壊したとき（コピーを加工して与える）→ check が rc=3 | rc=3、理由が C5 |
| V-1b | （V-1 が「ダイアログからは恒久化できない」だったので追加。2026-10-22）ワークスペースの承認ファイル `~/.kiro/workspace-roots/<hash>/permissions.yaml` に原典のルートの `fs_read` allow を**直接書き**、ウィンドウを開き直した**新しいセッション**で、検証官が `controllers/` の外（`service/`）の原典を読む | 原典の Read File のダイアログが出ない、かつ check で PASS。**出たら**「直接書いても恒久化できない」と記録し、原典の読み取りはセッション単位のままにする |

V-6 はフレームワークの selftest で再現した（記録の模型で C1〜C5 の各崩れ方と、形式の変化 4 通り）。
V-1〜V-5 は人が IDE で行う: `dev/kiro-ide-verifier-runbook.md`（`e18ef00` 時点。削除済み・git 履歴に残る）（`dev/kiro-ide-verifier-runbook-gen.py`（`e18ef00` 時点。削除済み・git 履歴に残る） が組み立てる）。
環境は `_measure/v-run/`（`init.sh --host=kiro-ide` で作った素の仕様リポジトリ。Phase B の `kp-*` の仕掛けを持たない）。
**V-1 は試行ごとに別のファイルを読ませる**（承認の保存がファイル単位かディレクトリ単位かを見分けるため）。

**V-1・V-2 が成り立たなければ**、無人実行はできないが**対話実行では使える**（ダイアログを人が Allow する）。
その場合も C1〜C5 の確かめは有効なので、`subagent-isolated` を名乗れる。無人実行の可否は `profile.env` の `UNATTENDED` に書く。

## 7. やらないこと

- 件数の検算官（シェルが要る）の隔離。Claude Code・Kiro CLI でも未確立。
- レンズ反証者（`specs/` を読むのが任務）の隔離。
- hook で止める案（§2）。
