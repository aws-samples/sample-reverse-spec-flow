# 完走試験（`R4`）の凍結記録 — 安定版を作る試験

この文書は **試験を走らせる前に、「完走」の定義・測定器・実行条件・記録する量を固定するため**のものである。
走り始めてから定義を変えた結果は使えない（[[SB-101]]）。
**以下を変更したら、その時点で走っている／走り終えた試験は無効になり、やり直しになる。**

**この文書は、試験を開始した後は追記専用。** 未実施（`freeze-state: pending`）のあいだは
**再凍結による §2 の更新を許し**、そのつど「再凍結の履歴」に追記する（**履歴は追記専用**）。
実行中に定義を変えたくなった場合、変更せずに
末尾の「実行中に起きた定義への疑義」に記録し、**その回は無効として再実行する**。

<!-- freeze-state: done -->

**`freeze-state` の取りうる値は `pending`（未実施）と `done`（実施済み）の 2 つだけ**である。
**その回を無効と判定したとき**（§0c・§7）は **`pending` に戻し、§2 を再凍結して「再凍結の履歴」に無効の理由を書く**。
`done` にするときは §結果 に**実行日と `gates.sh phase4` の出力**、および §1 二次の抜き取りの結果を書く。

## 0. この試験が何であって何でないか

> **問い: 現在の版は、1 つの解析対象を最後まで仕様化し、完了ゲートを exit 0 で通し、
> その完了が分類の付け替えなどの抜け道を通ったものでないと言えるか。**

### 0a. なぜこの試験が要るのか

**R3（2026-10-02〜04）は一次・二次とも合格した**（`docs/completion-run-r3-freeze.md` の結果節）。
ただし密度 Verify の止まり方が重く（HOLD-9 が 77 回、すべて推奨どおりの応答）、ブロックが上限より大幅に小さかったので、
**ユーザーは R3 の版を安定版にせず、次を直した版で R4 を行うと決めた**（2026-10-04）:

1. HOLD-9 の (A)（切り出し）は、その主張にとって初回なら人に諮らず自動で行う。人に諮るのは同じ主張の 2 回目と (B) のときだけ（`GP-103` ルール3）
2. (B)（外して partial）の前に、引用か走査を足して裏付けられるかを 1 回試す（同）
3. 修復が作った誤りを HOLD-9 の巡数に数えない。巡数の総上限は 5。台帳の notes に `repair-induced: N` を書く（同）
4. 同じファイルの同じ節の中なら、密度ブロックを上限（15 主張・8KB）の範囲で束ねてよい。「1 エンティティ / 1 エンドポイント」の上限を外した（`GP-103` ルール1）

**R4 が完走すれば、この版を安定版として固定する**（設計側の判断。2026-10-04）。

### 0b. この試験は「方式の比較」ではない

**合否を持つ 1 本の到達試験**である——比較相手は無い。R1〜R3 の数値とは合否の判断に使わない。
ただし上の修正が狙いどおりに効いたか（HOLD-9 で人に諮った回数・ブロックの大きさ）は、**R3 の値を並べて §結果 に書く**（条件の違いも書く。合否には使わない）。

### 0c. R4 も「ゲートの調整ラウンド」になりうる

**R3 の後に `gates.sh` の判定は変えていない**（コメントと、入れ子の未達の診断文だけ。ゲートは 40 種のまま）。
変わったのは**止まり方と束ね方の規約**（上の 1〜4）で、これは手順書・`AGENTS.md`・skill（`density-verify`）・付録（`rebuild-layer.md`）・台帳の雛形に入っている。
**この規約はまだ一度も完走試験を通っていない。**
⇒ **R4 で出る未達も、まず「ゲートの設計ミス」か「仕様の欠陥」かを分ける**（§5 #2）。
設計ミスなら直して再凍結し、その回は無効とする（§7）。

## 1. 「完走」の定義（**合否線。事後変更禁止**）

| | 線 | 判定 |
|---|---|---|
| **一次（合否）** | **`bash 03-audit/gates.sh phase4` が exit 0**（`FAIL` 0 かつ `INCOMPLETE` 0） | 到達 |
| **二次（合否）** | **設計側の隔離した抜き取りで、下の 4 つの母集団それぞれの不合格が 1 件以下** | 一次と二次の両方で完走 |

**二次の抜き取り**（試験の後に設計側が行う。実施者には渡さない）。**抽出と判定の手順をここで固定する**（事後に交渉しない）。
R3 と同じ設計で、R3 の「実行中に起きた定義への疑義」の 3 点だけを先に決めておく（下の (2) の C・D と走査範囲）。

**(1) 対象の版と原典**: 実施者が引き渡した生成先の**最終コミット**（SHA を §結果 に書く）。原典は断面 `db3915af…` をきれいに取り出したもの。
引き渡しは**履歴ごと**（squash・履歴の書き換えをしない。指示書で求める）。

**(2) 母集団**（出現を単位にする。1 行に 2 つあれば 2 件）:

| 母集団 | 取り出し方 | 不合格の条件 |
|---|---|---|
| **A** `UNKNOWN[undecidable]` | 下の「走査範囲」の出現 | **意図が原典（注釈・命名・文書）から読める**／実装事実の記述が原典と合わない／**読み切っていない**（確定したと書いた事実に、数えていない経路・読んでいない分岐がある） |
| **B** `UNKNOWN[partial]`（範囲に `[[ADR-` を含まないもの） | 同上。範囲が `[[分析物 ID]]` だけのものは、設計側がその分析物の引く `path:line` に解決して原典の位置だけを渡す | 「確認した範囲」の記述が原典と合わない／範囲内で確定したと書いた事実が誤り |
| **C** `UNKNOWN[partial]`（範囲に `[[ADR-` を含むもの＝HOLD-9 などで外した主張） | 同上。**外した主張の文面は、生成先の git 履歴に削除の直前の版があればその文面、無ければ範囲の ADR に書かれた外した主張の記載を渡す**（R3 の疑義 1。どちらを使ったかを件ごとに §結果 に書く。partial 行 1 つにつき、それに対応する外した主張の群を 1 件とする） | 外した主張が原典と**矛盾する**（反証なのに「確かめきれなかった」として渡した）。HOLD-9 以外の ADR の場合は「範囲の外として外したことが原典と矛盾しない」かを見る |
| **D** 付け替え・消失 | 生成先の git 履歴で一度でも `UNKNOWN[blocking]` として追加された出現（`git log -p` の追加行）を列挙し、最終版での行き先を設計側が 1 件ずつ対応づける。行き先が `undecidable` / `partial` のものは A〜C に属するので除き、**`deferred` / `out-of-scope` になったもの、または UNKNOWN が消えた（事実として書いた・削除した）もの**を母集団にする。**コミットの間に現れて消えたものは見えない**（R3 の疑義 2。見える範囲を母集団とし、コミット数を §結果 に書く） | `deferred`: 答えが原典にある／`out-of-scope`: 対応する ADR が無い・範囲外の判断が原典と矛盾する／消えた: 書いた事実が原典と合わない・削除して黙って落とした |

- **走査範囲**: `specs/` 配下の `*.md`。`gates.sh` の `content_spec_files` と同じく、`AGENTS.md`・`CLAUDE.md`・`_` で始まる雛形・`source-index.md` を除く。
  `~~…~~ **解消済**` の行・コードフェンス（mermaid の図を含む。R3 の疑義 3）と HTML コメントの中・凡例の `UNKNOWN[...]` を除く。抽出件数を §5 #8 の `metrics` の値と突き合わせ、差があれば理由を書く。
- **整列と抽出**: 鍵を「パス（リポジトリ相対）・行番号（数値）・行内の出現順」にして `LC_ALL=C` で整列し、
  `python3 -c 'import random; random.Random(SEED).shuffle(rows)'` で並べ替えて先頭から取る。
  **シードは A=`20261006`・B=`20261007`・C=`20261008`・D=`20261009`**。D の鍵は「最初に blocking として追加したコミットの日時・パス・その行の文面」。
- **標本数**: 各母集団 **8 件**（8 件未満なら全件）。

**(3) 判定**:

- **検証官は 1 件につき 2 体**（それぞれ別のコンテキストで隔離。設計側のセッションの既定のモデルを使い、モデル名を §結果 に書く）。
  渡すのは**該当行の文面・(C は外した主張の文面・ADR)・原典のパス**だけで、書き手の推論・分析物・作業記録・本記録は渡さない。
- **2 体とも不合格と判定したものだけを不合格に数える**（判定が分かれたものは境界例として件数と理由を §結果 に書く）。
- 検証官への指示文（この文面で渡す）:

      あなたは隔離された検証官です。渡されたのは仕様の 1 行（と、必要なら外した主張の文面・ADR）と、原典のパスだけです。
      書き手の推論は見ずに、原典を開いて次を判定してください: <母集団ごとの「不合格の条件」の欄をそのまま貼る>
      出力: 判定（合格／不合格）・根拠の path:line・理由を 3 行以内。迷ったら「迷った」と書き、どちらに寄るかも書く。

**(4) 合格線**: **各母集団で、8 件抽出なら不合格 1 件以下、全件（8 件未満）なら不合格 0 件**。母集団が 0 件なら合格（0 件と書く）。

**(5) この線の検出力（二項近似。母集団は 8 件より十分大きいと仮定。事後の解釈の交渉を防ぐために載せる）**:

| 真の不合格率 | 1 母集団で落ちる確率 | 4 母集団のどれかで落ちる確率（独立と仮定） |
|---|---|---|
| 2% | 1% | 4% |
| 5% | 6% | 21% |
| 10% | 19% | 56% |
| 30% | 75% | — |
| R2 と同じ水準（8 件中 7 件） | ほぼ 100% | — |

R2 と同じ水準の失敗はほぼ確実に捕まえる。30% 程度の誤りは 4 分の 1 の確率で素通りする。
検証官 2 体の一致を要求するのは、誤判定（境界例）で正しい成果物を落とす確率を下げるためである。

**この線の理由**: R2 は一次の線だけでは付け替えを捕まえられなかった。R4 は HOLD-9 の (A) を自動にしたので、
**人の確認を通らずに外された・切り出された主張が増えうる**。それが原典と矛盾していないかを C で見る。

**HOLD への応答の方針（応答する人は合否線を知っているので、事前に固定する）**: 応答者は**手順書の推奨どおり**に応える
（HOLD-9 で人に諮られるのは同じ主張の 2 回目と (B) のときだけで、裏付けの追加を試したあとの (B) は承認する。
分母を縮める HOLD-1 は、ADR の理由が原典の事実で裏付けられている場合だけ承認する）。
応答の内容はすべて実施者の実行記録と ADR に残させ、§結果 に件数を書く。

**`WARN` と `SKIP` は合否に影響しない**が、§5 で件数と理由を記録する。

> **⚠️ 合否線を実施者に渡さない。** 渡すと「その線に届く形」を目標に書いてしまう（teaching to the test）。
> 実施者への指示は別文書（`docs/completion-run-r4-instructions.md`）に切り出す。

## 6. 安定版にするかの判断

**一次と二次の両方を満たしたら、設計側はこの版を安定版として固定する手続きに入る**（タグ付けはユーザーの確認を得てから）。

**満たさなかった場合の扱い（R3 と同じ。2026-10-01 にユーザーが決定）**:

| どこで落ちたか | 扱い |
|---|---|
| 一次（未達） | §7 で分類する。ゲートの設計ミスなら直して再凍結・再実行（その回は無効） |
| 二次（抜き取り） | 不合格の**型**を分類する。**規約・ゲートで防げる型なら直して再凍結し、次の試験を行う**。防げない型（検証官でしか捕まらない誤り）なら、結果と誤りの率を利用者向けに明記したうえで、安定版にするかを改めて判断する |

## 7. 除外基準

| 除外するもの | 扱い |
|---|---|
| 環境固有の失敗（メモリ・ディスク不足による打ち切り） | **打ち切りは「合否不明」**——再実行する |
| **負荷による実時間の伸び** | 実時間のみ除外。品質側の量は有効 |
| **ゲート自身の設計ミスに起因する未達** | **記録し、直して再凍結・再実行する**（§0c。直すと測定器が変わるのでその回は無効） |
| 母集団の外のファイルに起因する未達 | 母集団の外 |
| `WARN` のみのゲート | 終了コードに影響しない設計 |
| 二次の抜き取りの不合格 | **除外しない**（§6 の表で扱う） |

**除外しないもの**: 分母の定義が終盤で覆った巻き戻し／是正が新しい誤りを作った分／隔離 Verify の運用上の失敗／並列由来の事故。
