# 完走試験（`R5`）の凍結記録 — Kiro IDE で最後まで回るかを確かめる試験

この文書は **試験を走らせる前に、「完走」の定義・測定器・実行条件・記録する量を固定するため**のものである。
走り始めてから定義を変えた結果は使えない（[[SB-101]]）。
**以下を変更したら、その時点で走っている／走り終えた試験は無効になり、やり直しになる。**

**この文書は、試験を開始した後は追記専用。** 未実施（`freeze-state: pending`）のあいだは
**再凍結による §2 の更新を許し**、そのつど「再凍結の履歴」に追記する（**履歴は追記専用**）。
実行中に定義を変えたくなった場合、変更せずに
末尾の「実行中に起きた定義への疑義」に記録し、**その回は無効として再実行する**。

<!-- freeze-state: done -->

**`freeze-state` の取りうる値は `pending`（未実施）と `done`（実施済み）の 2 つだけ**である。
**その回を無効と判定したとき**（§0c・§7）は **`pending` に戻し、§2 を再凍結して「再凍結の履歴」に無効の理由を書く**。
`done` にするときは §結果 に**実行日と `gates.sh phase4` の出力**、および §1 二次の結果を書く。

## 0. この試験が何であって何でないか

> **問い: 現在の版は、Kiro IDE の上で 1 つの解析対象を最後まで仕様化し、完了ゲートを exit 0 で通し、
> その完了が分類の付け替えなどの抜け道を通ったものでなく、密度 Verify の検証官が隔離されていたと言えるか。**

### 0a. なぜこの試験が要るのか

R1〜R4 はすべて Claude Code で走らせた。`purpose=rebuild` を Claude Code だけのものにしないこと（ユーザーの要件）を
**実際に確かめた記録は無い**。Kiro IDE は harness 層（`hosts/kiro-ide/`）を通して配置でき、Phase A・B・V で
規範の読ませ方・並列・ゲートの実時間・検証官の隔離（`spec-verifier` ＋ セッション記録の確かめ）を測った。
**この試験は、それらが Phase 0〜4 の通しで実際に機能するかを確かめる**（`dev/host-adapter-plan.md` Phase F）。
完走すれば `hosts/kiro-ide` の `SUPPORT_LEVEL` を `verified-full` に上げる（§6）。

### 0b. この試験は「方式の比較」でも「版の安定性の試験」でもない

**合否を持つ 1 本の到達試験**である。版の安定性は R4 で確かめた。R4 と解析対象が違うので、R4 の数値とは比べない。
**解析対象は小さい `jpetstore` を選んだ**（2026-10-22 ユーザー判断。数時間〜1 日で一巡できる規模で、Kiro IDE 固有の詰まりを早く見る）。

**Playbook なしで走らせる**（jpetstore は Spring MVC ＋ MyBatis XML で、手元の 2 つの Playbook のどちらにも合わない）。
**未達や詰まりは、「ホスト（Kiro IDE）に由来するもの」と「Playbook なしの経路に由来するもの」と「それ以外」に分けて記録する**（§5 #2）。

### 0c. R5 は「ゲートの調整ラウンド」になりうる

**R4 の後に `gates.sh` に `G-VERIFIER` を足した**（41 種。台帳の `verifier` 欄を見る）。`fresh-context` の定義と `verify-log` の保存規約も変えた。
**`G-VERIFIER` と harness の検証官（`spec-verifier`・`kiro-ide-verify-check.sh`）はまだ一度も完走試験を通っていない。**
⇒ **R5 で出る未達も、まず「ゲートの設計ミス」か「仕様の欠陥」かを分ける**（§5 #2）。設計ミスなら直して再凍結し、その回は無効とする（§7）。

## 1. 「完走」の定義（**合否線。事後変更禁止**）

| | 線 | 判定 |
|---|---|---|
| **一次（合否）** | **`bash 03-audit/gates.sh phase4` が exit 0**（`FAIL` 0 かつ `INCOMPLETE` 0） | 到達 |
| **二次（合否）** | **設計側の隔離した抜き取りで下の母集団 A〜D それぞれの不合格が線以下、かつ検証官の隔離の確かめ（E）で不合格 0 件** | 一次と二次の両方で完走 |

**二次 A〜D の抜き取り**（試験の後に設計側が行う。実施者には渡さない）。**R4 の凍結記録 §1 の (1)〜(5) をそのまま使う**。違うのは次だけ:

- **対象の版と原典**: 実施者が引き渡した生成先の**最終コミット**（SHA を §結果 に書く）。原典は断面 `c9a37f22e0afa06c11dfad26b1a8bf0e1a111d3e` をきれいに取り出したもの。
- **シードは A=`20261023`・B=`20261024`・C=`20261025`・D=`20261026`**。
- **検証官**: 設計側のセッションの既定のモデル（モデル名を §結果 に書く）で、1 件につき 2 体。2 体とも不合格と判定したものだけを不合格に数える。
- **合格線**: R4 と同じ（各母集団で 8 件抽出なら不合格 1 件以下、全件（8 件未満）なら不合格 0 件、0 件なら合格）。**小さい対象なので全件になる母集団が多い＝0 件の線が多くなる**。

**二次 E（検証官の隔離の確かめ。Kiro IDE で足した線）**:

| | 中身 |
|---|---|
| 母集団 | 最終版の密度台帳で `verify_status=verified` かつ `verifier=subagent-isolated` の**全ブロック**（抜き取らない） |
| 手順 | 設計側が、生成先をワークスペースにした **Kiro のセッション記録すべて**（`~/.kiro/sessions/` のうち `workspacePaths` が生成先のもの）に `kiro-ide-verify-check.sh --session <記録>` を当て、行の `block_id=` から**ブロックごとに最後に検証した `spec-verifier` の判定**を取る |
| 不合格 | (1) 最後の判定が `FAIL` のブロック ／ (2) `spec-verifier` の記録が 1 つも見つからないブロック（`subagent-isolated` と書いたのに機械の記録が無い） |
| 合格線 | **不合格 0 件** |

**この線の理由**: Kiro IDE では検証官の隔離を機械で強制できず、**記録で確かめて採用する**設計にした（`dev/kiro-ide-verifier-isolation.md`）。
採用の規律（PASS の行だけを `subagent-isolated` にする）を実施者が守ったかは、**ゲートからは見えない**（`G-VERIFIER` は語彙と開示しか見ない。機械の証跡＝L3 は未実装）。
だから設計側が記録で全数を確かめる。件数の検算官（`density-verify` §2b）とレンズ反証者は `prompt-isolated` 扱いなので E の対象外である。

**HOLD への応答の方針（応答する人は合否線を知っているので、事前に固定する）**: R4 と同じ。応答者は**手順書の推奨どおり**に応える
（HOLD-9 で人に諮られるのは同じ主張の 2 回目と (B) のときだけで、裏付けの追加を試したあとの (B) は承認する。
分母を縮める HOLD-1 は、ADR の理由が原典の事実で裏付けられている場合だけ承認する）。**HOLD-1 とレディ宣言の確認は、ユーザーが設計側のセッションに転送し、
設計側がこの方針で応答文を作る**（ユーザーは貼るだけ）。応答の内容はすべて実施者の実行記録と ADR に残させ、§結果 に件数を書く。

**`WARN` と `SKIP` は合否に影響しない**が、§5 で件数と理由を記録する。

> **⚠️ 合否線を実施者に渡さない。** 渡すと「その線に届く形」を目標に書いてしまう（teaching to the test）。
> 実施者への指示は別文書（`dev/completion-run-r5-instructions.md`）に切り出す。

## 6. 完走したら

**一次と二次の両方を満たしたら、`hosts/kiro-ide/profile.env` の `SUPPORT_LEVEL` を `verified-full` に上げ、`MEASURED.md` に R5 の結果を書く**
（`hosts/README.md` の対応表も直す）。**満たさなかった場合**:

| どこで落ちたか | 扱い |
|---|---|
| 一次（未達） | §7 で分類する。ゲートや harness の設計ミスなら直して再凍結・再実行（その回は無効）。Kiro IDE の制約で直せないものは `MEASURED.md` と `entry.md` に書き、`verified-smoke` のまま理由を残す |
| 二次 A〜D | R4 と同じ（型を分類し、規約・ゲートで防げる型なら直して再凍結・次の試験） |
| 二次 E | 不合格の型を分類する。採用の規律が守られなかった（FAIL の結果を採用した）なら、**手順書と `HOST.md` §5 の書き方の欠陥**として直す。記録が見つからない型なら L3（機械の証跡）を前倒しする |

## 7. 除外基準

| 除外するもの | 扱い |
|---|---|
| 環境固有の失敗（メモリ・ディスク不足による打ち切り） | **打ち切りは「合否不明」**——再実行する |
| **負荷による実時間の伸び** | 実時間のみ除外。品質側の量は有効 |
| **ゲート・harness 自身の設計ミスに起因する未達** | **記録し、直して再凍結・再実行する**（§0c。直すと測定器が変わるのでその回は無効） |
| 母集団の外のファイルに起因する未達 | 母集団の外 |
| `WARN` のみのゲート | 終了コードに影響しない設計 |
| 二次の不合格 | **除外しない**（§6 の表で扱う） |

**除外しないもの**: 分母の定義が終盤で覆った巻き戻し／是正が新しい誤りを作った分／隔離 Verify の運用上の失敗／並列由来の事故／Kiro IDE の承認で止まった時間。
