## 1. 30 秒でわかる全体像

既存のソースコードを読んで、**ISO/IEC/IEEE 29148 準拠の仕様書**を AI に書かせる仕組み。ただし
「AI にコードを読ませて要約させる」のとは根本的に違う。**AI の出力を信用しない前提で組まれている。**

具体的には次の 3 つが仕込まれている。

| 仕込み | 何のためか |
|-------|----------|
| **中間生成物を必ず経由する** | コードから直接仕様書を書かせない。構造マップ → 分析物 → 仕様書と段を踏ませ、各段を検査できるようにする |
| **数えられる分母を先に作る** | 「全部書いた」を主観で言わせない。コードグラフの全ノードが分母になり、消化率が機械計算される |
| **全部の記述に `path:line` を要求する** | 引用のない断定を残させない。しかも「行番号が付いている」ではなく「その行が主張を裏取りしている」で判定する |

そして最も重要な設計判断——**これらのルールを散文で書かず、`gates.sh` という実行スクリプトにした。**
Phase の完了条件は「AI が完了と言ったこと」ではなく「**`bash gates.sh phase4` が exit 0 を返すこと**」である。

> **なぜそうしたか**: 散文のルールは AI の自己申告で素通りする。実運用で
> 「母集団の 0.6% だけ検証して『検証済み』と宣言され、後の抽出調査で誤り率 29.2% が判明した」
> という失敗が起きている。この仕組みの主要な機能はほぼすべて、**実際に起きた失敗への対策**として入っている。

## 2. 2 つのリポジトリ・2 つのセッション

ここが最初に理解すべき点で、間違えると失敗になる。

```
<workspace>/
├── legacy-order-system/          ← 解析対象。参照専用。コピーも変更もしない
└── legacy-order-system-spec/     ← init.sh が作る独立 git リポジトリ（branch: spec/<spec-name>）
    ├── specs/                    ←   成果物（＝納品する仕様書）
    └── spec-extraction/          ←   作業アセット（手順書・中間生成物・ログ）
```

**セッションも 2 つに分かれる。**

| | 場所 | やること |
|---|---|---|
| **セッション 1** | `reverse-spec-flow/`（このフレームワーク） | `./init.sh` を実行するだけ。**ここで解析作業を始めてはいけない** |
| **セッション 2 以降** | `<product>-spec/`（ルートで開く。`spec-extraction/` で開かない） | `spec-extraction/AGENTS.md` のプレースホルダーを埋め、Phase 0 から実作業 |

分ける理由は、AI に読ませる文書とカレントディレクトリを混ぜないため。フレームワーク本体の
`CLAUDE.md`（開発者向けの規約）と、生成先の `AGENTS.md`（仕様抽出の行動規範）は別物であり、
同じセッションで両方を持つと AI がどちらに従うべきか判断できなくなる。

> ⚠️ 成果物 `specs/` と作業記録 `spec-extraction/` は**同じリポジトリ・同じブランチ**にあり、
> まとめてコミットする。分けない。

## 3. 初期化で決まること（purpose・Playbook）

### 先に決めること: Windows ならシェルを選ぶ

| 環境 | 動くか | 速さ | 備考 |
|---|---|---|---|
| macOS / Linux | ✅ | 基準 | |
| **WSL（Windows では推奨）** | ✅ | **速い** | 既定ロケールが `C.UTF-8` になりがちで、それ自体が固有の壊れ方を生むが**本体側で対策済み** |
| git bash（MSYS2） | ✅ | **遅い** | 判定結果は同じ。実時間だけが伸びる |

**遅さの原因はプロセス起動のコスト**である。この仕組みは点検を `grep`・`awk` の組み合わせで行うので、
プロセス起動の単価がそのまま効く。**実測**（ある Windows 機・同一リポジトリ・同一ファイルで 3 回ずつ）:

| 操作 | git bash | WSL | 倍率 |
|---|---|---|---|
| **完了時の点検（`gates.sh phase4`）** | **26.2 分**（1,534〜1,598 秒） | **3.4 分**（199〜217 秒） | **7.6 倍** |
| 引き継ぎの点検（`gates.sh session`） | 6.6 秒 | 0.8 秒 | 8.0 倍 |
| 本体の自己検査（`selftest.sh`。利用者は走らせない） | 35.7 分 | 6.5〜8.5 分 | 4.2〜5.5 倍 |

**プロセス起動が主成分であることは実測と整合する**——`phase4` の消費時間のうち
**システム時間が git bash で 73%・WSL で 63%** を占める（計算そのものではなく、
プロセスを作る側にコストが寄っている）。

> **⚠️ 絶対値は環境と成果物で変わる。** 上の分・秒は**ある 1 台の Windows 機**で、
> **仕様書 107 件・密度台帳 181 行**の成果物を測った値である。
> 別の機械・別の規模では絶対値が変わる。**倍率（同一機・同一ファイルでの比）だけが移植できる。**
> なお `selftest.sh` の値は別の機会の測定で、成果物の規模とは無関係である。

**判断の目安**:

- **小さい対象を試すだけなら git bash でよい。** 点検 1 回が数分で済む規模なら差は気にならない。
- **1 つのシステムを最後まで仕様化するなら WSL を選ぶ。** 点検は**各段の境界・各検証ラウンド・
  各セッション終了時**に走るので、**何十回も**繰り返す。1 回 26 分と 3 分の差はそこで積み上がる。
- **git bash を選ぶ理由が「環境を増やしたくない」なら、それは妥当な判断である**
  ——判定結果は同じなので、**遅いだけで間違った結論は出ない**。

```bash
./init.sh <解析対象のパス> <spec-name> [purpose] [--playbook <name|path>] [--host <name|path>]
```

`--host` は使う AI ツール（省略時は `claude-code`）。対応ホストと対応レベルは
[README の「対応している AI ツール」](../README_ja.md#対応している-ai-ツール) を参照。

### purpose — 「どこまで作るか」のプリセット

第 3 引数（省略時は対話で選択、既定は `rebuild`）。これが**ゲートの厳しさを決める**。

| purpose | 想定用途 | rebuild 層 | 密度ゲート | 完了条件 |
|---------|---------|-----------|-----------|------------|
| `maintenance` | 保守のための理解 | 作らない | **warn**（警告のみ） | 可読性の床 ＋ コードグラフの分母消化（未着手・分析中が 0） |
| `evaluation` | 再構築の評価・見積り | 骨子まで | **warn**（警告のみ） | 同上 ＋ 本質層の実体 ＋ **割当表の未割当 0** |
| `rebuild` | 再構築の実装まで完走 | フル密度 | **on**（FAIL 判定） | **全数の独立 Verify（`fabricated_open=0`）** |

選択結果は `00-ingestion/gate-config.env` に書き出され、`gates.sh` が毎回読む。

> **どの purpose でも「可読性の床」は FAIL 判定で守られる（`G-READABLE`）。**
> `責務`（何のためにあるか / 業務動線のどこか / 誰が使うか）が空の仕様は、
> **密度ゲートの設定に関係なく**通らない。密度（実装できる深さ）と
> 可読性（何のためにあるかが書かれているか）は**別の要求**なので分けてある。
>
> **以前は `責務` を密度の枠組み（`required-sections`）で実装していたため、
> `DENSITY_GATES=off` だった `maintenance` でだけ検査が切れていた**
> ——**人間の理解が目的の purpose でこそ必要な検査が無効**という逆転で、実運用で判明した設計の誤りである。
> 同時に `maintenance` の密度も `off` → **`warn`** に変えた（off だと「浅い」ことに気づけないまま完了できる）。

> **なぜプリセットにしたか**: 以前は「目標密度」を AI が毎回その場で導出していた。
> セッションごとに基準がぶれ、都合のよい低さに落ち着く。**基準は作業開始前に固定する。**

途中で変えたい場合は `gate-config.env` を編集できるが、これは **HOLD-7**（後述）に該当するので
AI は勝手に変更せず、ADR に理由を残して人に諮る。

> **⚠️ キーの「行を消す」ことで緩めることはできない**（2026-09-24 から）。
> `PURPOSE` / `DENSITY_GATES` / `REBUILD_LAYER` の行を削除すると **`rc=2` で中断する**
> ——消すと既定値に落ちて**検査が黙って緩む**経路だったため（空文字は以前から止めていたのに、
> 行削除だけが通っていた）。**値を変えたいなら値を書き換える**（許される値は出力に出る）。
> `gate-config.env` **自体を持たない旧リポジトリは従来どおり通る**——止めるのは
> 「ファイルはあるのにキーが無い＝編集された」場合だけである。

### 到達度 — 段階を刻むのではなく、要件で判定する

以前はここに **`DENSITY_TIER`（tier 1 / 2 / 3）という 4 つ目の設定値**があり、
「本質層だけの tier 1 → 抜取りの tier 2 → 全数の tier 3」と**段階を刻んで途中で配達する**方式だった（撤去した `GP-104`）。
**この方式は撤去した**（`GP-104` は欠番スタブ）。実測の根拠は リポジトリ外の退避先 の `x2-freeze.md`:

- **tier 1（本質層だけ）には到達した。** 機構としては回る。
- **しかし `purpose=rebuild` の完了条件（`fabricated_open=0`）には、1 能力・24 密度ブロックという
  最小規模でも 4 ラウンドの Verify で到達しなかった**（推移 68 → 28 → 7 → 4）。
- **収束を妨げていたのは段階分けではなかった。** 残存の半分は**是正そのものが生んだ新しい誤り**で、
  原因は「同一事実を 2 ブロックに二重記述する」ことと「是正で主張を足す」ことだった。
  ⇒ **段階を設けても・設けなくても同じ壁に当たる。**段階は判定を 1 軸増やすだけだった。

段階を消しても要求は消えていない。**到達度は設定値の段ではなく、ゲートが読む要件で判定する。**

| 何を守るか | どのゲートが見るか | 決める規約 |
|---|---|---|
| 分母（ノード・入口・テーブル）を使い切ったか | `G-DENOM` ＋ **列挙の 2 経路突合**（`G-ENUM-SOURCE`） | GP-2 / GP-103 |
| 能力仕様の**割当表**（未割当 0） | `G-DENOM`（**`artifact-key: capability-spec` を持つ仕様だけが対象**。持たない仕様は「対象 0 件（未検査）」と報告される） | GP-2 ルール8 |
| 本質層が実体を持つか（`category: rebuild` の仕様が 1 件以上。深さは問わない） | **`G-REBUILD`** | GP-13 |
| 可視性とアクセス範囲の不変条件が書かれているか | **`G-READABLE`**（`readable-sections:` で対象を選ぶ） | GP-3 ルール4b |
| 何のためにあるかが書かれているか（可読性の床） | **`G-READABLE`**（purpose に関係なく FAIL） | GP-14 |
| 密度（実装できる深さ）が宣言に届いているか | `G-DENSITY` ／ `G-LEDGER` | GP-20 / GP-21 |
| 検証官の隔離の記録（台帳の `verifier`）が語彙内か。機械で確かめていない検証の件数を宣言に書いたか | **`G-VERIFIER`** | GP-16 ルール2 / SB-12 |
| 全数主張が母集団の数え方を宣言しているか。**その列挙元が原典か**（内部成果物・外部規格・自表を分母にしない） | **`G-POPULATION`** | SB-102 / GP-2 ルール4 / GP-103 ルール7-(c) |
| 高リスク型を後回しにしていないか | **`G-VERIFY-ORDER`** | GP-103 |
| 反映は独立 Verify を通ったか | `G-LEDGER`（`fabricated_open=0`） | GP-22 / SB-20 / SB-21 |

`purpose=rebuild` の完了条件は **`gates.sh phase4` が exit 0**（`FAIL` と `INCOMPLETE` の合計が 0）である。
`maintenance` / `evaluation` は密度ゲートが **warn** なので**不足は見えるが止まらない**。
この 2 つでは**密度の全数 Verify（別の AI による記述ごとの裏取り）も任意で、既定では行わない**
（費用が約 1 桁増えるため。人が求めたときだけ範囲を決めて行う）。行わなかった場合は、未検証の件数を完成の判定書で開示する。
**ただし「可読性の床」は purpose に関係なく FAIL 判定**
——`責務`（何のためにあるか / 業務動線の位置 / 誰が使う）が空の仕様はどの purpose でも通らない。

<a id="layer-vs-depth"></a>

#### ⚠️ 「層」と「深さ」は別の軸（撤去後も残る区別）

tier を撤去しても、**層（layer）＝何を書いた文書か**と**深さ＝どこまで裏取りしたか**の区別は残る。
この 2 つを混ぜて「本質層 = 浅い、実装層 = 深い」と読むのが最も多い誤解である。

| | **層（layer）** | **深さ** |
|---|---|---|
| 値 | `specs/rebuild/`（技術非依存の本質層）／`specs/modules/` `api/` `data/` `behavior/`（実装事実層） | `verification:` と密度台帳の `verify_status` |
| 決める規約 | GP-13 | GP-20 / GP-22 |
| 記録される場所 | ディレクトリ | 各仕様ファイルの front-matter ＋ `density-ledger.tsv` |

**深さは同じ文書の中で増える。** 本質層を書き足すのではなく、
**引用を `path:line` 直書きから分析物層（Phase 2）へ張り替え、密度ブロックに分け、独立 Verify を通す**
——文書の枚数は変わらないまま裏取りが深くなる。だから「本質層を書き終えた」ことは完了ではない。

**深さはファイル 1 枚ごと・密度ブロック 1 個ごとに刻む**（`density-ledger.tsv` が正本）。
「この能力は Verify 済み、あの能力は未着手」という状態が正常である。

### 書く順序は実装事実層 → 本質層。ただし能力ごとに通し切る（2026-09-23 に反転）

**以前は「本質層を実装層より先に書く」ことを要求していたが、2026-09-23 に反転した**
（`FB-16` / `GP-13` ルール17 / 手順書 Step 3-0）。
効果測定 2 回で、**先に書いた層が最も誤りやすく、しかも膨らむ**ことが観測された
（本質層の誤り率は実装層の **11〜14 倍**・本質層の量は 1.8 倍）。
本質層は**全称主張・不変条件・母集団の集計**が中心で、**実装事実を先に持っていないと裏取りできない**。

**ただし旧ボトムアップ（全ノードの実装層を書いてから凝縮）にも戻していない。**
それだと再構築に直接使える層（総量の 17〜30%）が最後に来る（`FB-13`。この観測は撤回されていない）。
⇒ **1 ドメイン能力を実装層から本質層まで通し切ってから次の能力に進む**（縦串 ＋ カナリア）。
**未着手の能力は実装層も本質層も無いという対称な状態**になり、「片方だけ揃った」非対称が生まれない。

順序を守るためにやること（手順書 Step 3-0 / 3-0b が正本）:

| やること | なぜ |
|---|---|
| **分母の粒度を先に処分する**（展開する or ADR で粒度を宣言する） | `G-DENOM` の PASS は「分母を使い切った」ことしか言わず**「分母が正しい」ことは言わない**。実運用では終盤でこれに気づき、分母を拡張して約 2 日を追加した |
| **本質層の根拠は `[[分析物 ID]]` と `path:line` の両方を書く** | 実装事実層が先にあるので**分析物 ID が既に存在する**。先に書く方式では直書きから始めて後で張り替える移行が必要だったが、**順序を戻すと最初から両方書けるので移行が不要**（`GP-4` の 2 段が保たれる）。**`[[ID]]` だけにすると主張行 0 で `G-BLOCK-SIZE` が止まる** |
| **まず 1 能力だけ通し切る（カナリア）** | 全能力を一斉に進めない。**早期に手に入るのが「浅い全体」ではなく全数 Verify 済みの深い 1 本**になる。実測値を残してから横に広げる |
| **深掘りは選択的にする** | 宣言と実体が食い違えば FAIL（過大申告）／INCOMPLETE（未着手）として残る |

> **⚠️ これが「本質層を先に書く方式」をやめた理由である**（2026-09-23。上の節を参照）。
> **裏取りのない本質層だけの成果物では意思決定できない。**
> 参照解答と突合した隔離試験（Java 98K 行・全 15 能力）の実測:
>
> | 測った軸 | 結果 |
> |---------|------|
> | 時間 | 1 時間 09 分（同じ成果物クラスに実装層経由だと約 7 日） |
> | 網羅 | ノード 172 の未割当 **0**。系統丸ごとの欠落 0 |
> | 深さ | 「欠落すると作り直しになる項目」50 件の再現率は**改善を 3 回重ねても 3 分の 1 を落とした** |
> | 自己申告 | 欠落 8 件のうち未確定リストに現れたのは **3 件**（5 件は無自覚） |
>
> **時間の優位は主張できない**（当初「時間の効果は本物」と書いていたが撤回する）。
> 比較対象の「約 7 日」は**独立 Verify を 709 ブロック通し `fabricated_open` を 0 にした成果物**で、
> こちらは **blocking の 3 分の 1 を取りこぼす**水準である。**同じ品質のものを速く作った実測ではない。**
> **深さが足りないことが本質的な問題である。** とくに落ちやすいのが
> **「不変条件は書けるが、それが守られていないことは書けない」**型である——
> 「状態は 4 値」は書けるが「DB 制約が無く、書き込み経路 6 本のうち検査があるのは 2 本」は
> 全経路を読まないと分からない。この差が再構築の設計判断（DB 制約にするか）を誤らせる。
>
> 対策として能力仕様の雛形は **「可視性とアクセス範囲の不変条件」を必須節**にしている
> （実測で「未公開の対象が公開経路に現れない」という宣言が 1 箇所も無く、
> 割当表でも未確定リストでも検出されなかった。**`G-READABLE` が節の存在と非空を検査する**
> ——この要求は tier に依存しないので、撤去を跨いで残った）。

### Playbook — 「分母をどう数えるか」の差し替え可能な層

```bash
./init.sh --list-playbooks     # 利用可能な一覧
# 現在: java-jaxrs-jpa（JAX-RS + JPA アノテーション型）
#       java-struts-ormxml（Struts 2 + ORM XML 設定型）
#       java-struts1-ejb2（Struts 1 + EJB 2.x。手書きの記述子と XDoclet の両方）
#       vbnet-winforms-adonet（VB.NET + Windows Forms + ADO.NET 直接）
#       csharp-winforms-adonet（C# + Windows Forms + ADO.NET 直接）
#       cobol-cics-batch（COBOL + CICS + JCL バッチ + DB2 / VSAM）
#       aspnet-webforms（ASP.NET Web Forms + C# / VB.NET のコードビハインド）
#       php-procedural-mysql（手続き型 PHP + SQL 文字列 + MySQL 等）
#       oracle-plsql（Oracle の PL/SQL のパッケージ・トリガー・表。アプリ側の Playbook と --playbook を並べて併用する）
#       vb6（Visual Basic 6.0 のフォーム・モジュール + ADO / DAO。VBA から書き出したフォームを含む）
```

**これは今回の改修でいちばん構造的な追加**なので、なぜ必要かを説明する。

網羅性を担保するには「全部で何個あるか」（＝分母）を機械的に数える必要がある。ところが
**その数え方は技術スタックごとに違う。** 汎用手順書に「`@Path` を数えて API の分母にする」と
書いてしまうと、`@Path` を使っていない対象では**分母がゼロになり、突合が計算不能**になる。

これは仮定の話ではなく実測された破綻である。ある Java プロジェクトは `@Path` も `@Table` も
1 件も持っておらず、その現場は独自に代替手段を発明していた——**記録も再利用もされない形で。**

そこで `playbooks/<domain>/` を層として分離した。中身は 5 ファイルで、ファイル名が契約:

| ファイル | 役割 |
|---------|------|
| `enumeration.md` | **必須。列挙の独立ソース＝分母の定義**（走査コマンドと突合の等式） |
| `practices.md` | そのスタック固有の読解ノウハウ（`DP-<domain>-N` 形式） |
| `spec-appendix.md` | 仕様書に付ける技術固有の付録 |
| `gate-snippets.sh` | スタック固有の追加ゲート |
| `README.md` | この Playbook の適用条件 |

**`--playbook` は省略しても動く。** 雛形が配置され、Phase 1 の最初に自分で埋める。
未記入のまま列挙に進むと `G-ENUM-SOURCE` が FAIL する——「分からない」を「やらない」に
落とさないための作りである。

新規 Playbook の作成手順は [authoring-playbook.md](authoring-playbook.md)。

## 5. 実行時に AI を縛る 3 点セット

生成先には GP-N（生成プロセスの規約）と SB-N（品質の不変条件）という知見台帳がコピーされるが、
これらは**参照文書**である。実行時に AI が従うのは次の 3 つだけ。

```
pipeline-procedure.md   ← 手順（何をどの順でやるか）      ★ランタイム契約
AGENTS.md               ← 制約（常に守ること・止まる条件）
gates.sh                ← 判定（できているかの機械確認）
```

**この階層は意図的**である。以前は「GP/SB に良いルールが書いてあるのに、手順書に反映されて
いないので実行時に一切参照されない」状態だった。そこから生まれた規律がこれ:

> **手順書に反映されていない運用ルールは、実行時には存在しないのと同じ。**

`pipeline.md` / `playbook.md` は「**なぜそのルールがあるか**」（実運用フィードバック・根拠・ゲートの設計理由）を
保持し、手順書から `GP-17` `SB-11` のような ID でオンデマンド参照される。セッション冒頭で
全部読む必要はない。

## 6. Phase 0〜4 で実際に起きること

| Phase | 名称 | 主な成果物 | 完了条件 |
|-------|------|-----------|---------|
| **0** | 取り込み・スコープ確定 | `scope.md`・`references.md` | 参考情報の**ユーザー確認**を経る |
| **1** | コードグラフ構築 | `code-graph.md`（分母）・`work-plan.md` | `gates.sh phase1` が exit 0 |
| **2** | 分析 | `02-analysis/` の分析物 | （ゲートなし。work-plan の DoD で管理） |
| **3** | 仕様生成 | `specs/` の仕様書 | `gates.sh phase3` が exit 0 |
| **4** | 監査 | `traceability.md`・`gate-results.md` | `gates.sh phase4` が exit 0 |

### Phase 0 — 何を対象にするか固定する

解析対象のコミットを**断面として固定**する（後から動くと全部の `path:line` が信用できなくなる）。
スコープと除外を明示し、既存の設計書・README・コメント・画像を `references.md` に棚卸しする。

> **既存資料は「出所付き・検証待ちの主張」として扱う。** コードで裏取りするまで事実にしない。
> 資料とコードが矛盾したら**コードを正**とし、ドリフトとして記録する。
> Phase 1 に進む前にユーザー確認のゲートがある。

### Phase 1 — 分母を作る（最重要）

コードグラフは「AI が書く Markdown の構造マップ」で、グラフ DB は使わない。ノード（モジュール・
エントリポイント・外部境界）とエッジ（依存・呼び出し・データフロー）の 2 つのレジストリを作る。

列挙は**独立・機械的・全走査**で行う。狙い撃ちの grep は禁止。`enumeration.md` の走査コマンドを
使い、**突合の等式を両辺の実数値つきで記録に残す**（「数えた」ではなく「31 = 30 + 1（差分の説明）」）。

エッジを探す前に**ノードレジストリを凍結**する。凍結後の変更は HOLD-2 に該当する。
最後に `work-plan.md`（分析作業計画）を作り、Phase 2 以降は毎回これを参照する。

### Phase 2 — カテゴリ別に分析する

ノードを ARCH / REQ / API / DATA / BEHAVIOR / NFR の観点で分析し、各分析物に一意 ID を振る。
大規模なら**縦串（vertical slice）を反復**する。どの仕様も**実装まで精読**する
（インターフェース定義を見て終わりにしない）。

> **反復の終了条件は「コードグラフの全ノードの消化」**である。
> **自律進行の許可は、範囲を縮める許可ではない。** スコープ縮小は ADR かユーザー確認を経る。

### Phase 3 — 仕様書を書く

29148 準拠の章立てで書き、各記述に分析物 ID を `[[...]]` で引用し、**検証（Verification）を対で**
付ける。確定できないものは `🔍 UNKNOWN[blocking/deferred/out-of-scope/undecidable/partial]` でインラインに明示する
（推測を事実として書かない）。仕様 ID `SPEC-<category>-<name>-NN` は永続キーで、振り直し・再利用禁止。

### Phase 4 — 独立に監査する

生成とは分離した段で、網羅性・引用実在・根拠実在・事実/推測分離を突合する。`gates.sh phase4` が
完了ゲート群＋密度ゲート群を回す（**種類数は書かない**——増減するので `gates.sh` の出力が正本。教訓 13）。

**ゲート通過は「形式の健全性」まで**である。内容の正確性は別途、敵対的検証
（別エージェントによる反証・別コンテキストでの再検証）で補う。`/spec-adversarial-audit` skill がある。

## 7. ゲート — 何が機械検査されるか

```bash
bash 03-audit/gates.sh phase1     # Phase 1 完了ゲート
bash 03-audit/gates.sh phase3     # Phase 3 完了ゲート
bash 03-audit/gates.sh phase4     # Phase 4 完了ゲート（＋密度）
bash 03-audit/gates.sh density    # 密度ゲートのみ
bash 03-audit/gates.sh session    # セッション終了チェック
bash 03-audit/gates.sh metrics    # 指標の記録（合否判定なし）
bash 03-audit/gates.sh all        # phase1 + phase3 + phase4
```

**結果は `03-audit/gate-results.md` にスクリプトが自動追記する。** これが検証結果の正本で、
手書きの転記はしない（`metrics` と `session` は判定を持たないので混入させない設計）。

### 主なゲート

| ゲート | 何を見るか |
|-------|-----------|
| `G-DENOM` | コードグラフの全ノードが消化されたか。**状態語彙はホワイトリスト**（「対象外」以外の語でノードを分母から消せない） |
| `G-ENUM-SOURCE` | 列挙の独立ソース表・目印の系統・**分母の 2 経路突合**・実行記録（`enumeration.md`）が埋まっているか。2 経路突合では**定義が別の切り口であること・実数が数値であること・要素差分が書かれていること**を見る（件数の一致は集合の一致を意味しない） |
| `G-ENUM` | 列挙完全性の突合結果が実数値で記録されているか |
| `G-LINK` | `[[...]]` 引用が実在する分析物・仕様に解決するか（宙に浮いた参照ゼロ）。**走査するのは `specs/` ＋ レディ・監査の宣言文書 3 つ**（`03-audit/rebuild-readiness.md` / `traceability.md` / `observed-anomalies.md`）——**「レディ」の根拠にまだ作っていない成果物を書けないようにするため**（2026-09-24 に拡大）。`worklog/` と `investigation-notes/` は**作業中なので対象外**（未解決の前方参照を書いてよい場所） |
| `G-SPECID` | 仕様 ID の一意性 |
| `G-COMMIT` | `source-commit` が Phase 0 で固定した断面と一致するか |
| `G-SOURCE-INTACT` | 解析対象が `init.sh` の記録した状態から変わっていないか（全ファイルの中身の指紋で、変更・追加・削除を見る。比べるのはゲートを走らせた時点だけ。記録した HEAD が断面と違えば WARN。SB-5） |
| `G-FRESH` / `G-DRAFT` | 未決マーカー・`draft` 状態の残存 |
| `G-TEMPLATE` / `G-PROVISIONAL` | 未記入テンプレ・暫定記述を完了宣言に混ぜていないか |
| `G-ARTIFACT` | 成果物の形態が揃っているか（`artifact-key` で厳密突合。ファイル名推定はしない）。**本質層（`specs/rebuild/`）の形態は `REBUILD_LAYER` が `off`/`skeleton` のときは要求しない（不正値は実行前に中断する）。雛形は現状すべて本質層にあるので `off`/`skeleton` では対象 0 件＝常に PASS** |
| `G-REBUILD` | 本質層（`specs/rebuild/`）に仕様が 1 件以上あるか（front-matter に `spec-id`（値あり）＋ `category: rebuild` を持ち本文が空でないもの。雛形複製・機械生成物・索引・統合ビューは数えない）（`REBUILD_LAYER != off` で要求。深さは問わない。**非該当 ADR では消化できない**——作らない判断は `off` に設定し、その行に根拠 ADR の番号を書く: `REBUILD_LAYER=off  # ADR-96`） |
| `G-RECON` | reconciliation を実施したか |
| `G-INDEP` | 高影響宣言に独立検証の記録があるか（**検証範囲＝母集団・割合・標本の選び方まで**） |
| `G-HOLD-ADR` | 分母を縮めた判断に**実在する** ADR が紐づくか |
| `G-QUEUE` | 判断待ち・未検証を残したまま完了宣言していないか。**監査完了などの宣言を人に諮っている間はこれが未完了で、`phase4` は exit 1 になるのが正しい**（判断の後に exit 0 になる。行を外して通さない） |
| `G-NO-DUP-STATE` / `G-SESSION-POINTER` | 進捗状態の複製禁止・ポインタの実在 |
| `G-LEDGER` | 密度台帳が全 verified・`fabricated_open` 合計 0 か。**主張（`path:line` / 表形式）を持つ仕様が 1 ブロックも登録されずに残っていないか**（台帳が空でも・無くても見る。索引・生成物は front-matter の宣言で除外）  |
| `G-BLOCK-SIZE` | 密度ブロックの粒度が上限内か（既定 15 主張 / 8KB） |
| `G-BLOCK-OUTSIDE` | 密度ブロックの外に残った `path:line` 主張を**列挙する**（件数は合否を変えない。ただし**閉じ忘れ・入れ子でマーカーが測れないときは未完了**） |
| `G-VERIFY-ORDER` | 誤りの密度が高い型（全称主張・対外契約）を後回しにしていないか。**並行は許すが追い越しは禁じる**（高リスク型に未検証が残る間、他型の検証済み数がそれを超えない） |
| `G-POPULATION` | 「すべて / 唯一 / 存在しない / 0 件」型の**全数主張**を持つ**未検証**の密度ブロックに**母集団の宣言**（数え方＋件数）があるか。反例 1 件で結論の向きが変わる型なので、母集団が無いと検証を始められない（宣言の有無は完成品に遡って要求しない）。**あわせて「母集団の列挙元」を見る**（2026-09-24 追加）——**内部成果物**（`01-code-graph/` のレジストリ・`02-analysis/` の分析物・`03-audit/` の台帳）・**外部規格**・**自表**（「列挙元 = 下表の N 行」＝循環定義）を分母にしていないか。理由は 1 つ——**独立検証の検証官には原典しか渡らない**ので、それ以外を分母にすると原理的に検証できない。**この検査は `verified` 済みのブロックにも掛かり、該当すれば台帳の格下げを要求する** |

> **ゲートに落ちたら**: 出力に**失敗した行そのもの**が出る。目視で代替したり
> 「実質問題ない」と自己判断で通すことは禁止されている。直すか、直せないなら
> HOLD として人に諮るのが正しい対応。

## 8. あなたの出番 — Tier と HOLD

「AI にどこまで任せるか」を一律で決めると、**過剰停止と過少停止が同時に起きる。**
記録の更新みたいな後戻りコストゼロの作業でも止まる一方、「分母を静かに縮める」ような
不可逆な判断は作業単位の境界に当たらなければ素通りする。

そこで**後戻りコストと人の理解形成価値**で 3 段に分けている。

| Tier | 何が該当するか | 振る舞い |
|------|--------------|---------|
| **Tier 0** | work-plan に記載済みの項目内の作業（列挙・分析・仕様記述・引用付与） | **確認なしで継続** |
| **Tier 1** | 記録更新・知見追記・コミット・push・**縦串スライス間の移行** | **止まらず実行し記録を残す**（人は後から worklog / git log でバッチレビュー） |
| **Tier 2** | 下記 HOLD トリガー | **必ず停止**して判断材料を添えて人に諮る |

### HOLD トリガー（ここで AI はあなたに聞いてくる）

| # | トリガー |
|---|---------|
| HOLD-1 | **分母を縮める判断**（ノードを対象外にする・スコープ縮小・実装不在の確定） |
| HOLD-2 | **レジストリ凍結後の変更**（分母そのものの変更） |
| HOLD-3 | 同一の矛盾の調査で**仮説ログが 3 行到達**、または 2 セッション跨ぎ |
| HOLD-4 | 参考情報と実コードの矛盾が**設計方針レベル**（単発の drift でなく体系的） |
| HOLD-5 | **work-plan にない、まとまった追加作業**の発生 |
| HOLD-6 | **高影響・不可逆な宣言**（監査完了・再構築レディ・reconciliation ゼロ・保持必須契約） |
| HOLD-7 | 29148 章立ての省略/追加、**purpose の変更**、目標密度の変更 |
| HOLD-8 | **Phase 境界の通過**（0→1→2→3→4） |
| HOLD-9 | **密度 Verify が 3 ラウンドで収束しない**、または前ラウンドより悪化した |

停止時は**軽量停止プロトコル**で、ADR ドラフトを 4 節（背景 / 選択肢 / 決定案 / 影響）で提示する。
あなたは一言で承認できる。判断待ちの間、AI は依存しない別作業に進んでよく、保留は
`session-context.md` の Decision Queue で追跡される。

**HOLD が 1 スライスで 3 回以上出るなら、トリガーの基準が広すぎるサイン**なので調整を提案してくる。

> **正直に書いておくべき限界**: 「トリガーが発火したのに停止しなかった」を直接検出する
> ゲートは存在しない（`gates.sh` は成果物しか見えず、停止したかは実行履歴にしか現れない）。
> 機械化されているのは「**停止すべき判断が記録なしに成果物に入っていないか**」の側だけである。
> 特に HOLD-3 の仮説ログは git 管理外の scratchpad なのでゲートから読めず、**散文ルールのまま**。
> 詳細は `docs/knowledge/pipeline.md` の GP-106。

## 9. セッションが切れても続けられる仕組み

AI のセッションは予告なく切れる。「終わったら記録する」という散文ルールは、**切れた瞬間に発火しない。**
そこで「着手時に受け皿を開く」設計になっている。

### 開始時（AI が自動で行う 6 項目）

1. `session-context.md` を読み、**キューを先に処理する** — Decision Queue の判断待ちを**最初に報告**
   → Verification Queue の未検証を**検証してから**新規作業 → Active Investigation の調査を継続
2. `pipeline-procedure.md` で現在の Phase の手順を確認
3. **Phase 2 以降は `work-plan.md` を開く**（記憶で進めない）
4. `gates.sh` で現状を確認
5. **中断された作業を継続する**（`分析中` ノード・scratchpad・未完サブタスク）
6. 作業ツリーが dirty なら、各変更を `provisional`（後で戻す）/ `candidate-fix`（検証して残す）に分類

### 終了時（Tier 1 = 指示を待たず実行。キリのよいところで随時）

worklog 追記 → `session-context.md` 更新（Last Checkpoint / Current Position / Next Actions / 3 キュー）
→ scratchpad 処理 → コミット → push → **`gates.sh session` で機械確認** → `git log` と `git status` を報告。

`gates.sh session` の 6 ゲートは、たとえば次を検出する:

- `session-context.md` が**存在しない**（← 削除するのが最も簡単な「全通過」方法だったので最初に検査する）
- 未コミット変更があるのに**作業ツリー台帳が空**、または台帳が dirty な変更を網羅していない
- scratchpad があるのに Active Investigation が空（中断の痕跡が消える）
- **Next Actions が「つづき」のような復元不能な記述**（`path:line` / ファイル名 / WP-ID を要求する）
- Last Checkpoint の日付がプレースホルダーや `TBD`

### 進捗はどこを見るか

**状態の種類ごとに正本が 1 つ**決まっており、他のファイルは参照するだけで**同じ表を複製しない**。

| 知りたいこと | 見る場所 |
|------------|---------|
| ノード単位の仕様化状態 | `01-code-graph/code-graph.md` |
| 縦串（WP）単位の状態 | `01-code-graph/work-plan.md` |
| 縦串 × レイヤの進捗（大規模時） | `01-code-graph/roadmap.md` |
| 未解決の UNKNOWN | `03-audit/traceability.md` |
| 未検証の密度ブロック | `03-audit/density-ledger.tsv` |
| **いま何をしているか（ポインタのみ）** | `worklog/session-context.md` |

`session-context.md` に進捗のノード一覧は書かれない（`G-NO-DUP-STATE` が複製を FAIL にする）。
**進捗を知りたいときは正本を読む。**

> **なぜ**: 同じ情報が 2 箇所にあると必ず乖離し、**古い方を根拠に完了宣言できてしまう。**

## 10. 「網羅」と「密度」の 2 軸

完成度は 1 次元ではない。

- **網羅（coverage）**: コードグラフの全ノードが仕様のどこかでカバーされているか
- **密度（density）**: その仕様を読んで**実装できるだけの情報があるか**

**`path:line` があること ≠ 実装できること。** 「このモジュールは注文を検証する」に行番号が
付いていても、検証ルールの一覧・境界値・エラーコードがなければ再構築はできない。
そこで purpose が `rebuild` 系のときは**密度昇格**というステップが入る。

### 密度昇格に Verify が必須な理由

生成と同一コンテキストの自己申告では、**「`path:line` 付きで一見正しい」誤りが約 35% 残る**
（実測。存在しない行番号・例外クラスの誤帰属・過大な must・HTTP コードの誤り・
デッドコードを live として掲載・キー名や enum の誤り）。

そこで **Extract → Verify → Repair → Gate** を回す。Verify は**コンテキストを隔離した**
別エージェントが原典と突合し、`fabricated`（捏造）が 0 になるまで Repair する。
`/density-verify` skill がこれを自動編成し、`density-ledger.tsv` に結果を記録する。

### ブロックは小さく割る（ここが最新の改修点）

`fabricated=0` は**全数合格**の条件である。1 主張の正答率が 95% でも、100 主張の全数合格確率は
**0.6%** しかない。**厳格さと単位の大きさは両立しない。**

実際にこれで運用が止まった。あるプロジェクトは 1 ブロックが 164 主張・52KB になり、
7 ラウンド回しても収束せず、残りの見積りが 120〜240 時間になって、現場は
「2 ラウンドで打ち切る」という独自ルール——つまり**品質ゲートの実質無効化**に倒れた。

対策は**上限を緩めることではなく、単位を割ること**だった（GP-103 / SB-102 / 失敗は FB-7）:

- **粒度上限**: 15 主張 / 8KB（束ねてよいのは同じ節の中。3 行以下のブロックは束ねることを推奨）。超えたら**分割**する（分割は分母の縮小ではないので ADR 不要）
- **再 Verify は修正した主張に限定**（全体再検証は verified 昇格の直前に 1 回だけ）
- **欠落（missing）の列挙は初回のみ**。新規に見つかった欠落は別途起票し、合否から切り離す
  （これをやらないと、直すたびに指摘が増えて永久に収束しない）
- 3 ラウンドで収束しない、または悪化したら **HOLD-9 で停止**

`G-BLOCK-SIZE` がこの上限を機械強制する。ブロックが小さいので**並列化が効き、実時間はむしろ縮む。**

## 11. 困ったときの読み替え表

| 症状 | 意味 | 対応 |
|------|------|------|
| `G-ENUM-SOURCE` が FAIL する | `enumeration.md` が未記入。分母の数え方が決まっていない、または**分母を 2 経路で突合していない** | Playbook を指定するか、走査コマンドを自分で埋める。**空欄のまま進まない**。2 経路の作り方が分からないときは同ファイルの探索手順に従う |
| `G-DENOM` が FAIL する | 分母のノードが消化されていない、または**状態語彙が不正** | 「スコープ外」等の独自語を書いていないか確認（許容語は 未着手/分析中/仕様化済/対象外） |
| `G-HOLD-ADR` が FAIL する | ノードを対象外にしたのに ADR がない、または ADR 番号が実在しない | 判断の根拠を ADR に起票する。事後の記録も正当な手順 |
| `G-LINK` が FAIL する | 仕様が存在しない分析物を引用している。**または「レディ」の根拠にまだ作っていない成果物を書いた**（`rebuild-readiness.md` / `traceability.md` / `observed-anomalies.md` も走査対象） | 引用先を作るか、引用を直す。作らないなら**非該当 ADR を書く**か**その行を消す** |
| `G-SYMMETRY` が INCOMPLETE になる | **`specs/<カテゴリ>/` が空**（実仕様 0 件）で、作らないと決めた ADR も無い。**0 件のカテゴリは分布に現れないので「対称」と誤判定される**ため、完了ゲートで別に検出する（2026-09-24 追加） | そのカテゴリの仕様を作る。作らないなら **`decisions.md` にカテゴリ名と「作らない」を同じ行で**書く。空のままでは**密度ゲートの分母にも入らない**ので中身が 1 件も検査されない |
| `gates.sh` が `rc=2` で止まり「キーが無い」と言う | `gate-config.env` の `PURPOSE` / `DENSITY_GATES` / `REBUILD_LAYER` の**行を消した**（2026-09-24 から中断する）。既定値に落ちて検査が緩むため | 消した行を戻す。値を変えたいなら**値を書き換える**（許される値は出力に出る）。**ファイル自体が無い旧リポジトリは従来どおり通る** |
| 密度 Verify が収束しない | ほぼ確実に**ブロックが大きすぎる** | 上限を緩めず**分割する**。3 ラウンド超なら HOLD-9 で停止して相談 |
| `gates.sh session` が FAIL する | 引き継ぎ情報が不完全。次セッションが復元できない | Next Actions を `path:line` まで具体化し、dirty な変更を台帳に分類 |
| AI が「実質問題ないので進みます」と言う | **設計上の禁止事項** | ゲートの目視代替・自己申告による通過は禁止。直すか HOLD |
| 「レディです」「監査完了です」と言われた | HOLD-6。独立検証が必要 | 検証範囲（**母集団・割合・標本の選び方・層別結果**）を確認する。「検証しました」だけでは不十分 |

## 12. この仕組みが意図的にやらないこと

| やらないこと | 理由 |
|------------|------|
| **グラフ DB / ベクター DB / エンベディング** | 持たない・要求しない。「コードグラフ」は物理 DB ではなく AI が書く Markdown の構造マップで、コード探索はホストの AI ツールに委譲する。**依存ゼロ・ツール非依存が核心価値** |
| 解析対象の変更・整形・コミット | 読むだけ。コピーもしない |
| 再構築先スタックの前提 | rebuild 層は技術非依存の本質仕様として書く |
| 無人での自動生成 | 人が理解を形成する過程が目的の一部。HOLD はそのための場でもある |
| 消費側の検索・chat ポータル | 別の話として扱う（基盤が必要になる領域） |
