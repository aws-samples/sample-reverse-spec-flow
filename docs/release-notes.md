#### 中規模の Web アプリケーションを最後まで仕様化しました（v2.0.0・Claude Code・`rebuild`）

**中規模の Web アプリケーション（構成要素 約 280・業務のまとまり 17）を 1 つ、最初から最後まで仕様化し、
完了の点検をすべて通しました。** あわせて、**点検を通すために記述の分類を付け替える・確かめきれない記述を
黙って消すといった抜け道を通っていないか**を、作業者と別の検証者が抜き取りで確かめ、問題は 0 件でした。

- **所要時間**: 開始から完了の点検を通すまで**約 38 時間**（AI の作業時間に、人の確認待ちを含む）。
- **人の判断が要った場面**: 作業の区切り（工程の境目）・対象の数え方の確定・既存データとの互換の方針・完了後に追加の検証をするかの 4 種類だけでした。
- **成果物に残る誤り**: 完了の点検を通した後でも、記述を無作為に 200 件抜き出して原典と照合すると
  **約 5% に一部の誤り**（一覧の不足・条件の欠落・言い過ぎ・引用位置のずれ）がありました。
  **再構築に直接使う中核部分は約 1 割**と高めです。**完全に誤った記述は 0 件**でした。
  この数字は、記述ごとの裏取りを全数行う `rebuild` での結果です。
  仕様書をもとに再構築したアプリケーションは、UAT やリグレッションテストなどで、現行システムと同じように動くことを別途確認してください。
- **確かめきれなかった点は「未確定」として残ります**（下の「v2.0.0 の変更」の (4)）。起動・画面操作・DB の実行などの動的な確認はしていません。

### v2.2.0 の変更（v2.1.1 から）

#### (1) 「保守のための理解」「再構築の評価」では、記述ごとの裏取りを既定では行いません

仕様書の記述 1 つずつを別の AI に原典と突き合わせさせる作業（全数の裏取り）は、費用を**約 1 桁**押し上げます。
これまでの手順書は、この作業を必須と読める書き方と任意と読める書き方が混ざっており、AI の判断が回ごとに割れていました。

- **`maintenance`（保守のための理解）と `evaluation`（再構築の評価）では、既定では行いません。**
  必要なときは人が範囲を決めて指示します（その範囲は判断記録に残ります）。
- **行わなかった場合は、完成の判定書に「行っていない」ことと、確かめていない記述の量を書きます。**
- `rebuild`（再構築の実装まで）では、これまでどおり必須です。
- 監査での抽出検証（無作為に選んだ記述の裏取り）は、どの目的でもこれまでどおり行います。

#### (2) Claude Code で、検証役の切り離しの確かめ方を変え、費用を下げました

v2.1.0 では、検証役が書き手から切り離されていることを**起動のたびに**確かめる手続きがありました。
この手続きのために取りまとめ役の AI が生まれて費用が膨らみ、確かめの数が合わずに検証をまとめてやり直すこともありました。

- **検証が終わった後に 1 回、記録から確かめる**形に変えました（確かめる道具を用意しています）。
  確かめられなかった検証役の結果だけを捨て、ほかの結果はそのまま使います。
- 開発時の測定では、記述のまとまり 1 つあたりの費用が**約 3 分の 1** になりました（所要時間はほぼ同じです）。
- **新しいフォルダで使い始めるときは、Claude Code の「このフォルダを信頼するか」の確認を一度承認してください。**
  承認しないと切り離しの仕組みが動かず、確かめの道具がそれを知らせます。

#### (3) Windows での不具合を直しました

- **Kiro IDE**: 検証役の切り離しの確かめが、Windows では必ず止まっていました。Windows の形のパスを読めるように直しました。
  あわせて、Windows で使うときの注意（シェル・文字コード・パスの書き方）を導入手順に書きました。
- **Claude Code を Windows で使う場合の切り離しの確かめ**は、まだ Windows で確かめていません（注意書きを入れてあります）。
- 自動で作る逆引きの索引のせいで、目次の点検が落ちていた問題を直しました。

### v2.1.0 の変更（v2.0.0 から）

#### (1) Kiro IDE でも使えるようになりました

これまで最後まで通して確かめたのは Claude Code だけでした。**Kiro IDE でも、1 つの対象を最初から最後まで
仕様化し、完了の点検をすべて通しました**（確かめた対象は小規模の Web アプリケーションで、Claude Code で
確かめた対象のおよそ 4 分の 1 の規模です）。初期化のときに使う AI ツールを指定します（指定しなければ Claude Code）。

| AI ツール | 状態 |
|---|---|
| Claude Code | 検証済み（最後まで通して確認） |
| Kiro IDE | 検証済み（最後まで通して確認。小規模の対象） |
| Kiro CLI | **未検証**（ファイルを置くところまで。検証役の切り離しだけ確かめました） |
| それ以外 | 未対応 |

**Kiro IDE の注意**: 何もしないと、長い作業の途中で**操作の承認を求めるダイアログが何度も出て止まります**。
承認をまとめて入れるスクリプトを用意しましたが、**止まる回数がどこまで減るかはまだ確かめていません**。
また、承認を広く与えるほど、AI が意図しない操作をしても確認なしに通ります（リスクは手順書に書いています）。

**作業中のプロジェクトを Kiro IDE に移すこともできます**（AI ツールに合わせたファイルだけを置き直す道具を用意しました。
仕様書と作業記録には触りません）。

#### (2) 仕様書を確かめる「検証役」を、書き手から機械的に切り離しました

仕様書の記述は、書いた AI とは別の AI（検証役）が原典と突き合わせて確かめます。これまでは
「書き手の考えを渡さない」という指示で切り離していましたが、**検証役が読めるのを解析対象のソースだけに
機械的に制限**するようにしました（Claude Code と Kiro IDE）。

あわせて、**記述ごとに「どの方法で確かめたか」を記録し、点検で見る**ようにしました。
機械的に切り離せなかった方法で確かめた件数は、完成の判定書で読み手に開示します。

#### (3) 解析対象のソースが変わったら気づくようになりました

解析対象のソースは読むだけで、書き換えてはいけません。初期化のときに**ソースの全ファイルの中身の指紋**を
記録し、**作業の区切りの点検のたびに比べて、変わっていれば止まります**（変わったファイルの名前を示します）。

- これは**止める仕組みではなく、気づく仕組み**です。点検と点検の間に書き換えて元に戻した場合は気づけません。
- **解析対象を動かして観察する場合は、別の複製で動かしてください**（ビルドや起動でできるファイルも「変化」として止まります）。
- ソースが git で管理されていない場合は戻す手段が無いので、**作業の前に複製を取ってください**。

#### (4) レガシー技術向けの Playbook を 9 種類追加し、組み合わせて使えるようにしました

Playbook は、技術ごとの「数え方」（画面・入口・テーブルをどこからどう数えるか）をまとめたものです。
これまでの Java 2 種類に、次を加えました。

| 技術 | Playbook |
|---|---|
| VB.NET / C# の WinForms 業務アプリ（ADO.NET） | 2 種類 |
| ASP.NET Web Forms（C# / VB.NET） | 1 種類 |
| COBOL（CICS ＋ JCL バッチ ＋ DB2 / VSAM） | 1 種類 |
| 手続き型 PHP（HTML 混在 ＋ SQL 文字列） | 1 種類 |
| Struts 1 ＋ EJB 2.x | 1 種類 |
| Oracle PL/SQL | 1 種類 |
| Visual Basic 6.0 | 1 種類 |

- 画面は VB.NET、データ処理は PL/SQL のように**技術が混ざったシステムでは、Playbook を組み合わせて**使えます。
- 新しい Playbook は**公開されているソースで数え方を実測して**作りましたが、**最初から最後まで通した確認はまだしていません**。
  数え方が合わない場合は、作業の最初の段階で止まって知らせる作りになっています。

### v2.0.0 の変更（v1.22 から）

利用者から見える変化は次のとおりです。(1)〜(3) は**「気づかないうちに不完全な仕様書ができる」
経路を塞ぐもの**で、作業が止まる場面が増えます。(4)〜(8) は**作業を最後まで終えられるようにするもの**です。

#### (1) 仕様書の種類に空のものがあると、完了の点検で止まります

仕様書は用途別に数種類（構成／外部接続／データ／振る舞い／再構築用）を作ります。
**このうち 1 種類でも中身が 0 件だと、完了の点検で止まるようになりました。**

以前は**全種類が揃って 0 件だと「偏りなし」と判定されて通っていました**
（1 種類だけ少ない場合は検出できていたのに、全部空だと通るという穴でした）。
実際にこの穴を踏んだ例では、空の種類を作った後に点検対象が 14 件から 102 件に増え、
**そこで初めて 28 件の記載不足が見つかりました**。

**作らないと決めた種類がある場合は、判断の記録（decisions.md）に「この種類は作らない」と
書いてください。**書けば止まりません。

#### (2) 設定の行を消して点検を緩めることはできなくなりました

点検の強さは設定ファイルで決まります。**その設定の行を削除すると、作業が中断します**
（以前は行を消すと既定値に落ち、**点検が黙って緩くなっていました**）。

強さを変えたい場合は**行を消すのではなく値を書き換えてください**（使える値は画面に表示されます）。
なお**設定ファイル自体を持たない古い成果物は従来どおり動きます**——止まるのは
「ファイルはあるのに行が消されている」場合だけです。

#### (3) 「完成しました」の根拠に、まだ作っていない仕様書を挙げられなくなりました

完成の判定を書く文書で「この件は〇〇の仕様書に書いた」と参照するとき、
**その仕様書が実在するかを点検するようになりました。**

以前はこの文書が点検の対象外で、**まだ作っていない仕様書を根拠に「完成」と書けていました**。
実際に、独立した検証を 7 巡・のべ 459 項目行っても誰も気づかなかった例があります。

#### (4) 読み切れなかった箇所は「確認した範囲」を添えて未確定のまま完了できます

ライブラリの既定動作や実行環境に依存して、ソースコードだけでは決められない点があります。
**そうした点は「どこまで確認したか（原典の位置）」を添えて「未確定」と書けば、完了の点検を通ります。**
以前は、確かめきれない点を別の分類に付け替えて点検を通す使い方が起きていました。
**読み手は「未確定」の一覧を見れば、利用時に確かめるべき点が分かります。**

#### (5) 仕様書のファイルを「読む人の単位」で分けます

構成の仕様書は**ソースコードの部品（コンポーネント）単位**、外部接続と振る舞いの仕様書は**機能単位**で 1 ファイルにします。
以前は入口ごとに細かくファイルが分かれ、同じ対象でも作るたびにファイル数が大きく変わっていました。
**ソースのファイルから該当する仕様書を引く一覧は自動で作られます。**

#### (6) 確認が収束しない記述は、自動で切り分けて先へ進みます

独立した検証で同じ箇所の指摘が何度も続くと、以前は**そのたびに作業が止まり、人の判断を待っていました**
（実測で 77 回。答えはすべて同じ推奨どおりでした）。
**v2.0.0 から、初回は自動でその記述を小さく切り分けて確かめ直し、判断の記録に残します。**
人に確認するのは「確かめきれないので記述を外す」ときと、同じ記述で 2 回目のときだけです。
**外す前には、根拠を足せば残せないかを 1 回試します**（以前は、正しい記述を根拠不足のまま外していました）。

あわせて、検証の単位を**同じ節の中で束ねられる**ようにしました。小さすぎる単位が多く、管理の手間が増えていたためです。

#### (7) AI ツールが並列実行できる場合は、並列が既定になります

対象の洗い出し・分析・執筆・検証・監査は、AI ツールが並列実行の機能を持っていれば**並列で進めるのが既定**です。
並列で起きやすい事故（同じファイルへの同時書き込み・番号の重複など）への対策は手順書に組み込みました。
並列にしなかった区間は、理由を作業計画に書きます。

#### (8) 件数を述べる記述は「数え方」が再現できることまで確かめます

検証は「引用の裏取り」と「件数の再現」の 2 種類に分けました。**「〇件ある」と書いた記述は、書かれた数え方で
同じ件数が出るか**を別の検証者が確かめます。数え方の書かれていない件数は差し戻しになります。

### ⚠️ 重要: v1.17〜v1.22 は非推奨です（新規の仕様抽出に使わないでください）

**v1.17 から v1.22 までの版は、仕様書を最後まで作り切れない設計上の問題を抱えています。**
これらの版で新しく仕様抽出を始めないでください。

#### 何が問題だったか

これらの版は **「技術に依存しない本質的な仕様」を先に書き、その後で実装の詳細を書く**順番を
要求していました。**この順番が誤りでした。**

本質的な仕様には「〜はすべて〇〇である」「〜は 1 箇所だけにある」といった**全体を見渡した断定**が
多く含まれます。ところが**実装の詳細を先に調べていないと、その断定の裏づけが取れません**。
結果として「裏づけのない記述を先に書き、後から直す」作業になり、**直すたびに文章が壊れ**、
本質的な仕様の誤りが実装側の 8〜11 倍に達しました（同一の対象で 2 回測定）。

#### 何をしたか

**順番を元に戻しました**——**実装の詳細を先に調べ、その上で本質的な仕様を書く**。
ただし「全部の実装を調べ終えてから本質に入る」のでもなく、**業務のまとまり 1 つを
実装から本質まで通して仕上げてから、次のまとまりに進む**形にしています。

あわせて **v1.17 で入れた「3 段階に分けて受け取る仕組み」は取り下げました**
（浅い段階で受け取っても再構築の判断には足りず、深い段階へ上げ直す作業が本質的な仕様の
書き直しになるためです。詳細は下の「v1.17〜v1.22 の変更」の 1）。

#### どの版を使えばよいか

**v2.2.1 をお使いください**（v2.0.0 以降の版も引き続き使えます。違いは各版の変更を参照してください）。

- **v1.16 以前**: 上記の順番の問題はありませんが、点検の仕組みが古く、
  現在の基準では不足が検出されません。
- **v1.17〜v1.22**: **非推奨**（上記の理由）。
- **v2.0.0**: 順番を直した版です。**1 つの対象を最後まで仕様化し、完了の点検をすべて通したことを確認しました**（冒頭の「検証で確かめたこと」）。
- **v2.1.0**: v2.0.0 の手順はそのままに、使える AI ツールと技術を広げた版です（「v2.1.0 の変更」）。
- **v2.2.0 / v2.2.1**: 検証にかかる費用を下げた版と、その不具合の修正版です（「v2.2.0 の変更」「v2.2.1 の変更」）。

> v1.22 までは、どの版でも「完了の点検をすべて通した」実績がありませんでした。
> v2.0.0 は、その確認を取ってから出した最初の版です。

### v1.17〜v1.22 の変更

v1.16 から v1.22 までの変更です。番号は、ほかの節から参照するために付けています。

#### 1. 成果物の作る順番を変えました（v1.17。段階配達は **v2.0.0** で取り下げました）

**v1.16 までは「全部できあがるまで何も出てこない」構造**でした。実測では、仕様書全体のうち
再構築に直接使える部分は総量の 2〜3 割で、しかも**最後に作られていました**。
規模の大きいシステムでは、その部分に到達する前に工数が尽きます
（実測で 1 ヶ月を超える見積りになったプロジェクトがあります）。

**v1.17 から、順番を逆にしました。** システム全体を機能単位で整理した仕様書
（1 単位あたり 230 行前後・数時間）を**先に**作り、そのあとで裏取りを深くしていきます。
**この順番の変更は現在も有効です**——これが v1.17 の実質的な価値でした。

##### ⚠️ v1.17 で入れた「3 段階で受け取る仕組み」は取り下げました（**v2.0.0**）

当初は到達度を **第 1 段階 / 第 2 段階 / 第 3 段階**という設定値で刻み、
「段階ごとに区切って受け取れる」仕組みを用意していました。**これを取り下げました。**

**理由は実測です。** 1 つの機能単位（検証の区画 24 個）という**最小規模**で最後まで進める試験を行い、
**4 巡の検証を回しても「再構築」の完了条件に届きませんでした**（未検証の記述が 68 → 28 → 7 → 4 と
減りはしたが 0 にならない）。**しかも残った 4 件のうち半分は、直した作業そのものが生んだ新しい誤り**でした。

**原因は段階分けではありませんでした。** 効いていなかったのは
「**全記述を独立検証まで通す**」という完了条件の形（直すたびに新しい確認対象が生まれる）と、
**同じ事実を 2 箇所に書いていたこと**でした。段階を設けても設けなくても同じところで止まります。
段階という設定値は**判定を 1 つ増やすだけ**だったので、取り下げて要求そのものに一本化しました。

**利用者から見える変化:**

| 変わったこと | 内容 |
|---|---|
| 設定 | 到達度の段階を指定する設定項目が無くなりました（環境変数 1 つが不要になります。初期化時の質問は変わりません） |
| 仕様書 | 各仕様書の冒頭にあった「第 N 段階」の刻印が無くなりました |
| 点検 | 「段階に達していない」という点検項目が無くなりました。段階の仕組みの中にあった点検 3 件のうち、**2 件（引用先の実在確認・1 単位目の実測記録）は段階に依存しない点検へ移し**、1 件（「まだ検証していない」の表示）は**記録場所を作業台帳に一本化**しました |
| 完了条件 | 下記のとおり、段ではなく**満たすべき要件**で判定します |

**既存の成果物はそのまま通ります**（古い書式の刻印が残っていても点検は受け付けます）。

**新しく作る機能単位の仕様書には 1 つ変化があります。** 雛形の「状態」欄の初期値を
**「下書き」**に変えたので、書き終えたら**「下書き」から進める**必要があります
（従来は段階の名前が入っており、書き終えても下書きのままだと気づけませんでした）。
既存の仕様書には影響しません。

**すでに作業中のプロジェクトで 1 箇所だけ書き換えが必要です。**
作業記録の「再構築レディ」チェックリストに「**到達段が目的の完了条件を満たしている**」という
古い項目があれば、現在の雛形の文言「**検証の到達度が目的の完了条件を満たしている**」に
書き換えてください（段階が無くなったので、元の項目は原理的に満たせません）。
設定ファイルに残る段階の設定値・各仕様書に残る「第 N 段階」の刻印は、
**読むプログラムが無くなったのでそのままでも点検は通ります**（消しても構いません）。

**あわせて、段階の仕組みの中にあった点検 2 件を段階に依存しない形へ移しました。**
すでに 2 つ以上の機能単位に着手済みのプロジェクトでは、この 2 件が新しく指摘を出す場合があります。

| 移した点検 | 何を見るか | すでに着手済みのプロジェクトへの影響（実測） |
|---|---|---|
| 引用先の実在確認 | 仕様書が引用する分析メモの ID が実在するか | **影響なし**（実際の 2 つのプロジェクトで未解決 0 件） |
| 1 単位目の実測記録 | 作業計画の「カナリア実測」表が埋まっているか | **2 つ目の機能単位に着手済み**のプロジェクトで、表が空欄または無ければ「まだ終わっていない」と出ます——**埋めてください**（1 単位目の所要時間・件数の実測値）。1 つ目の作業中は鳴りません |

**あわせて、作業計画の点検を完了時にも行うようにしました**（従来は序盤にしか見ていませんでした）。
古い形式の作業計画（残作業の「量」を書く欄が無いもの）を使っているプロジェクトでは、
完了前の点検に「作業計画が旧形式」という指摘が 1 件増えます。

**指摘の総数がどうなるかはプロジェクトによって違います**（実測したプロジェクトでは同数でした）:

| プロジェクトの状態 | 完了前の点検の指摘数 |
|---|---|
| 作業計画が旧形式 ＋ 段階の点検が鳴っていた | **変わりません**（1 件と 1 件が入れ替わる。実測したプロジェクトはこれ） |
| 作業計画が旧形式 ＋ 段階の点検は鳴っていなかった | 1 件増えます |
| 作業計画が現行形式 ＋ 段階の点検が鳴っていた | 1 件減ります（実測した別のプロジェクトはこれ） |
| 作業計画が現行形式 ＋ 段階の点検は鳴っていなかった | 変わりません |

**上記に加えて**、2 つ目の機能単位に着手済みで「カナリア実測」表が空欄なら、さらに 1 件増えます。

##### どこまで進めれば「完了」かは、最初に選ぶ目的で決まります

作業開始時に目的を 3 つから選びます。**選んだ目的によって完了条件が変わります。**

| 目的 | 完了条件 |
|---|---|
| **保守のための理解** | 機能の数え上げを使い切っていて、「何のためにあるか」が書かれている |
| **評価・見積り** | 上記 ＋ 機能単位の仕様書が実体を持っている |
| **再構築（作り直しを実施する）** | 上記 ＋ **全記述が独立検証を通っている** |

**どの目的でも「何のためにあるか」が空の仕様書は通りません**（下記 2 の点検）。
浅くてよい場合でも、**読んで意味が分かる水準は保証されます。**

**「再構築」を選んだ場合、独立検証を通すまで完了になりません。**
点検プログラムが「まだ終わっていない」と出し続けます（**中途半端な状態で「完了」と宣言できない**設計です）。

**ただし対象範囲は絞れます。** 「この機能群はここで止める」という判断は可能で、
その場合は**理由を記録として残します**（記録のない未完了は「未達」として残ります）。
「独立検証が任意」ではなく、**「独立検証まで進める範囲を決められる」**という意味です。

なお目的は**最終ゴール**なので、作業の途中で下げません（下げると「粗いまま完了」になります）。
変更が必要な場合は、AI エージェントが作業を止めて人に確認します。

> **上の実測から、工数の見積りについて 1 つ申し添えます。** 「再構築」の完了条件
> （全記述の独立検証）は、**最小規模でも 4 巡で終わりませんでした**。
> 範囲を絞る判断（どの機能群を独立検証まで通すか）は、**着手前に決めておくことをおすすめします**。

##### 機能単位の仕様書に必ず書かせるもの（浅さを補う 2 つの必須項目）

**(a) 機能の数え上げと割り当て（v1.17）**

「機能単位を数え上げて、**どこにも割り当てられていないものが 0 件**」であることを機械が点検します。
これにより**まるごと見落とした機能群がある状態を検出できます**
（この点検がない場合、実測で 1 件の見落としが発生しました）。

**(b) 「誰に何が見えるか／見えてはならないか」（v1.18）**

**未公開・下書き・予約公開のものが公開経路に現れない**、**無効化された利用者のアクセスはどうなるか**、
**認証なしで到達できる経路は何か**——こうした要件を必ず書く節を設けました。

**実測で、この種の要件が 1 箇所も書かれていませんでした。** 派生的な記述（「集計は公開分のみ」等）は
あったのに、**要件としての宣言が無かった**のです。**落とすと情報漏洩を作り込む**種類の項目なので、
必須節にして書かれていなければ点検で止めます。

##### ⚠️ 深掘り前の成果物についての注意（重要）

**独立検証を通す前の仕様書だけで再構築の判断をしないでください。**

同じシステムに対して 3 回測定した実績では、**「欠けたまま実装すると作り直しになる項目」を
3 分の 1 取りこぼします**（再現率 54% → 62% → 66% と改善中ですが、100% には届きません）。
しかも**取りこぼしたことを AI 自身は自覚できません**（「未確定」の一覧にも載りません）。

そのため、この段階の仕様書は **「全体像の把握」と「深掘りの作業計画」**として使い、
**重要な判断は深掘りを終えてから**行う運用を推奨します。この注意書きは成果物にも自動で入ります。

#### 2. 仕様書が「読んで分かる」ことを点検するようになりました（v1.18）

**機能単位の仕様書に「この機能は何のためにあるか」を必ず書かせる**ようにしました。

従来は、コードの行番号付きの詳細は充実しているのに、**「何のための機能で、業務のどこに位置し、
誰が使うのか」が 1 行も書かれていない**状態が起こり得ました。実測では、4 件のうち
**2 件がほぼ全機能単位でこの説明を欠いていました**（片方は 29 件中 28 件）。
**詳細は機械で点検できますが、「読んで分かるか」は点検されていなかった**ためです。

v1.18 から、各機能単位の仕様に次を要求し、**書かれていなければ点検で止まります**
（**v1.20 でこの点検を目的から独立させました**——以前は「保守のための理解」を選んだ場合だけ
この点検が無効になっており、**人が読むことが目的の場合にこそ切れていた**という誤りがありました）:

- **何のためにあるか**（その機能が成立させている業務上の結果）
- **業務動線のどこに位置するか**（前後の画面・処理）
- **誰が使うか**
- あわせて **処理の流れ**と**依存関係**も必須にしました（同じく節ごと消えていました）

#### 3. 作業量の見通しが立つようになりました（v1.19 / v1.20）

深掘りの作業を実際に 2 回計測し、**予測と実績を突き合わせる欄**を作業計画に追加しました。
あわせて **各段階の「何を満たせば完了か」**を作業計画に明文化しました（従来は口頭の判断でした）。

- 実測では**予測が 0.9 倍の精度で当たり**（2 回連続）、作業計画として使える水準でした
- **1 機能単位の深掘りに約 25 分**（対象システムの規模による）
- 「1 単位目で共通部分が片付くから 2 単位目は速くなる」と予想しましたが、**実測では速くなりませんでした**
  （25 分 → 26 分）。**単純に単位数を掛けて見積もってよい**、という結論です

これにより「残り作業はあとどれくらいか」を数字で示せます。

#### 4. 進捗の見え方を改善しました（v1.20）

**v1.19 まで**は点検結果が「残り 1 件」と表示され、それを直すと次が現れ、また次が現れる状態でした。
**残りが何件あるか分からない**ため、完了時期が見通せませんでした。

**v1.20 から、残作業をまとめて全部表示します**（「残り 2 種類: 未処理 15 件 / 独立検証が未完了」のように）。
点検の合否判定そのものは変わっていません（既存プロジェクトで全項目の判定が一致することを確認済み）。

#### 5. 記録できるようになったこと（v1.18 / v1.20）

**「調べたけれど判断できない」を書き残せるようになりました（v1.20）**

コードを精読した結果、「この動きが**意図どおりなのか不具合なのか判断できない**」ことがあります。
従来はこれを記録する場所がなく、曖昧なまま消えていました。専用の印を用意したので、
**後から利用者が判断できます**。

**「仕様」と「現行システムの不具合らしきもの」を分けて記録します（v1.20）**

コードを精読すると必ず現行システムのおかしな箇所が見つかりますが、これを仕様書に混ぜると
「そういう仕様なのか、バグなのか」が区別できなくなります。別の一覧に分けます。

**中間文書の書式を統一しました（v1.18）**

深掘りで作る分析メモの雛形を用意しました。作業ごとに書式が違う状態を避けられます。

#### 5b. 「保守のための理解」を選んだ場合の精度を上げました（v1.20）

**変更点は 2 つです。**

1. **「何のためにあるか」の点検を、目的から独立させました**（上記 2）。
   以前は「保守のための理解」を選ぶとこの点検が無効になっていました——**人が読むことが目的の場合に
   こそ必要な点検が切れていた**という設計の誤りです。現在はどの目的でも点検します。
2. **記述の深さ不足が「警告」として見えるようになりました。** 以前は完全に無効で、
   **浅いことに気づけないまま完了できました**。現在は作業を止めずに不足箇所を表示するので、
   「ここは浅いので必要ならコードを直接見る」という判断ができます。

**なお「保守のための理解」でも、網羅（機能を数え上げて漏れが 0 件）と
根拠の裏取り（記述がコードのどこに対応するか）は従来どおり機械で点検しています。**
無効だったのは「各項目をどこまで深く書いたか」の点検だけです。

#### 6. Windows 環境での不具合を修正しました（v1.19）

**Windows（Git Bash）で点検が誤検知を出していました。** 実測で 17 件の誤った指摘が出ており、
「仕様書に不備がある」と表示されるのに実際には不備がない状態でした。
原因は Windows と macOS でコマンドの挙動が異なる箇所で、全 19 箇所を修正しました。

**Windows でお使いの場合は v1.19 以降への更新を推奨します。**

**あわせて、改行コードの設定ファイルの追加が必要です**（v1.22 で同梱）。これが無いと、
Windows でリポジトリを取得したときに**点検プログラム自体が読めなくなり**、
「git リポジトリ内で実行してください」という誤った案内で停止します（中にいるのに、です）。
上記の誤検知とは別の問題で、
**すでに作業中のプロジェクトには自動では入りません**（下の「公開前の版で作業中のプロジェクトを更新する」を参照）。

#### 7. 点検の強化（v1.17〜v1.20）

v1.16 から、**自動点検の種類**とツール自身の**自己検査**はどちらも大幅に増えています。
具体的な数はここには書きません——版ごとに変わり、書き写した数は必ず古くなります。
現在の数はお手元の実物が正本です（点検の一覧は点検を実行したときの出力に、
自己検査の件数はツール自身の点検の最終行に出ます）。

追加された主な点検:

- **「対象がないので確認しませんでした」を合格にしない** — 確認していない状態が「合格」と表示され、
  見落としに気づけない箇所が複数ありました
- **仕様書の各節が「見出しだけで中身が空」になっていないか**（上記 2 の点検）
- **記述の裏取りを検証する際、根拠の行番号だけでなく「因果関係が原典に書かれているか」も確認する**
  — 検証で見つかる誤りの最多が「コードに書かれていない因果を書いてしまう」型でした（23 件中 10 件）

#### 8. 資料の訂正（v1.20）

このツールの精度が改善していたのに、**説明資料に古い数字（実力より約 12 ポイント低い値）が
残っていました**。3 回の測定結果に更新しました。

あわせて、よくある誤解への説明を追加しました——**「文書の種類」と「裏取りの深さ」は別の軸**です。
深掘りに進むと、新しい種類の文書が増えるだけでなく、**すでにある文書の裏取りも深くなります**。

#### 9. 「このファイルを直すと、どの仕様書が古くなるか」が分かるようになりました（v1.21）

これまでの仕様書は、記述のひとつひとつに「根拠はソースコードのどこか」を示していました。
しかしこれは**片方向**です。逆——「**このファイルを変更したら、どの仕様書を見直せばよいか**」——には
答えられませんでした。改修や移行の計画を立てるとき、実際に必要になるのはこちらの向きです。

**v1.21 から、ソースコードのファイル単位で「そのファイルを根拠にしている仕様書の一覧」を
自動で作るようになりました。**

| 使う場面 | 分かること |
|---|---|
| 既存システムを改修する | これから触るファイルから、影響する仕様書とその箇所数 |
| 仕様書を保守する | ソースコードが更新されたとき、見直すべき仕様書 |
| 設計の中心を見つける | 多くの仕様書から参照されている、システムの要になっているファイル |

参照の多い順に並ぶので、**どのファイルがシステムの中心かが一目で分かります**
（実際のプロジェクトでは、設定ファイル 1 つが 14 の仕様書から 68 箇所参照されていました）。

##### 手で書く必要はありません

- 一覧は機械が作ります。**手で編集しないでください**（次の作成時に上書きされます）
- 仕様書を更新したら一覧も作り直す必要があります。**古いまま放置すると点検で止まります**
  （中身と一覧が食い違った状態で仕様書を渡してしまうことを防ぐためです）
- 何度作っても同じ結果になります。**Windows と mac で作った一覧が 1 バイトも違わないことを
  確認済み**です（環境によって並び順が変わると、片方で作ったものが他方で「古い」と
  判定されてしまうため、そこを重点的に検証しました）

##### 設定が 2 つ増えました

| 設定 | 役割 | 設定しなかった場合 |
|---|---|---|
| 解析対象のソースコードの場所 | 根拠の照合に使う | 一覧は作りますが「照合していない」と明示した簡易版になり、**警告**が出ます |
| 一覧から除外するフォルダ | ビルド生成物などを対象外にする | 除外せずに一覧化します（同じ名前のコピーが混ざることがあります） |

##### すでに作業中のプロジェクトへの影響

- 点検プログラムを差し替えると、一覧が無いため**「未完了」と表示されます**。
  一覧を作る操作を 1 回実行すれば解消します（手順書に記載しています）
- 解析対象の場所を設定していない場合は**警告表示**になります。設定を 1 行足せば解消します
- **既存の成果物を壊さないことは確認済み**です（設定が無い場合も、無いことを明示して動きます）

##### 作成にかかる時間

**mac で 1〜2 秒、Windows で 10 秒前後**です。システムの規模にはほとんど比例しません
（Windows で長くかかるのは環境の特性によるもので、大規模なシステムでも同程度に収まります）。

#### 10. 仕様書を渡した相手（AI）が、鵜呑みにせず「どこまで信じてよいか」を判断するようになりました（v1.22）

**これが v1.22 の中心です。**

仕様書は AI が生成したもので、**全部が同じ確からしさではありません**。独立検証を通した記述と、
まだ通していない記述が同じ見た目で並びます。ところが受け取った側の AI は**その区別が付かないため、
すべてを同じ確度で断定してしまいます**——ここが、これまで人が毎回口頭で補っていた部分でした。

**v1.22 から、仕様書の中に「読む側の AI が守る規範」を同梱します。**
特別なツール・アプリ・追加のインストールは不要で、**仕様書を開けばそのまま効きます。**

##### 何が変わるか

改修の下調べや仕様の確認を AI に頼んだとき、回答が次のようになります。

| 変わること | 具体的に |
|---|---|
| **最初に「今どこまで確認できる状態か」を宣言する** | 解析対象のソースコードが手元にあるか無いかで、できることが変わります。**無いのに「確認しました」と書かなくなります** |
| **記述ごとに確からしさを添える** | 独立検証済み／未検証／機械生成、を**印象ではなく記録を引いて**判定します |
| **「分かっていないこと」を必ず書く** | 仕様書に「未確定」と記録された箇所を、**推測で埋めずにそのまま返します**。空なら「無い」と書きます |
| **調べた範囲の外に結論を広げない** | 「この種類のファイルには 0 件でした」を「システムに存在しません」と言い換えなくなります |
| **仕様書を勝手に書き換えない** | 調べる目的で開いた場合は読み取り専用として扱います（誤りを見つけたら是正の手順に戻します） |

##### なぜ効果があるか

**「未確定」と書かれた箇所を AI が推測で埋めてしまうのが、最も見つけにくい誤りです。**
埋められた文章は自然に読めるため、受け取った人は**それが推測だと気づけません**。
規範を同梱すると、その箇所は「分かっていないこと」として明示的に返ってきます。

同じ理由で、**未検証の記述を断定形で説明されるのも危険です**。改修の判断に使うと、
検証されていない前提の上に作業が積み上がります。

##### 使い方

**特別な操作はありません。** 仕様書のフォルダで AI エージェントを起動すれば、
規範が自動的に読み込まれます。エージェントが「モード」「結論」「根拠」「分かっていないこと」の
形で答え始めたら、正しく効いています。

- **専用のツールもサーバーも不要です**（Markdown のファイルが増えるだけです）
- **どの AI ツールでも同じ内容が使えます**（ツールに依存する書き方をしていません）
- **改修の判断に関わる説明では、現行システムの「実装バグらしき箇所」も確認するよう指示しています**
  （仕様どおりに直すと壊れる箇所があるためです）

##### すでに作業中のプロジェクトへの影響

- **点検プログラムだけでなく、仕様書フォルダのファイルも差し替えが必要です**
  （規範のファイルが増えます）。手順書に記載しています
- **Windows でご利用の場合は改行コードの設定ファイルの追加が必要です**
  （追加しないと点検プログラムが読めなくなり、誤った案内で停止します）
- **環境個別ファイルの除外設定を 1 行変更する必要があります。**
  変更しないと、入口のファイルが**記録されずに消えます**（従来の設定では除外対象でした）
- 規範のファイルを足した直後は、上の「v1.17〜v1.22 の変更」の 9 の「ファイルから仕様書を引く一覧」が
  **「古い」と表示されます**。一覧を作り直す操作を 1 回実行すれば解消します

### 公開前の版で作業中のプロジェクトを更新する

新しい版から順に書いています。

**v2.1.0 への更新について**: 作業中のプロジェクト（v2.0.0 で始めたもの）は、そのまま続けられます。
点検プログラムを差し替えると、**解析対象の指紋が記録されていないという警告**が出ます（止まりはしません）。
警告に表示されるコマンドを 1 回実行すれば、その時点の状態が記録されます。AI ツールを Kiro IDE に移すときは、
AI ツールに合わせたファイルを置き直す道具を使います（[hosts/README.md](../hosts/README.md)）。

**v2.0.0 への更新は、新しく開始するプロジェクトから適用してください。** v1.17〜v1.22 で作業中のプロジェクトは、
作る順番が違うため**点検プログラムの差し替えだけでは揃いません**。作業中のプロジェクトは、その版のまま進めるか、v2.0.0 以降で始め直すかを判断してください（下の「判断が必要になるケース」）。
**Windows でご利用の場合は WSL をお使いください**（Git Bash でも同じ判定になりますが、点検の実行時間が約 7.6 倍になります）。

このツールは**インストール不要**（シェルスクリプトと Markdown のみ）です。
更新は最新版を取得するだけで、既存の成果物には影響しません。

**すでに作業中のプロジェクトについて**: 点検プログラムと雛形は、各プロジェクトに配置された時点の
コピーで動きます。したがって**更新は新しく開始するプロジェクトから適用されます**。
作業中のプロジェクトに反映したい場合は点検プログラムを差し替えてください。その際、
**v1.19 以降で点検の種類が増え、必須の成果物と必須項目も増えているため、新しい未達項目が
表示される場合があります**（品質基準が上がったためで、成果物が壊れたわけではありません）。
v1.21 で増えた「ファイルから仕様書を引く一覧」については、上の「v1.17〜v1.22 の変更」の 9 のとおり
**一覧を作る操作を 1 回実行すれば解消します**。

**Windows でご利用の場合は、改行コードの設定ファイル（`.gitattributes`）の追加が必要です。**
これが無いと、Windows でリポジトリを取得したときに**点検プログラム自体が読めなくなり**、
「git リポジトリ内で実行してください」という**誤った案内**で停止します
（リポジトリの中にいるのにそう表示されます）。
初期化スクリプトの場合は **`set: pipefail: invalid option name`** という表示だけで止まります
——どちらも原因は同じ改行コードです。
新しく開始するプロジェクトには自動で入りますが、**すでに作業中のプロジェクトには入りません**。
**手順には順序があります**（順序を間違えると同じ停止が再発します）:

1. 設定ファイル（`.gitattributes`）を**リポジトリの一番上のフォルダ**に置き、
   **リポジトリに記録（commit）してください**（共有リポジトリの場合は反映も）。
   中身は「このリポジトリのファイルの改行を LF に固定する」という数行の指定です
   （**ツール本体のリポジトリ直下に同名のファイルが入っています**ので、それをコピーして使えます）。
   記録しないと、次に取得し直しても設定ファイルが存在せず、**同じ状態に戻ります**。
2. その後に**リポジトリ全体を取得し直してください**。
   1 ファイルだけ直す方法もありますが、**仕様書のファイルが元の改行のまま残り、
   別の点検項目が誤って「未達」と表示されます**のでお勧めしません。

**取得し直す前に、記録していない仕様書の作業を必ず記録するか、別の場所に退避してください**
——取得し直すと、記録していないファイルは失われます。

#### 更新すると増える点検

**再構築に直接使う仕様（作り直しの入力になる中核部分）が 1 件も書かれていない状態を、
未完了として表示します。** 「その部分を作る」設定のまま実物が無い、という食い違いを見ます。
作らない判断であれば、設定を「作らない」に変更し、**その理由を決定の記録に残してください**
——設定だけを書き換えて理由が残らない、という形にはできないようにしてあります。

**すでに深掘りまで進んでいるプロジェクトで、この中核部分に着手していない場合は新たに未完了が出ます**
——品質基準が上がったためで、成果物が壊れたわけではありません。

あわせて、**記述の詳しさをどこまで測ったかの記録から漏れている箇所**を挙げる点検を追加し、
既存の同種の点検を、深掘りの前から働くように移しました。「測っていない箇所が見えない」状態を防ぐためです。

**「すべて」「唯一」「存在しない」と言い切る記述には、数えた範囲を書きます。**
この種の記述は**反例 1 件で結論がひっくり返る**（「対策は不要」が「対策が必要」に変わる）ため、
どこから何件を数えたのかが書かれていないと**確認する側が判定できず、必ず差し戻し**になります。
書き方は「数え方（実行したコマンドか、どの一覧から採ったか）＋件数」です。
**すでに確認が済んだ箇所には遡って要求しません**——これから確認する箇所だけが対象です。

**確認の順序も見るようになりました。** 「すべて〜」と言い切る記述と、外部との取り決めを書いた箇所は、
実測で**誤りの割合が他の 3〜5 倍**でした。それにもかかわらず最後に回されがちで、
最終盤で結論が変わると手戻りが最大になります。**並行して進めるのは問題ありませんが、
これらを追い越して他を先に確認し終える形は止まります。**

**分析の最初の段階で、対象の数え方を 2 通りで突き合わせます。**
1 通りだけで数えた合計は検算できません（数え方そのものが漏れていても気づけない）。
実測で、**終盤に数え方の誤りが判明して 2 巡ぶん（約 2 日）の作り直し**が発生しています。
最初に 2 通りで突き合わせておけば、その手戻りは起きません。

**v1.22 は仕様書フォルダ側のファイルも差し替えが必要です**（上の「v1.17〜v1.22 の変更」の 10）。
あわせて**環境個別ファイルの除外設定を 1 行変更してください**——変更しないと入口のファイルが
記録されずに消えます。

#### 判断が必要になるケース

- **深掘り前の成果物で判断を進めたい場合** — 取りこぼしの性質（何が落ちやすいか）は、上の「深掘り前の成果物についての注意」にあります。
  それを踏まえて、どこまでリスクを取るかを決めてください
- **Windows 環境で点検の誤検知が出ている場合** — 判定の誤検知は v1.19 以降で修正済みです。
  ただし**改行コードに起因する停止は別問題**で、改行コードの設定ファイルの追加と
  記録（commit）が必要です（作業中のプロジェクトには自動では入りません）。手順は上にあります
- **作業量の見積りが必要な場合** — 深掘りを 1 機能単位だけ実施すると、
  そのシステムでの実測値が得られます（残りの見積りの根拠になります）
- **作業中のプロジェクトを v1.22 に更新したい場合** — 仕様書フォルダのファイル追加と
  除外設定の変更が必要です（上の「v1.17〜v1.22 の変更」の 10）
- **v1.17〜v1.22 で作業中のプロジェクトを v2.0.0 以降に移したい場合** — 作る順番が違うため、
  点検プログラムの差し替えだけでは揃いません。どこまでを活かせるかは、作る順番の違いを踏まえて判断してください
