# 仕様章立ての追補（php-procedural-mysql）

ISO/IEC/IEEE 29148 準拠の章立て（GP-8）に対する、このスタック固有の追補。
汎用テンプレート（`specs/*/_template.md`）の節では表現しきれない要素だけを扱う。

- **対象スタック**: 手続き型の PHP（PHP 4〜8）の Web アプリ。1 画面 1 ファイル＋ include する共通ファイル、SQL は文字列で組み立てる

## 追加すべき節（カテゴリ別）

| カテゴリ | 追加する節 | 理由（このスタックで必要になるもの） | 密度の判定基準 |
|---------|----------|--------------------------------|--------------|
| behavior | 画面の処理の流れ（1 ファイルの上から下） | 画面のファイルは「共通ファイルの include → 引数の読み取り → 操作の分岐 → SQL → HTML の出力」を上から順に書く。分岐の条件と順序が仕様 | 画面 1 つにつき include する共通ファイル・操作ごとの分岐・出力する HTML の部品 |
| behavior | 操作の一覧 | 1 つのファイルが `action` 等の値・送信ボタンの名前で複数の操作を受ける（DP-php-procedural-mysql-3） | 画面 1 つにつき `list-actions` の値の全数 |
| behavior | 要求の引数 | 引数は `$_GET` / `$_POST`（PHP 4 では `$HTTP_*_VARS`）・読み取りの関数から来て、型の宣言が無い | 画面 1 つにつき `list-params` の名前の全数・型と既定値・検証 |
| behavior | 画面遷移 | 遷移はリンク・フォームの送信先・`header('Location: ...')`・ファイル名の定数経由で書かれ、宣言的な遷移の定義が無い | 遷移元・遷移先・渡す値（クエリ文字列のキー）・条件 |
| data | 画面・ファイル × 表 × 操作（CRUD） | SQL は画面のファイルと共通ファイルの関数に散らばる（`list-crud`） | ファイル 1 つにつき参照・更新する全表と操作 |
| data | SQL の組み立て規則と値の埋め込み方 | 条件句の連結が業務ルールで、値の埋め込み方（エスケープ関数・プリペアド・素の連結）が移行判断を決める | 組み立てる SQL 1 つにつき基本形・条件句ごとの付加条件・埋め込み方 |
| data | 表名の解決規則 | 表名が定数・接頭辞・関数で決まる（osCommerce の `TABLE_*`・MantisBT の `{bug}` / `db_get_table()`） | 論理名と物理名の対応・接頭辞の設定箇所 |
| modules | 共通ファイルと関数 | 業務の処理が include する共通ファイルの関数にある（`includes/functions/*.php`・`core/*_api.php`） | 関数 1 つにつき引数・戻り値・使う表・呼び出し元 |
| modules | 設定（`configure.php` / `config_inc.php` / DB の設定表） | 動作の切り替えが定数・設定ファイル・DB の設定表に分かれる | 設定 1 つにつき既定値・読む箇所・意味 |
| modules | 認証・権限・セッション | ログインの確認と権限の判定が各画面の先頭の include と関数呼び出しにある | 画面 1 つにつき必要な権限・未ログイン時の遷移先 |

## 記述方式の指定

同じ対象を複数の書き方で書くと横断突合ができなくなるため、方式を固定する。

- **画面 ID（`SCR-NN`）は入口のファイル名と 1 対 1 に対応させ、本文にファイル名（拡張子つき）を必ず書く**
  （`AccountGroups.php`。`idents-page` の出力と `G-IDENT` で突合する。同じ名前が別ディレクトリにあるときはパスで区別する）。
- **引用は `path:line` で書く**。
- **操作は「値 → 処理」の形で 1 行ずつ書く**（`action=process → 住所を検証して保存`）。送信ボタンで分ける形は `submit=Name` と書く。
- **表は物理名（論理名）で書き、綴りは `idents-table` の出力に合わせる**。関数は `idents-function` の綴りで書く（`G-IDENT` は大小を区別して突合する）。
- **画面遷移は mermaid `stateDiagram` で書き、ノード ID を画面 ID と一致させる**（統合画面遷移図のノード数 = 画面数の突合。GP-14 ルール6）。

## このスタックで静的読解が効かない箇所（SB-6 の具体化）

- **変数でパスを組み立てる include**: `include(DIR_WS_MODULES . 'payment/' . $module)`・ディレクトリを列挙して include する形は、
  静的に先が決まらない。`ep-diff` の「変数で組み立てる include の式に当たるので入口から外したファイル」と、`mod-diff` の「解決できなかった include」を読む。
- **可変関数・可変変数**: `$func()` / `call_user_func($name)` / `$$var` は呼び出し先が実行時に決まる。名前の出どころ（設定・DB）を書く。
- **グローバル変数**: 共通ファイルが作る `$db` / `$language` 等のグローバル変数に画面が依存する。どの include で作られるかを書く。
- **`register_globals` / `extract($_POST)`**: 古いアプリは要求の引数がそのまま変数になる。`list-params` に出ない引数があるので、`extract` と
  `register_globals` の前提の有無を確かめる。
- **DB の設定表**: 動作の切り替え・メニュー・モジュールの有効・無効が DB の設定表（osCommerce の `configuration`）にあり、コードからは値が決まらない。
- **表名の接頭辞**: 接頭辞は設定で決まり、コードの SQL は論理名で書く（MantisBT の `{bug}`）。物理名は設定の値を添えて書く。
