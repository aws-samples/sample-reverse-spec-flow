# entry.md — Claude Code の規範の読ませ方とツール名対応表（GP-107）

## 1. 規範の読ませ方

| 文書 | 扱い | 根拠 |
|---|---|---|
| ルート `AGENTS.md` | **入口。** ルート直下なので起動時に読まれる。ただし下記のとおり**版によっては `CLAUDE.md` に抑止される** | 教訓 38 |
| ルート `CLAUDE.md` | **`@AGENTS.md` の 1 行だけ**を置く。要約を書かない | 同 |
| `specs/AGENTS.md` | **自動では読まれない。** 入口の表から自分で読む | 同 |
| `spec-extraction/AGENTS.md` | 同 | 同 |

**`CLAUDE.md` を置く理由**（置かないと環境によって入口が死ぬ）:

ルートに `AGENTS.md` と `CLAUDE.md` が両方あるときの扱いは**実装と版に依存する**。

| 環境 | 挙動 |
|---|---|
| macOS / 2.1.267 | **`CLAUDE.md` を優先し `AGENTS.md` を読まない**（3 回再現） |
| Windows / 2.1.265 | **両方読む**（3 回再現） |

つまり後から `/init` 等で `CLAUDE.md` が作られた時点で入口が無効化されうる。
`CLAUDE.md` に `@AGENTS.md` を書くことで**散文の誘導（モデルが自発的に読むかに依存）ではなく
ホスト保証**になり、**両環境で 3/3 成功**した。
**片方の環境で「無くても読まれる」ことを確認しても外してはいけない**（もう片方で入口が死ぬ）。

## 2. ツール名対応表

| 役割（抽象） | Claude Code でのツール名 |
|---|---|
| サブエージェントを起動する | Agent / Task 系のツール（版で名前が変わる。**手順書・skill には書かない**） |
| 隔離した検証官を起動する | 上のツールで **`subagent_type: spec-verifier`** を指定する（§5） |
| ワークスペースを検索する | Grep / Glob 系 |
| シェルを実行する | Bash |

## 3. このホスト固有の禁止事項

| # | 禁止・制約 | 理由 |
|---|---|---|
| 1 | ルート `CLAUDE.md` に**要約（件数・版・ゲート数・フェーズ一覧）を書かない** | 二重記録になり腐る（実運用の 3 リポジトリで、手書きの `CLAUDE.md` がゲート数と改称前の呼称を古いまま保持していた）。GP-101 |
| 2 | ルート `CLAUDE.md` を `.gitignore` に入れない | 追跡しないと引き継がれず、環境によっては入口が発火しない |

## 4. 既知の制約

- **ゲートの実時間はシェルで大きく変わる**（Windows 実測）。`gates.sh phase4` が
  git bash で **26.2 分** / WSL で **3.4 分**（**7.6 倍**）。プロセス起動のコストが主成分
  （システム時間が git bash で 73% / WSL で 63%）。**Windows では WSL を推奨する**。
  ただし **`init.sh` は Git Bash で走らせる**——Claude Code は hook（`verifier-guard.sh`）を Git Bash で動かすので、WSL で初期化すると
  `gate-config.env` の `SOURCE_PATH` が `/mnt/d/…` の形になり、hook が解析対象を見つけられず検証官の読み取りをすべて拒否するはず（**未実測**。スクリプトからの推論）。
  詳細は `docs/how-it-works.md` §3。
- **並列実行の事故が 2 件観測されている**（完走試験）——共有した一時ディレクトリの上書きと、
  並列中のコミットが中間状態を取り込んだ件。対策は `GP-15` ルール11 に反映済み。

## 5. 検証官の隔離（GP-16 ルール2）

skill（`density-verify` §2・`spec-adversarial-audit` 手順 3）は「読み取りを解析対象ソースの配下に
機械で制限する起動手段」とだけ書いている。この節は、その手段のこのホストでの実体と、隔離の確かめ方を示す。
根拠は `MEASURED.md` 項目 4・5（2.1.305）。

**起動**: サブエージェントを **`subagent_type: spec-verifier`** で起動する（`.claude/agents/spec-verifier.md`）。
複数バッチは並列起動してよい。定義は次の 3 点の組で隔離を強制する。

| 定義の要素 | 塞ぐもの |
|---|---|
| `tools: Read, Grep, Glob` | Bash で回り道すること（hook はシェルのコマンド文字列を判定できない） |
| `omitClaudeMd: true` | ルートの `CLAUDE.md` と、そこから `@` で取り込まれる `AGENTS.md` の注入 |
| PreToolUse hook（`.claude/hooks/verifier-guard.sh`） | 検証官が仕様リポジトリの分析物・仕様本文を自分で読みに行くこと（読み取りを `SOURCE_PATH` の配下だけに通す） |

**版の下限: Claude Code 2.1.271 以上**（公式ドキュメント: `omitClaudeMd` は 2.1.271 以降）。それより前の版では
`omitClaudeMd` が黙って無視され、ルートの `CLAUDE.md` → `@AGENTS.md` が検証官に注入される。**この緩みは hook のカナリア記録では
検出できない**（記録は hook が動いたことしか示さない）ので、版を `claude --version` で確かめてから起動する。
教訓 38 の実測版（2.1.265 / 2.1.267）は入口文書の挙動の記録であって、この節の根拠（2.1.305）とは別である。

**注入されるものの残り**（公式ドキュメント「what loads at startup」。`omitClaudeMd` でも止まらない）:
仕様リポジトリの **git status のスナップショット**（ブランチ・状態・直近コミット）と、MCP サーバーの instructions。
直近のコミットメッセージは生成側の文脈になりうる（例: 「API 仕様の X 節を書いた」）。止める設定（`includeGitInstructions`）が
サブエージェントに効くかは**未測定**。測るまでは、コミットメッセージに検証対象ブロックの結論を書かないことで緩和する。

**作業ディレクトリは仕様リポジトリのルートにする**（下のパスはルートからの相対。`spec-extraction/` で起動すると外れる）。
生成先の `.gitignore` は `*.log` を除外するので、記録は `.tsv` にしてある（`.log` だと隔離の証跡が追跡されない）。

**隔離の確かめ方**（検証官の自己申告で確かめない。対象は spec-verifier で起動した検証官と、検証官の指示テンプレートで起動したサブエージェントすべて）:

確かめるのは**終わった後に 1 回**である。Claude Code はサブエージェントごとの記録（種類・ツール呼び出し・hook の拒否）を
セッション記録に残すので、それを `spec-extraction/03-audit/claude-verify-check.sh` が検証官ごとに読む。
**起動のたびに照合しない。取りまとめ役のサブエージェントを立てない**（以前の「確認の窓」は、並列のバッチを
窓にまとめる手続きのために取りまとめ役が生まれてサブエージェントの費用の約 4 割を占め、照合に失敗した巡は丸ごとやり直しになった。
約 5,200 行の対象での実測。`MEASURED.md` 追補 V-6）。

1. **セッションで最初に Verify する前に、spec-verifier を 1 体だけ起動して確かめる**（hook は信頼ダイアログの承認で
   動くかどうかが変わるので、セッションごとに 1 回）。起動前に `date -u +%Y-%m-%dT%H:%M:%S` を控え、
   完了後に `bash spec-extraction/03-audit/claude-verify-check.sh --since <控えた時刻> --expect 1` が **exit 0** であることを見る。
   `C2`（hook が動いていない）で落ちたら信頼ダイアログを承認してから起動し直す。
2. 以後は**並列に起動してよい**。巡（またはまとまった起動）の前に時刻を控え、起動した検証官の数を数えておき、終わったら
   `--since <時刻> --expect <起動した数>` で同じスクリプトを 1 回走らせる（**数えるのは起動した数だけ**。記録との照合はスクリプトが行う。
   PASS が起動数に満たなければ rc=3——指示文を言い換えて汎用で起動した 1 体は記録から見分けられないので、数で拾う）。
3. **採用してよいのは `PASS` の行の検証官の結果だけ**。`FAIL` の行の結果、および出力の `isolation_check` が `"denied"` で
   ない結果（`READ_SUCCEEDED`・`UNVERIFIED`・欄が無い）は**集計にも台帳にも入れない**。
   **捨てるのはその検証官の結果だけで、巡全体を無効にしない**（同じブロックを spec-verifier で起動し直す）。
4. exit 2（記録が見つからない・対象 0 体）は**何も確かめていない**。作業ディレクトリが仕様リポジトリのルートか
   `spec-extraction/` であるか、`--since` が起動前の時刻かを確かめる。それでも読めないときは下の縮退へ倒す。
   **Windows（Git Bash）では未実測**（記録のパスが `C:\…` の形になるのを POSIX 形式に直して照合するが、実機で確かめていない）。

| 検査 | 何を拾うか |
|---|---|
| C1 検証官のテンプレートで起動したのが spec-verifier か | 汎用のサブエージェントで代用した検証官 |
| C2 verifier-guard の拒否が記録にあるか | hook が動いていない検証官（信頼ダイアログ未承認など） |
| C3 読み取りが解析対象ソースの配下だけか（外は hook に拒否されているか）・Read / Grep / Glob 以外を使っていないか | 隔離の外を読めた検証官 |

`guard-canary.tsv`（hook がカナリアを拒否した記録）は**残す**が、合否には使わない（補助の証跡。カナリアのパスを取り違えた
検証官は、hook に拒否されても行が残らない——実測）。

**縮退（GP-107 ルール7）**: hook は**ワークスペースの信頼ダイアログを承認するまで動かない**（`claude -p` も承認扱いにならない）。
`tools` と `omitClaudeMd` は効くので表面上は動いて見えるが、上の確かめ方で検出され結果は捨てられる。
承認してから起動し直す。それでも確かめられないときは GP-16 ルール8 の縮退（別コンテキスト再検証 → 人間サインオフ）へ倒す。

**この手段で起動できない検証官**:

| 検証官 | 理由 | 起動方法 |
|---|---|---|
| 件数の検算官（`density-verify` §2b） | 走査コマンドの実行にシェルが要り、シェルはパスで閉じ込められない | 汎用のサブエージェントで起動し、台帳の notes に `count-verifier: prompt-isolated` と残す |
| レンズ反証者（`spec-adversarial-audit` 手順 2） | `specs/` と code-graph を読むことが任務に含まれる | 汎用のサブエージェント（隔離は指示文の規律だけ） |

**仕様リポジトリの中で汎用のサブエージェントを起動して spec-verifier の代わりにしない。** 分析物を自分で読みに行けるので、隔離にならない。
**他ホストの手段（`spec-extraction/03-audit/kiro-verify.sh` など）が残っていても使わない**（ホストを切り替えた後の残置物。このホストでは測っていない）。
