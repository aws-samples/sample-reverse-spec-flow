| 確認項目 | 結果 |
|---|---|

| 出現回数 | 3 回 |

#### 測定方法（**ここが結論を決めたので詳しく残す**）

| 要件 | どう満たしたか |
|---|---|
| 承認ダイアログを区間に入れない | コマンドを `bash -c '…'` の 1 本にした。**`bash *` はこのワークスペースの `permissions.yaml` に allow で在り**、`sleep *` はグローバルの `trustedCommands` に在る |
| モデル応答待ちを区間に入れない | **サブエージェントのツール呼び出しを 1 回だけ**にした（開始マーカー・`sleep`・終了マーカーを 1 コマンドに入れた）。ターンをまたがないので区間にモデル待ちが入らない |
| 時刻をモデルに報告させない | 区間の両端を**OS が付けるファイルの mtime** で取り（`printf x > …`）、親が後から `stat -f '%N %Fm'` でナノ秒まで読んだ |
| 親側の直列化と混ざらない | 判定は**サブエージェント同士の区間の重なり**で行い、親の体感時間を使わない |

```sh
# 各サブエージェントに実行させた唯一のコマンド（N は 1..8）
bash -c 'D=…/_scratch/par; printf x > $D/bN-start; sleep 30; printf x > $D/bN-end'
```

#### 🔴 初回の測定は誤りだった（撤回する。**空振りの記録として残す**）

**撤回する結論**: 「平均同時実行数 1.17・瞬間最大 3 で、実効的にはほぼ逐次」。

**誤りの原因**: 測定器に **`date +%s.%N` を使った**。
`date` は**グローバルの `trustedCommands`（24 件）にもワークスペースの `permissions.yaml` にも無い**。
したがって 8 本のサブエージェントが区間の両端で `date` を呼ぶたびに**承認ダイアログで止まり**、
**人がクリックするまで待っていた**。観測した起動間隔（16.7 / 8.9 / 3.8 / 6.8 / 7.9 / 26.2 秒）は
**ホストの並列度ではなく人のクリック待ち**である。
さらに区間の中にモデル応答待ちが 2 回入っていた（`date` → `sleep` → `date` で 3 ターン）。

**なぜ気づけたか**: 自分では気づかなかった。**ユーザーが「テストのやり方が悪かったことはないか」と
問い直したことで再検討した。** A-2d / A-5 で「シェルは承認が要る／承認は 2 層ある」ことを
**自分で測って記録していたのに、その知識を自分の測定器に適用していなかった。**

**教訓（他ホストの測定にも効く）**:
1. **測定器に使うコマンドが承認を要しないことを、測定の前に許可リストで確認する。**
   承認が挟まると**人の反応時間をホストの挙動として記録してしまう**。
2. **「ほぼ逐次」のような否定形の結論は、肯定形より強い証拠を要求する**
   （`GP-103` ルール6 の「不在型は反例 1 件で崩れる」と同型）。1 条件 1 回で断定したのが誤りだった。
3. **区間の両端をモデルに報告させない。** OS が付ける時刻（mtime）を使えば、
   モデル応答待ちも承認待ちも区間から外れる。

#### 帰結（Phase 0' / B の設計に効く）

- **`GP-15`「安全区間は並列が既定」は Kiro でも成立する。** 実効 3.3 倍である。
- **`GP-103` / FB-7「分割すれば並列に走るので実時間は縮む」も成立する。**
- **🔴 `work-plan.md` (D) の「同時数」に 5 を書かない**（2026-10-21 にユーザーの指摘で訂正した。
  **初版は「5 を超える値を書かない」と書いており、これは誤りだった**）。
  理由は 3 つある。
  1. **5 はホスト固有・版固有である。** 定数は **Kiro IDE 1.4.5 の拡張バンドルにしか無い**。
     **`kiro-cli` は別製品**（実測 `kiro-cli 2.33.0`）で、
     バイナリ内に `MAX_CONCURRENT_SUBAGENTS` の文字列が**無い**——**上限は IDE 固有である**。
     Claude Code では 10 以上の並列実績がある（ユーザー報告）。
  2. **`work-plan.md` はホスト中立な計画書である。** そこにホストのスロットル値を焼き込むのは、
     ルート `AGENTS.md` の「**変動する値を書かない。書くと必ず腐る**」と
     `GP-105` ルール6「汎用側にスタック固有の記述を戻さない」に正面から反する。
     **ホストの上限はホスト層（`hosts/<host>/MEASURED.md`）に書く。**
  3. **キューで待つことに弊害が無い。** 本測定で 8 本投入して **8 本とも完走した**
     （起動拒否・取りこぼし・出力の混線はいずれも観測されていない）。
     待ち時間が増えるだけで、**失敗もデータ欠損も起きない**。

## A-5. 未信頼ワークスペースでの挙動 — **前提が崩れた。代替測定で決着（fail-open なし）**

### 🔴 前提の誤りを 2 件訂正する

**訂正 1: 信頼ダイアログは出なかった。** 2026-10-21、**一度も開いたことのない新規ワークスペース**
（`…/jpetstore-spec-untrusted`）を `kiro -n` で開いたが、**信頼を求めるダイアログは表示されなかった。**
`~/Library/Application Support/Kiro/User/settings.json` に
`security.workspace.trust.*` 系のキーは**存在しない**（無効化されているのではなく、設定自体が無い）。

→ **Kiro 1.4.5 には VS Code 流の「ワークスペース信頼」プロンプトが見当たらない。**
したがって **A-5 を「未信頼ワークスペースを作って比較する」形では測定できない**
（比較対象の状態を作れない）。

**訂正 2: `~/.kiro/.trust-migration.json` は信頼状態の保存先ではない。**
本記録は当初これを「信頼状態の保存先」と書いたが、**誤りである**。中身は**1 回限りの移行記録**で、
信頼の可否を持たない:

```json
{ "version": 1, "userScope": { "completedAt": "2026-08-20T…", "rulesWritten": 3 },
  "mcpUserScope": { "completedAt": "2026-08-20T…", "rulesWritten": 9 } }
```

同名のファイルが**ワークスペースごとにも**置かれるが、こちらも移行記録である
（`root` にワークスペースの絶対パスを持つだけ）。

### 実際の機構: ワークスペース単位の**能力別許可リスト**

`~/.kiro/workspace-roots/<workspace-hash>/` が実体である。

| ファイル | 内容 |
|---|---|
| `.trust-migration.json` | 移行記録。`root`（ワークスペースの絶対パス）・`completedAt`・`rulesWritten` |
| **`permissions.yaml`** | **承認の実体。** `capability` ごとの allow ルール |

`jpetstore-spec`（`e21d08ef6d9dc7b9`）の `permissions.yaml`:

```yaml
rules:
  - capability: shell
    effect: allow
    match: [ "head *", "printf *", "tr *", "sw_vers *", "which *", "kiro *",
             "/usr/libexec/PlistBuddy *", "env", "sort *", "mkdir *", "bash *",
             "tee *", "cp *", "rm *", "comm *", "diff *", "mktemp *", "rmdir *",
             "cut *", "uniq *", "chk *", "stat *" ]
  - capability: skill
    effect: allow
    match: [ "density-verify" ]
```

> **🔵 2026-10-21 追記（実装の確認で 2 点わかった）。**
> **(1) スコープは 2 層ではなく 3 つある。** 設定キー `kiroAgent.trust.defaultScope` の enum は
> **`user` / `workspace` / `session`**（既定 `workspace`）である。
> **`session` スコープの存在が「一度きりの許可は痕跡を残さない」理由を説明する**
> ——痕跡が残らないのは不備ではなく、**セッション限りの許可が一級の選択肢として用意されている**ためである。
> **(2) 許可パターンにも 3 種ある。** `kiroAgent.trust.defaultPattern` の enum は
> **`full` / `partial` / `base`**（既定 `base`）。`permissions.yaml` の `match: [ "bash *" ]` という形は
> **`base` パターン**（コマンドの基底＋ワイルドカード）の産物である。
> **(3) `permissions.yaml` を書く経路は「常に許可」だけではない。** コマンド
> `kiroAgent.openPermissionsUser` / `kiroAgent.openPermissionsWorkspace` が存在し、
> **UI から直接編集できる**（A-5 の未測定項目「`permissions.yaml` を書く経路の網羅」の一部が埋まった）。

**承認は 2 層ある**（これが A-2d の解釈を変える。下記）:

| 層 | 場所 | 範囲 |
|---|---|---|
| グローバル | `User/settings.json` の `kiroAgent.trustedCommands` / `trustedTools` | 全ワークスペース |
| **ワークスペース** | `~/.kiro/workspace-roots/<hash>/permissions.yaml` | そのワークスペースのみ |

**`capability: skill` が存在することが重要**: **ワークスペース skill の有効化は承認ゲートの対象**である。
`density-verify` が allow に入っているのは、**セッション 1 の A-3-2 で有効化したときに承認された**ためと解釈できる
（A-3-2 の記録に承認ダイアログの言及が無いのは**記録漏れ**である）。
一方 `spec-adversarial-audit` は allow に無い＝**まだ有効化されていない**（A-3 の「未試行」と整合）。
→ **提示一覧に載ること（A-3-5）と、有効化できること（A-3-2）は別のゲートである。**

### 🔴 A-2d の結論を訂正する

A-2d で「`bash` は許可リストに入っていないので、`gates.sh` の実行は信頼済みでもダイアログが出る」と
書いたが、**誤りである**。**`bash *` は `jpetstore-spec` の `permissions.yaml` に allow として入っていた。**
グローバル側（`kiroAgent.trustedCommands`）だけを見て判断したのが原因で、
**ワークスペース層を見落としていた。**

→ A-2d の「シェルで承認が出なかった」事実は変わらないが、**理由は 2 層のどちらかであり、
`sed` はグローバル層、`bash` はワークスペース層**だった。
**案 B（シェル経由に統一）がリポジトリ外の設定に依存するという結論は変わらない**
——むしろ**依存先が 2 つに増えた**ので、より弱い。

### 測定の本命はどう変わるか

当初の本命は「**警告もエラーも出ずに** skill や steering が効かなくなるか」（fail-open）だった。
**実機構は fail-open ではなく fail-closed に見える**:

- 承認されていない能力は**ダイアログで止まる**（黙って無効化されるのではない）。
- 承認の履歴は `permissions.yaml` に**人間可読で残る**＝**事後監査が可能**。

→ **カナリアの設計方針が変わる。** 「黙って無効化されたことを検出する」仕掛けではなく、
**「`permissions.yaml` に `capability: skill` の allow があるか」を確認する手順**で足りる可能性がある。

### 判断
