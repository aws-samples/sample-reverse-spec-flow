# spec-adversarial-audit — 高影響宣言の敵対的独立検証（SB-12/GP-16 の実装）

高影響・不可逆な宣言（再構築レディ・監査完了・reconciliation ゼロ・保持必須契約）は、生成者と
同一コンテキストの自己申告で確定してはならない（SB-12）。この skill は独立検証を段階的縮退の
**最上位（別エージェントの敵対的反証）で常に実行**し、実施記録の追記までを責務とする
（記録漏れ＝「未検証レディ」問題の再発防止）。

`gates.sh phase4` が「形式の健全性」を担保するのに対し、この skill は「内容の正確性」を担保する
（GP-6 ルール11 の役割分離）。**gates.sh が FAIL 0 になってから実行する**（形式未達のまま内容検証しても差し戻しになる）。

## 引数

検証対象の宣言を指定する（複数可。省略時はユーザーに確認する）:
- `ready` — 再構築レディ宣言（GP-13 ルール10 の十分条件）
- `audit-complete` — 監査完了宣言（GP-6）
- `reconciliation` — reconciliation ゼロ主張（SB-2）
- `contracts` — 保持必須契約の互換保証（GP-13 ルール5）

## 手順

### 1. 前提確認

- `bash spec-extraction/03-audit/gates.sh phase4` を実行し FAIL 0 を確認する。FAIL があれば
  中断してユーザーに報告する（形式未達の是正が先）。
- 解析対象ソースのパスを `spec-extraction/AGENTS.md` から取得する。

### 2. 反証者の編成（レンズ分担 + 多数決）

対象宣言ごとに、**異なるレンズを割り当てた複数のサブエージェント**を並列起動する
（同一反証者 N 体の冗長多数決より、レンズ多様化の方が失敗モードを多く捕まえる: GP-16 ルール3）。

**隔離の規律（GP-16 ルール2）**: 各反証者に渡すのは (a) 検証対象の claim（宣言文とその根拠として
提示されているチェックリスト・数値）、(b) 一次情報の所在（解析対象ソースのパス・specs/ のパス・
code-graph のパス）**のみ**。生成時の推論・要約・worklog を見せない。
**手順 2 のレンズ反証者は、specs/ と code-graph を読むことが任務に含まれるので、読み取りを解析対象ソースに
機械で制限する起動手段（手順 3）を使えない。** 隔離は指示文の規律に頼る（機械で強制されていない）。

**共通指示（全反証者）**: 「あなたの任務は確認でなく反証。この宣言を偽だと示せるか試し、
判断に迷ったら反証側に倒せ。出力は JSON: `{lens, verdict: REFUTED|UPHELD, findings: [{what, evidence}]}`」

**宣言別のレンズ割当:**

| 宣言 | レンズ（各 1 エージェント） |
|------|---------------------------|
| ready / audit-complete | (a) データ完全性: 全エンティティ定義（`01-code-graph/enumeration.md`（併用時は `enumeration-<名前>.md` も）の NODE-BND 独立ソース）を独立列挙し data 仕様との差集合を取る（SB-9 横断版） |
| | (b) EP・コマンド網羅: 全 EP/コマンド/別アダプタ（REST/CLI/Batch/メッセージング）を独立列挙し仕様との差集合（SB-2 横断版）。別バージョン API の探索観点を必ず適用 |
| | (c) 縦串間整合: 二重記述の値矛盾（対外契約 URL・列挙・閾値の文字列突合）・委譲先の実在（GP-11 C） |
| | (d) 成果物形態: 宣言した成果物種別（画面/帳票/ジョブ/統合ビュー等）の複製実体 or 非該当 ADR を独立列挙で確認（GP-19。件数一致でなくファイル実在まで） |
| | (e) 密度充足と類型の抜け: 台帳の thick 判定を抜き取りで原典突合＋「既存類型に収まらない密度対象（DDL 列・API 契約・イベント/権限/seed）はないか」（GP-20/21） |
| reconciliation | 上記 (b) ＋ disposition の水増し分類検査（not_applicable / delegated の理由が妥当か。委譲先実在まで） |
| contracts | 保持必須契約ごとに 1 体: 具体パターン（URL テンプレート・スキーマ・形式）が原典と一致し、この記述だけで互換を保証できるか（抽象記述への逃げを検出） |

completeness-critic の規律: 反証者には**生成物を見せる前に一次情報から独立列挙させ、その後で
specs/code-graph と突合させる**（claim に挙がっていない見落とし＝カバレッジの穴は、claim の検証では出ない:
GP-16 ルール7）。

### 2b. 全体推定のための層化無作為抽出（GP-16 ルール10・FB-6。レンズ検証と直交する必須段）

手順 2 のレンズ検証は「**特定の失敗モードが在るか**」を突く（狙い撃ち）。これだけでは
「**仕様全体の誤り率がどれくらいか**」は分からない。実運用で、レンズ相当の意図的な標本 10 件
（母集団 1,742 の 0.6%）で「レディ」を宣言し、後の層化無作為抽出 48 件で**誤り率 29.2%**
（95% CI 18.2〜43.2%）が判明して格下げされた。よって**両方**行う。

1. **母集団を機械的に定義して数える。** 単位は「`path:line` を伴う検証可能な主張」。
   数え方のコマンドと件数を記録する（後から再現できるように）。
1b. **断定型の密度を測り、配分を決める（GP-16 ルール10-(7)）。**
   `bash 03-audit/gates.sh metrics` を実行し `assertion_density_absent` / `_unique` / `_universal` を読む。
   **比例配分は「誤りが層に均等に散らばっている」前提に立つが成り立たない**——層ごとに
   「**反例 1 件で崩れる記述**」の密度が数倍違う。実測では**ある層は行数では母集団の 20% なのに
   断定型の 54%（301/555 件）を占め、その層の誤り率が 54.5% で全層最悪**だった。
   - **不在型（「0 件」「存在しない」「持たない」）は手順 3 に回す前に機械で絞る**:
     識別子を抽出して**全ソース 1 パス走査**で反例を探す。走査語は識別子ではなく**役割**で設計し
     （GP-2 ルール8）、**正規表現の交替は長い識別子を先に置き語境界を付ける**（短い語が長い語に食い込む）。
   - **唯一型・全称型は機械では反例を探しにくい**（母集団の定義が記述に埋め込まれている）
     → **隔離反証者に回す優先対象**にする。
2. **層化無作為抽出でサンプルを作る。** 層はカテゴリ（modules / api / data / behavior / rebuild）。
   各層に**断定型の密度で重み付けした配分**＋**最低数**を確保する（比例配分にしない。手順 1b）。
   層が薄いと 1 件の誤りで誤り率が大きく振れるため、層別に意味のある推定ができる件数を確保する。
   **乱数シードを固定して記録する**（時刻由来のシードは使わない）。層別の誤り率は大きく偏るため
   （実測: api/behavior 10〜11% に対し **data 41.7%・modules 54.5%**）、層を跨いで薄く取ると
   最も危険な層を見落とす。**重み付けした場合は層別推定を母集団比で再重み付けして全体率を出す**
   （重点配分した標本をそのまま平均すると全体率が過大になる）。
3. **各サンプルを隔離した反証者に渡す。** 渡すのは (主張の本文 + 原典の所在) のみ
   （手順 2 と同じ隔離規律。**ただし原典の所在は解析対象ソースのパスに限る**。下の起動手段は specs/・code-graph の読み取りを拒否する）。判定は `CONFIRMED / PARTIAL / REFUTED`。
   **反証者は、読み取りを解析対象ソースの配下だけに機械で制限する起動手段で起動する**（`density-verify` §2 と同じ。
   手段の実体と隔離の確かめ方はリポジトリのルートの `HOST.md` の「検証官の隔離」節）。
   **隔離を確認できなかった結果は誤り率の集計に入れない**（手段が無いホストでは指示文の規律で起動し、
   実施記録に `prompt-isolated` と残す）。
4. **層別の誤り率と信頼区間を算出する**（Wilson score interval 等）。点推定だけを報告しない。
5. **誤りを安全側／危険側に分類する。** 担保を**過大**に述べる誤りは再構築時に機能欠落を生む。
   **ただし「過小申告だから安全」と自動判定しない**——実運用では過小申告の誤りも安全側ではないと
   判定された（読者が過剰な作り込みや誤った設計判断に導かれるため）。各誤りが再構築時に何を引き起こすかで判定する。
6. **母集団換算の残存誤り数を推定する**（例「母集団の 317〜752 件に誤りが残ると推定」）。

**判定への接続**: 誤り率が目標を超える場合、レンズが全て UPHELD でも
**「レディ」ではなく「条件付きレディ」に格下げする**（是正すべき層と件数を明示する）。
`data` / `modules` のように行番号や件数断定が壊れやすい層は、是正後に**同じシードで再検証**する。

### 3. 判定の集約（多数決）

- 各レンズの verdict を集約する。**1 レンズでも REFUTED（具体的 findings 付き）なら宣言は不成立**
  （高影響宣言は過半でなく「反証ゼロ」を要求する——レンズは重複しない失敗モードを見ているため、
  多数決で薄めない）。
- findings が検証者の誤り（見落とし）と疑われる場合は、該当箇所の原典を開いて裁定する。
  誤反証だった場合も、なぜ紛らわしかったかを記録して該当記述を明確化する（GP-16 ルール5）。

### 4. 手戻りの接続（GP-1）

REFUTED の findings は「その場で辻褄合わせ」せず、発生元フェーズの中間生成物
（分析物・コードグラフ・仕様・台帳）まで戻して修正する。修正後、影響を受けたレンズだけ再実行する。

### 5. 実施記録の追記（この skill の必須責務）

結果に関わらず、次の 2 箇所に実施記録を追記する:
- `spec-extraction/03-audit/rebuild-readiness.md` の「独立検証の記録」欄
- `spec-extraction/03-audit/traceability.md` の「高影響宣言の独立検証」欄

記録内容: 手段（別エージェント反証・レンズ構成）／実施日／結果（レンズ別 verdict・反証件数・
差し戻し項目・裁定）。生 JSON は `spec-extraction/03-audit/verify-log/` の下に、実施日と宣言が分かる名前で保存する（例: `adversarial-<宣言>-<日付>.json`、`adversarial-<日付>/`）。

**「検証範囲」欄も必ず埋める（GP-16 ルール10。空欄は G-INDEP が FAIL にする）**:
母集団の定義と件数／検証件数と割合／標本の選び方（層化無作為抽出＋シード値 / 意図的選択）／
層別の誤り率／誤りの安全側・危険側の分類。**「実施した」だけの記録は規約違反**である。

### 6. 報告

ユーザーに報告する: 宣言ごとの判定（成立 / 条件付き / 不成立＋差し戻し先）／レンズ別の findings 要約／
**層化抽出の結果（母集団・検証割合・層別誤り率・信頼区間・母集団換算の残存誤り推定）**／
修正済み・未修正の内訳。

**格上げの条件は 2 つあり、両方必要**:
- 全レンズが UPHELD（手順 3。特定の失敗モードが無いこと）
- 層化抽出の誤り率が目標内（手順 2b。全体として誤りが薄いこと）

どちらか欠ければ「未検証レディ（provisional-ready）」または「条件付きレディ」のまま格上げしない。
**レンズ全 UPHELD だけを根拠に「レディ」と名乗ることは FB-6 の再発である。**

## 注意

- **この skill はオプションの加速装置。** skill が使えない環境では GP-16 ルール8 の段階的縮退
  （(2) 別コンテキスト再検証 → (3) 人間サインオフ）で独立性を確保する。いずれの経路でも
  実施記録の追記（手順 5）は必須（記録の無い独立検証は G-INDEP で未実施扱いになる）。
- 解析対象ソースは参照専用（SB-5）。
- 大規模（多数ドメイン）では、この skill の (a)〜(e) レンズが GP-16 ルール9 の
  「横断 completeness-critic 5 レンズ」を兼ねる。
