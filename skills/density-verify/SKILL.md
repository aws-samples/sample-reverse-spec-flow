# density-verify — 密度ブロックの独立 Verify（GP-22/SB-20/SB-21 の実装）

密度昇格ブロック（1 スライスの API 契約・計算式群・DDL 等）は、生成と同一コンテキストの自己申告では
**"path:line 付きで一見正しい" 誤りが約 35% 残る**（実測。存在しない行番号・例外クラス誤帰属・過大 must・
HTTP コード誤り・デッド宣言の live 掲載・キー名/enum 誤り）。この skill は GP-22 の
**Extract→Verify→Repair→Gate** の Verify 以降を、コンテキスト隔離を機械的に強制して実行する。

## 前提

- 作業対象は reverse-spec-flow が生成した spec リポジトリ（`spec-extraction/03-audit/density-ledger.tsv` が存在する）。
- 台帳が正本。Markdown 表は生成物（SB-14 の正本規律）。
- 原典（解析対象ソース）のパスは `spec-extraction/AGENTS.md` の冒頭に記載されている。

## 手順

### 1. 対象ブロックの列挙

`spec-extraction/03-audit/density-ledger.tsv` を読み、`verify_status` が `verified` 以外
（unverified / verifying / repairing）のデータ行を列挙する。引数でブロック ID・カテゴリ・spec ファイルが
指定された場合はそのサブセットに絞る。

対象が 0 件なら「全ブロック verified 済み」と報告して終了する。

### 2. Verify — コンテキスト隔離したサブエージェントで原典突合

対象ブロックを **2〜3 ブロックずつのバッチ**（GP-15 ルール9: 異常終了時の再実行を安くする）に分け、
**各ブロックにつき、下の指示テンプレートを埋めた検証官を 1 体起動する**（サブエージェントを起動する手段は
ホストで違うので、ここではツール名を書かない。GP-107）。複数バッチは並列起動してよい（ホストが許す範囲で）。

**検証官は、読み取りを解析対象ソースの配下に機械で制限する起動手段で起動する**（GP-16 ルール2）。
指示文で渡さなくても、検証官は仕様リポジトリの分析物を自分で読みに行けるため（実測）。
**手段の実体・隔離の確かめ方・縮退は、リポジトリのルートの `HOST.md` の「検証官の隔離」節に従う**
（使っているホストの harness の写し）。
- 手段があるホストでは、**仕様リポジトリの中で汎用のサブエージェントや別セッションを起動して代用しない**（分析物を自分で読みに行けるので、隔離にならない）。
- 手段が無いホスト（`HOST.md` に「無い」とある）では通常のサブエージェントで起動し、
  機械で強制されていないことを台帳の `verifier` 欄に `prompt-isolated` と残す（§3。明示格下げ）。
- 指示テンプレートの `isolation_check` 欄は、起動手段の定義が値の書き方を指示する場合だけ意味がある
  （それ以外の検証官が書いた値は隔離の根拠にしない。合否は `HOST.md` の確かめ方で決める）。
- **起動手段が「検証できる主張の範囲」を限定している場合はそれに従う**（`HOST.md` の「検証官の隔離」節）。渡されたパスの
  読み取りしかできない手段では、唯一型・全称型・不在型は**分母を誰が決めたか**で意味が変わる——**【原典パス】には母集団の走査コマンド
  （`母集団:` 行）の出力を全部渡す**（検証官が全部読んだことを手段側が確かめる）。候補を自分の判断で選んで渡すと「渡した集合の中で」
  の判定になり、生成側の視野を引き継ぐ（SB-12）。その形の結果と、範囲外の主張は `verified` にせず、GP-16 ルール8 の縮退へ回す。

> **【着手前に必ず確認】ブロックが大きすぎないか（GP-103 / SB-102）**
> `fabricated=0` は全数合格ゲートなので、**1 ブロックの主張数が多いと収束しない**
> （1 主張 95% 正答でも 100 主張の全数合格は 0.6%）。着手前に上限を確認する:
> - **主張 15 件以下**（`path:line` を含む行 ＋ 表のデータ行を 1 主張として数える）
> - 本文 **8KB 以下**。束ねてよいのは**同じファイルの同じ節の中**（主張 3 行以下のブロックは束ねることを推奨。GP-103 ルール1）
>
> 超えていたら**Verify を始める前にブロックを分割する**（別 `block_id` を採る。HOLD-1 不要）。
> `bash spec-extraction/03-audit/gates.sh density` の **`G-BLOCK-SIZE`** で機械確認できる。
> **実運用の失敗（FB-7）**: 100 主張・52KB のブロックで 7 ラウンド／未収束（1→7 と増加）、
> 残り 40 ファイルで 120〜240 時間の見積りとなり運用停止。**分割すれば並列に走るので実時間は縮む。**

> **【順序】断定型を優先する（GP-103 ルール6 / GP-16 ルール10-(7)）**
> ブロック内の主張は等価ではない。**「0 件 / 唯一 / すべて」型は反例 1 件で完全に崩れ、
> 結論の向きが変わる**（「対策不要」→「対策必要」）。「N 箇所ある」型は過小・過大に振れても近い値になりやすい。
> - **不在型（「0 件」「存在しない」「持たない」）はサブエージェントに渡す前に機械で絞る**:
>   識別子を抽出して**全ソース 1 パス走査**で反例を探す。走査語は識別子ではなく**役割**で設計し、
>   **正規表現の交替は長い識別子を先に置き語境界を付ける**（短い語が長い語に食い込む）。
> - **唯一型・全称型は機械では反例を探しにくい** → **隔離 Verify の優先対象**にする。
> - ブロック横断の分布は `bash spec-extraction/03-audit/gates.sh metrics` の
>   `assertion_density_absent` / `_unique` / `_universal` で測れる（合否は持たない測定値）。

**隔離の規律（GP-16 ルール2。破ると検証がアンカリングされ無効になる）:**
サブエージェントに渡してよいのは次の 2 つ **だけ**:
1. **生成ブロック本文**（spec ファイルの該当セクションをそのまま）
2. **原典ファイルのパス**（解析対象ソース内の、ブロックが引用しているファイル群のパス）

**渡してはいけないもの**: 生成時の推論・要約・分析物（02-analysis）・会話履歴・「この仕様は正しいはず」等の
先入観を与える説明。サブエージェントは一次情報（原典コード）に対してゼロから突合する。

**サブエージェントへの指示テンプレート:**

```
あなたは仕様記述の敵対的検証官である。任務は「確認」ではなく「反証」。
判断に迷ったら fabricated 側に倒す（デフォルトは不合格）。

以下の仕様ブロックの各主張について、引用された path:line を実際に開き、
次をすべて検査せよ:
1. 行番号が原典に実在するか（ファイル行数超過・ずれ）
2. 引用行が主張と同じ内容を指しているか（別内容の行を引いていないか）
3. 例外クラス・enum 値・キー名・HTTP コード等の固有名が原典と一致するか
4. 記述された挙動が live か（デッドコード・未配線・到達不能を live として書いていないか）
5. must/must not の強度が原典の実装で裏づけられるか（過大な一般化はないか)

また completeness の観点で、ブロックが扱う対象範囲において
「原典にあるのにブロックに書かれていない」事項（missing)を列挙せよ。

出力は次の JSON のみ（説明文を混ぜない）:
{
  "isolation_check": "denied | READ_SUCCEEDED | UNVERIFIED",
  "block_id": "<対象 ID>",
  "verdict": "CONFIRMED | PARTIAL | REFUTED",
  "fabricated": [
    {"claim": "<誤った主張の抜粋>", "cited": "<path:line>", "actual": "<原典の実際>", "type": "行番号不在|内容不一致|固有名誤り|デッド宣言|過大主張|件数不再現"}
  ],
  "missing": [
    {"what": "<欠落事項>", "evidence": "<path:line>"}
  ]
}

【検証対象ブロック】
<ブロック本文>

【原典パス】
<パス一覧>
```

### 2b. 件数宣言の再現 — 別の検証官に走査コマンドを実行させる（GP-22 ルール9）

**(a) 引用の裏取り（上の 2）だけでは件数・不在の誤りは見つからない。** 実測（ある完走試験の 1 層）で、
(a) の 3 巡は `fabricated` を 0 にできず、**最後の巡の誤りはすべて「書かれた走査コマンドを実行すると
別の数が出る」型**だった。引用は実在し内容も合っているので、(a) では何巡しても通る。

対象は、件数・不在・全数を述べる主張（`母集団:` の行、「N 件」「0 件」「存在しない」「すべて」「唯一」）を 1 つでも含むブロック（**これから検証するブロックだけ**。`verified` 済みには遡らない）。**(a) とは別の検証官**を起動する（同じ検証官に両方を頼むと (a) で満足して (b) を省く）。
**この検算官は上の機械的な隔離手段で起動できない**（走査コマンドの実行にシェルが要り、シェルのコマンド文字列は
パスで閉じ込められない）。起動方法は `HOST.md` の「検証官の隔離」節に従い、機械で強制されていないことを
台帳の notes に `count-verifier: prompt-isolated` と残す。
渡すものは (a) と同じ（ブロック本文と原典パスだけ）。

先に `bash spec-extraction/03-audit/gates.sh density` の **`G-SCANCMD`** を通す
（ERE の中の `\|` は常に 0 を返すので、機械で先に落とす）。

```
あなたは件数の検算官である。任務は「確認」ではなく「反証」。
以下のブロックで、件数・不在・全数を述べる主張（「N 件」「0 件」「存在しない」「すべて」「唯一」、
および「母集団:」の行）を 1 つずつ取り出し、次を行え:
1. 書かれた走査コマンドを原典のディレクトリで実行し、出力と終了コードを記録する。
   **読み取り専用のコマンドだけを実行する**（`sed -i`・`>`・`rm`・`mv` など書き込みを含むものは実行せず、
   fabricated（type: 件数不再現、actual: 「書き込みを含むため実行しない」）に挙げる。原典は変更しない＝SB-5）。
   件数の裏付けがコマンドでなく列挙（`:263,:267,…` 等）なら、列挙の要素を原典で確かめて数える。
2. 出力の数が主張の数と一致するか。一致しなければ、何を数えれば主張の数になるか（あるいは、ならないか）を書く。
3. 裏付けがコマンドも列挙も無い・実行できない（パスが無い・構文が誤り）・大小の区別などの条件が書かれていない
   ——いずれも fabricated（type: 件数不再現）に挙げる。
推測で数を書かない。実行していない数は報告しない。

出力は次の JSON のみ:
{"block_id": "<ID>", "counts": [{"claim": "<主張>", "command": "<実行したコマンド>", "rc": <終了コード>,
  "declared": <主張の数>, "actual": <出力の数>}],
 "fabricated": [{"claim": "<主張>", "cited": "<path:line またはコマンド>", "actual": "<実測>", "type": "件数不再現"}]}
```

**`verified` にしてよいのは (a) と (b) の両方で `fabricated` が 0 件のときだけ。**

### 3. 集計と台帳更新（Verify 結果の記録）

**先に隔離を確認する（検証官の自己申告で確かめない）。** 機械で制限する起動手段で起動した検証官（§2 (a)・抽出標本の検証）の
結果のうち、`HOST.md` の「検証官の隔離」節の確かめ方で隔離を確認できなかったものは、**集計にも台帳にも入れない**。
検証官が仕様リポジトリを読めた状態の結果だからである。
**この確認の対象は機械的手段で起動した検証官だけである。** 手段で起動できない検証官（§2b の件数の検算官、
手段が無いホストの検証官）の結果は確認の対象外で、`prompt-isolated` と記録したうえで採用する（捨てない）。

各サブエージェントの JSON を集計し、台帳を更新する:
- `fabricated_found` += 検出件数、`fabricated_open` = 未修復件数
- `verify_status`: fabricated が 0 なら `verified`、1 件以上なら `repairing`
- `verified_at` に実行日（`date +%Y-%m-%d` で取得）、`verifier` に、機械で隔離を確認した検証官なら `subagent-isolated`、
  手段が無いホストの検証官なら `prompt-isolated`（どちらかを機械から見分けられるようにする）

Verify の生出力（JSON）は `spec-extraction/03-audit/verify-log/` の下に保存する
（監査証跡。GP-22 チェック方法「構造化出力が残っているか」）。**ファイル名と束ね方は自由**——
1 ファイルに複数ブロック・複数の結果をまとめてよい。要件は 2 つだけ: **各結果が `block_id` を持つ**こと（指示テンプレートの出力にある）、
**何巡目の Verify かが名前か中身で分かる**こと（例: `<block_id>-r<巡>.json`、`<まとめの単位>-r<巡>.json`）。

### 4. Repair — fabricated の修復（発生元まで戻す。GP-1）

`repairing` のブロックについて、fabricated 指摘を 1 件ずつ処理する:
1. 指摘された path:line の**原典を開いて再裏取り**する（指摘の丸呑みもしない——検証官も誤りうる）。
2. 指摘が正しければ、spec の該当記述を原典に合わせて修正する。missing の欠落も同様に補う。
   **修復の単位は「指摘された行」ではなく「その数・その名前が現れる全箇所」**（GP-22 ルール9）。変えた数値・識別子を
   **同じファイル全体（ブロックの外を含む）と、それを引く他の仕様**で `grep` し直す（実測で、修復の波及がブロックの外に残った）。
3. 指摘が誤り（検証官の見落とし）なら、なぜ紛らわしかったかを踏まえて記述を明確化する（GP-16 ルール5）。
4. **再 Verify は「修正した主張とその直接の依存」に限定する**（ブロック全体を再検証しない。GP-103 ルール2）。
   隔離は維持したまま、渡すのは**修正後の当該主張 ＋ 原典パス**のみ。
   **ブロック全体の再 Verify は `verified` 昇格の直前に 1 回だけ**行う（差分検証の取りこぼしを拾う）。
5. **`missing` の列挙は初回 Verify のみ**に求める。再 Verify のサブエージェントには
   「`missing` は列挙不要。指定された主張の真偽のみ判定せよ」と明示する。
   **新規 `missing` を無制限に受けると発散する**（実運用で 4 ラウンド目に fabricated が 1→7 と増えた原因）。
   新しい欠落は `03-audit/observed-anomalies.md` の ANO / `🔍 UNKNOWN` として**別途起票し、
   当該ブロックの合否から切り離す**。
6. **3 ラウンドで fabricated_open が 0 にならない、または前ラウンドより増えたら HOLD-9 で停止する**
   （巡数と増加は**もとの主張の誤り**で数える。直前の修復で書き換えた行・取り込んだ missing・切り出しで書き直した行への指摘は
   「修復が作った誤り」として数えず、台帳の notes に `repair-induced: N` と書く。**総数は 5 巡まで**）
   （増加時は 3 ラウンドを待たず）。**その主張で初回なら (A) を自動で行い ADR に残す**（停止しない）。
   **同じ主張の 2 回目と (B) のときは、勝手に打ち切らず・勝手に続けず、ユーザーに相談する**（(B) の前に引用・走査を足して裏付けられるかを 1 回試す）。
   相談で示すのは (a) ラウンドごとの fabricated 推移 (b) 残存指摘 と、**3 択**（GP-103 ルール3。手順書 Step 3-1d が正本）:
   **(A) 切り出して書き直す**（同じ主張は 1 回まで。`notes` に `hold9-split-from: DB-N`）／
   **(B) 外して `partial` で残す**（`type` が過大主張か、再現手段の無い件数不再現＝裏付けなしの主張だけ。範囲は `[[ADR-N]]`）／
   **(C) もう 1 巡**（人が明示・ブロックにつき 1 回）。目標密度の変更は別に HOLD-7。
   **「上限を切って未検証で進む」を既定運用にしてはならない**（SB-20 の無効化）。

### 5. Gate — 反映判定（SB-20: verdict でなく fabricated=0）

- 台帳の `fabricated_open` が 0 になったブロックのみ `verified` にする。
- **総合 verdict（CONFIRMED/PARTIAL）を合否に使わない**——CONFIRMED でも fabricated が残っていれば Repair へ。
- 全対象の処理後、`bash spec-extraction/03-audit/gates.sh density` を実行し G-LEDGER が
  FAIL しないことを確認する。

### 6. 報告

ユーザーへの報告に含める: 処理ブロック数 / verified へ昇格した数 / fabricated 検出総数と内訳（type 別）/
Repair で修正した spec ファイル / 残作業（repairing のまま残ったブロックと理由）。
fabricated 検出率（検出ブロック数 ÷ Verify したブロック数）も報告する（実測 35% との比較でExtract 品質の指標になる）。

## 注意

- **この skill はオプションの加速装置。** skill が使えない環境では GP-16 ルール8 の段階的縮退
  （別コンテキスト再検証 → 人間サインオフ）で同じ台帳を手動更新する（pipeline-procedure Step 4-5b 参照）。
  台帳と G-LEDGER ゲートはホスト非依存であり、最終判定の強制力は skill なしでも変わらない。
- 解析対象ソースは参照専用（SB-5）。Verify・Repair で原典を変更しない。
- 台帳の更新は単一の書き手（このメインエージェント）が行う。サブエージェントに台帳を直接書かせない（GP-15 ルール2）。
